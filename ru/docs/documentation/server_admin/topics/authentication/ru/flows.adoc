=== Потоки аутентификации

_authentication flow_ - это контейнер аутентификации, экранов и действий во время входа, регистрации и других {project_name} рабочих процессов.

==== Встроенные потоки

{project_name} имеет несколько встроенных потоков. Вы не можете изменить эти потоки, но вы можете изменить требования потока в соответствии с вашими потребностями.

.Процедура
. Нажмите *Authentication* в меню.
. Нажмите на _браузер_ элемента в списке, чтобы увидеть подробности.

image:images/browser-flow.png[Браузер Flow]

===== Тип аутентификации

Имя аутентификации или выполняемое действие. Если аутентификация отстутствуется, она находится в подпотоке. Он может выполняться или не выполняться в зависимости от поведения его родителя.

. Печенье
+
При первом входе пользователя в систему {project_name} устанавливает сессионный cookie.  Если Cookie уже установлен, этот тип аутентификации успешен. Так как cookie провайдер вернул успех и каждое выполнение на этом уровне потока является _альтернативой_, {project_name} не выполняет другое выполнение. Это приводит к успешному входу.
. Kerberos
+
Аутентификатор по умолчанию отключен и пропущен во время просмотра браузера.
. Перенаправление идентификатора провайдера
+
Это действие настроено по ссылке *Действия* > *Конфигурация*. Он перенаправляется на другой IdP для <_identity_broker, идентификационный брокер>>.
. Формы
+
Поскольку этот подпоток помечен как _alternative_, он не будет выполняться, если прошел тип аутентификации *Cookie*. Этот подпоток содержит дополнительный тип аутентификации, который необходимо выполнить. {project_name} загружает выполнение для этого подпотока и обрабатывает их.

Первое выполнение — *Форма пароля для имени пользователя*, тип аутентификации, которая отображает страницу с именем пользователя и паролем. Он помечен как _required_, поэтому пользователь должен ввести правильное имя пользователя и пароль.

Второе исполнение - это подпоток *Browser - Conditional 2FA*. Это подпоток _conditional_ и выполняется в зависимости от результатов выполнения *Condition - User Configured* и *Condition - credential*. Если результат истинный, {project_name} загружает выполнение для этого подпотока и обрабатывает их.

Следующее выполнение — аутентификация *Условие - Настройка пользователя*. Эта аутентификация проверяет, настроен ли {project_name} на другие закачки для пользователя. Подпоток *Browser - Conditional 2FA* выполняется только тогда, когда пользователь имеет настроенные OTP учетные данные.

Следующее выполнение — это аутентификация *Условие - учетные данные*. Этот шаг проверяет, что процесс аутентификации уже аутентифицировал пользователя с учетными данными WebAuthn (passkey), избегая в этом случае 2FA.

Окончательное исполнение — это *OTP формат*. {project_name} помечает это выполнение как _альтернатива_, но он запускается только тогда, когда пользователь имеет Учетные данные OTP из-за установки в подпотоке _conditional_ . Если учетные данные OTP не настроены, пользователь не видит OTP формы.

Поток по умолчанию *browser* содержит еще два исполнения в *Browser - Conditional 2FA*, *WebAuthn Authenticator* и *Recovery Authentication Code Form*. По умолчанию эти команды _Disabled_ и являются другими 2FA методами, которые могут быть добавлены к потоку. Измените требование с _Disabled_ на _Alternative_ для того, чтобы сделать их доступными, если соответствующие учетные данные были настроены для пользователя. Если пользователь сконфигурировал все альтернативные типы учетных данных, то по умолчанию отображаются учетные данные с наивысшим приоритетом. Тем не менее, появится опция *Попробуйте еще один путь*, так что у пользователя есть альтернативные методы входа.

[[_execution-requirements]]
===== Требование

Выпадающее меню, контролирующее выполнение действия.

Требуется:: Все _Требуемые_ элементы в процессе должны быть успешно выполнены. Поток завершается, если требуемый элемент не работает.
Альтернативный:: Только один элемент должен успешно выполняться для того, чтобы процесс оценивался успешно. Потому что _Требуемые_ элементов потока достаточно, чтобы отметить поток, как успешный, любой элемент _Alternative_ потока внутри потока, содержащий элементы потока _Required_, не будет выполняться.
Отключено:: Элемент не считает поток успешным.
Условный:: Этот тип требования устанавливается только для подпотоков.
* _Условие_подпоток содержит выполнения. Эти заказы должны быть оценены в логических операциях.
* Если все команды вычисляют как _true_, то _Conditional_ функционирует как _Required_.
* Если какое-либо исполнение вычисляет как _false_, то подпоток _Conditional_ действует как _Disabled_.
* Если вы не установили выполнение, то _Conditional_ функционирует как _Disabled_.
* Если поток содержит выполнение и поток не установлен в _Conditional_, {project_name} не вычисляет выполнения, и выполнение считается функционально _Disabled_.

==== Создание потоков

Важные функциональные возможности и соображения безопасности применяются при проектировании потока.

Чтобы создать поток, выполните следующие действия:

.Процедура
. Нажмите *Authentication* в меню.
. Нажмите *Создать поток*.

[NOTE]
====
Вы можете скопировать и затем изменить существующий поток. Нажмите кнопку «Список действий» (три точки в конце строки), нажмите *Дублировать* и введите имя для нового потока.
====

При создании нового потока, вы должны сначала создать потоки верхнего уровня со следующими параметрами:

Наименование:: Имя потока.
Описание:: Описание, которое вы можете установить на поток.
Тип потока верхнего уровня:: Тип потока. Тип *client* используется только для аутентификации клиентов (приложений). Для всех остальных случаев выберите *основное*.

image:images/Create-top-level-flow.png[Высокий уровень]

Когда {project_name} создал поток, {project_name} отображает кнопки *Добавить шаг*, и *Добавить подпоток*.

image:images/New-flow.png[Новый Flow]

Поведение потоков и подпотоков определяет три фактора.

* Структура потока и подпотоков.
* Выводы в рамках потоков ресурсов
* Требования устанавливаются в рамках подпотоков и исполнений.

Выполнения имеют множество действий, от отправки сброса письма до проверки OTP. Добавить выполнение с помощью кнопки *Добавить шаг*.

image:images/Create-authentication-execution.png[Добавление выполнения аутентификации]

Выполнение аутентификации может по желанию иметь настроенное значение ссылки. Это может быть использовано в карте протокола _Authentication (AMR)_ для заполнения _amr_ претензий в доступе к OIDC и токенах идентификатора (более подробная информация по претензии
AMR claim, https://www. fc-editor.org/rfc/rfc8176.html[RFC-8176]). При настройке протокола _Authentication Reference (AMR)_ для клиента, он будет заполнять _amr_ претензией со значением ссылки для любого выполнения аутентификации, которое пользователь успешно завершает во время процесса аутентификации.

image:images/config-authenticator-reference.png[Настройка значения ссылки на аутентификацию]

Существуют два типа выполнений, _автоматические выполнения_ и _интерактивные выполнения_. _Автоматические выполнения_ похожи на выполнение *Cookie* и автоматически
выполнит свое действие в потоке. _Интерактивные вызвания_ остановить поток, чтобы получить вход. Выполнение успешно присвоено статус _success_.  Для завершения процесса ему необходимо хотя бы одно выполнение со статусом _success_.

Вы можете добавить подпотоки к потокам верхнего уровня с помощью кнопки *Добавить подпоток*. Кнопка *Добавить подпоток* отображает страницу *Создать объект исполнения*. Эта страница похожа на страницу *Создать форму верхнего уровня*. Разница в том, что *тип потока* может быть *основным* (по умолчанию) или *формы*. *Форма* создает подпоток, который генерирует форму для пользователя, аналогичную встроенному потоку *Регистрации*.
Успех подпотоков зависит от того, как они оценивают их исполнители, включая их содержащие подпотоки. Смотрите <_execution-requirements, execution requirements section>> для подробного объяснения того, как работают подпотоки.

[NOTE]
====
После добавления выполнения, проверьте, что требование имеет правильное значение.
====

Все элементы потока имеют опцию *Удалить* рядом с элементом. У некоторых выполнений есть пункт меню *⚙️* (значок передачи), чтобы настроить выполнение. Также можно добавить выполнение и вложенные потоки к вложенным потокам со ссылками *Добавить шаг* и *Добавить подпоток*.

Так как порядок выполнения важен, вы можете перемещать исполнение и подпотоки вверх и вниз, перетаскивая их имена.

[WARNING]
====
Проверьте, правильно ли протестировать конфигурацию при настройке потока аутентификации для подтверждения того, что в вашей установке не существует отверстий безопасности. We recommend that you test various
corner cases. Например, попробуйте протестировать поведение аутентификации для пользователя при удалении различных учетных данных из учетной записи пользователя до аутентификации.

В качестве примера, когда 2nd-факторные аутентификаторы такие как OTP или WebAuthn Authenticator, настроены в потоке как НЕОБХОДИМО и у пользователя нет регистрационных данных для конкретного типа
, пользователь сможет настроить определенные учетные данные во время самой аутентификации. Эта ситуация означает, что пользователь не аутентифицируется с этими учетными данными, поскольку он установил
это право во время аутентификации. Для аутентификации в браузере убедитесь, что ваш поток аутентификации настроен с такими учетными данными 1st-factor как Пароль или WebAuthn
Аутентификатор без паролей.
====

==== Создание беспарольного логического процесса

Чтобы проиллюстрировать создание потоков, этот раздел описывает создание расширенного потока входа в систему. Цель этого потока состоит в том, чтобы позволить пользователю выбрать между входом в систему с помощью xref:webauthn_{context}[WebAuthn], или двухфакторная аутентификация с помощью пароля и OTP.

.Процедура
. Нажмите *Authentication* в меню.
. Нажмите на вкладку *Блокировки*.
. Нажмите *Создать поток*.
. Введите в имени `Browser Password-less`.
. Нажмите *Создать*.
. Нажмите *Добавить исполнение*.
. Выберите из списка *Cookie*.
. Нажмите *Добавить*.
. Выберите *Альтернативу* для типа аутентификации *Cookie*, чтобы установить требование альтернативы.
. Нажмите *Добавить шаг*.
. Выберите *Kerberos* из списка.
. Нажмите *Добавить*.
. Нажмите *Добавить шаг*.
. Выберите из списка *Identity Provider Redirector*.
. Нажмите *Добавить*.
. Выберите *Альтернативу* для типа аутентификации *Identity Provider Redirector*, чтобы установить его требование в качестве альтернативы.
. Нажмите *Добавить подпоток*.
. Введите *Формы* в качестве имени.
. Нажмите *Добавить*.
. Выберите *Альтернативу* для аутентификации типа *Формы*, чтобы установить требование альтернативное.
+
image:images/Passwordless-browser-login-common.png[Логин браузера без пароля]
. Нажмите на меню *+* при выполнении *Формы*.
. Выберите *Добавить шаг*.
. Выберите из списка *Username Form*.
. Нажмите *Добавить*.

На данном этапе форма требует имя пользователя, но пароль не требуется. Мы должны разрешить аутентификацию паролей, чтобы избежать рисков безопасности.

. Нажмите на меню *+* подпотока *Формы*.
. Нажмите *Добавить подпоток*.
. Введите `Authentication` в качестве имени.
. Нажмите *Добавить*.
. Выберите *Обязательный* для *аутентификации* типа аутентификации, чтобы установить требуемое требование.
. Нажмите на меню *+* подпотока *Authentication*.
. Нажмите *Добавить шаг*.
. Выберите *WebAuthn Passwordless Authenticator* из списка.
. Нажмите *Добавить*.
. Выберите *Альтернативу* для типа аутентификации *Webauthn Passwordless Authenticator*, чтобы установить его требование в качестве альтернативы.
. Нажмите на меню *+* подпотока *Authentication*.
. Нажмите *Добавить подпоток*.
. Введите `Password with OTP` as name.
. Нажмите *Добавить*.
. Выберите *Альтернативу* для типа аутентификации *Password with OTP*, чтобы установить требование в качестве альтернативы.
. Нажмите кнопку *+* меню *Пароль с OTP* подпотоком.
. Нажмите *Добавить шаг*.
. Выберите из списка *Форма паролей*.
. Нажмите *Добавить*.
. Выберите *Обязательный* для того, чтобы тип аутентификации *Форма паролей*, устанавливал требование к нему.
. Нажмите кнопку *+* меню *Пароль с OTP* подпотоком.
. Нажмите *Добавить шаг*.
. Выберите из списка *OTP Форма*.
. Нажмите *Добавить*.
. Нажмите *Обязательный* для того, чтобы установить требуемый тип аутентификации *OTP формы*.

Наконец, измените привязки.

. Нажмите на меню *Action* в верхней части экрана.
. Выберите *Bind flow* из меню.
. Нажмите на выпадающий список *Browser Flow*.
. Нажмите *Сохранить*.

image:images/Passwordless-browser-login.png[Логин браузера без пароля]

После ввода имени пользователя поток работает следующим образом:

Если пользователи имеют учетные данные WebAuthn без паролей, они могут использовать эти учетные данные для прямого входа. Это логин без паролей. Пользователь также может выбрать *Password with OTP*, потому что выполнение `WebAuthn Passwordless` и `Password with OTP` flow равны *Альтернатива*. Если у них установлен *Обязательный*, то пользователь должен ввести WebAuthn, пароль и OTP.

Если пользователь выбирает ссылку *Попробуйте другой способ* с помощью аутентификации `WebAuthn passwordless`, пользователь может выбрать между `Password` и `Passkey` (WebAuthn passwordless). При выборе пароля пользователю необходимо будет продолжить вход с назначенным OTP. Если у пользователя нет учетных данных WebAuthn, то пользователь должен ввести пароль и затем OTP. Если у пользователя нет учётных данных OTP, ему будет предложено записать одну.

[NOTE]
====
Так как выполнение WebAuthn без пароля установлено в *Альтернатива*, а не *Обязательно*, этот поток никогда не попросит пользователя зарегистрировать учетные данные WebAuthn. Для того чтобы пользователь имел учетные данные Webauthn, администратор должен добавить необходимое действие для пользователя. Сделать это:

. Включение *Webauthn Register Passwordless* required action in the realm (see the xref:webauthn_{context}[WebAuthn]).
. Установка требуемого действия с помощью меню управления *Учетные Сбросы* пользователя xref:ref-user-credentials_{context}[Credentials].

Создание расширенного потока, такого как это может иметь побочные эффекты. Например, если вы включите возможность сброса пароля для пользователей, это будет доступно из формы пароля. В потоке `Сбросить учетные данные` пользователи должны ввести их имя пользователя. Поскольку пользователь уже ввел ранее имя пользователя в `Browser Password-less` потоке, это действие не является необходимым для {project_name} и является неоптимальным для пользователя. Чтобы исправить эту проблему, вы можете:

* Дублировать поток "Сбросить учетные данные". Установите его имя на «Сбросить учетные данные для пароля», например.
* Нажмите *Удалить* (мусорный значок) шага *Выберите пользователя*.
* В меню *Действия* выберите *Привязать поток* и выберите в раскрывающемся списке *Сброс учетных данных* и нажмите *Сохранить*
====

[[_client-policy-auth-flow]]
==== Использование политики клиента для выбора потока аутентификации

<<_client_Policies>> может использоваться для динамического выбора потока Аутентификации на основе конкретных условий, например, запрашивая определенную область действия или ACR (ссылка на класс аутентификации в контексте аутентификации), используя `AuthenticationFlowSelectorExecutor` в сочетании с желаемым состоянием.

`AuthenticationFlowSelectorExecutor` позволяет выбрать соответствующий поток аутентификации и установить уровень аутентификации после завершения выбранного потока.

Возможная конфигурация предполагает использование `ACRCondition` в комбинации с `AuthenticationFlowSelectorExecutor`. Эта настройка позволяет вам выбрать поток аутентификации на основе запрошенного ACR и включить ACR значение с помощью <_mapping-acr-to-loa-realm, CR to LoA Mapping>>.

Подробнее см. <<_client_policy, Client Policies>>.

[[_step-up-flow]]
==== Создание браузерного процесса входа с механизмом ускорения

В этом разделе описано, как создать расширенный поток входа в браузер, используя механизм ускорения. Целью ускорения аутентификации является предоставление доступа к клиентам или ресурсам на основе определенного уровня аутентификации пользователя.

.Процедура
. Нажмите *Authentication* в меню.
. Нажмите на вкладку *Блокировки*.
. Нажмите *Создать поток*.
. Введите имя `Browser Incl Step up Mechanism`.
. Нажмите *Сохранить*.
. Нажмите *Добавить исполнение*.
. Выберите из списка *Cookie*.
. Нажмите *Добавить*.
. Выберите *Альтернативу* для типа аутентификации *Cookie*, чтобы установить требование альтернативы.
. Нажмите *Добавить подпоток*.
. Введите *Auth Flow* в качестве имени.
. Нажмите *Добавить*.
. Нажмите *Альтернатива* для типа аутентификации *Auth Flow*, чтобы установить требование альтернативы.

Теперь вы настраиваете поток для первого уровня аутентификации.

. Нажмите кнопку *+* меню *Авторизации*.
. Нажмите *Добавить подпоток*.
. Введите `1-е Условие Flow` в качестве имени.

Чтобы использовать ускоряющий механизм, в запросе аутентификации укажите запрошенный уровень аутентификации (LoA). Параметр "претензии" используется для этой цели:

[source,subs=+attributes]
----
https://{DOMAIN}{kc_realms_path}/{REALMNAME}/protocol/openid-connect/auth?client_id={CLIENT-ID}&redirect_uri={REDIRECT-URI}&scope=openid&response_type=code&response_mode=query&nonce=exg16fxdjcu&claims=%7B%22id_token%22%3A%7B%22acr%22%3A%7B%22essential%22%3Atrue%2C%22values%22%3A%5B%22gold%22%5D%7D%7D%7D
----

Параметр `claims` указан в представительстве JSON:

[source]
----
claims= {
            "id_token": {
                "acr": {
                    "essential": true,
                    "values": ["gold"]
                }
            }
        }
----

Адаптер JavaScript {project_name} поддерживает легкое создание JSON и отправку его в запросе входа.
Смотрите *Keycloak JavaScript адаптер* по ссылке:{securing_apps_link}[защита приложений] для получения более подробной информации.

Вы также можете использовать упрощенный параметр `acr_values` вместо параметра `claims`, чтобы запрашивать определенные уровни в качестве ненеобходимых. Это упомянуто
в спецификации OIDC.

Вы также можете настроить уровень по умолчанию для конкретного клиента, которая используется, когда отсутствует параметр `acr_values` или параметр `claims` с претензией `acr`.
Подробнее см. <<_mapping-acr-to-loa-client,Client ACR configuration>).

NOTE: Запрашивать acr_values как текст (например `gold`) вместо числового значения, вы настраиваете сопоставление между ACR и LoA.
Можно настроить его на уровне Realm (рекомендуется) или на уровне клиента. Для настройки смотрите <<_mapping-acr-to-loa-realm,ACR to LoA Mapping>.

Подробнее читайте на https://openid.net/specs/openid-connect-core-1_0.html#acrSemantics[official OIDC specification].

*Логика потока*

Логика предыдущего настроенного потока аутентификации выглядит следующим образом: +
Если клиент запрашивает высокий уровень аутентификации, значение уровень аутентификации 2 (LoA 2), пользователь должен выполнить полную двухфакторную аутентификацию: Имя пользователя/Пароль + OTP.
Однако, если у пользователя уже есть сеанс в {project_name}, который был зарегистрирован с логином и паролем (LoA 1), запрашивается только второй коэффициент аутентификации (OTP).

Параметр *Max Age* в условии определяет, сколько секунд (максимум) является допустимым. This setting helps to decide
whether the user will be asked to present the authentication factor again during a subsequent authentication. If the particular level X is requested
by the `claims` or `acr_values` parameter and user already authenticated with level X, but it is expired (for example max age is configured to 300 and user authenticated before 310 seconds)
then the user will be asked to re-authenticate again with the particular level. Однако, если уровень еще не истек, пользователь будет автоматически
считаться аутентифицированным на этом уровне.

*Макс. Возраст* со значением 0 означает, что данный уровень действителен только для одной аутентификации. Следовательно, каждый повторный запрос на этот уровень
должен пройти повторную аутентификацию на этом уровне. Это полезно для операций, которые требуют повышенной безопасности приложения (например, отправить платеж) и всегда требуют аутентификации
на конкретном уровне.

WARNING: Обратите внимание, что такие параметры, как `claims` или `acr_values` могут быть изменены пользователем в URL-адресе, когда запрос логина отправлен от клиента к {project_name} через браузер пользователя.
Эта ситуация может быть смягчена, если клиент использует PAR ((Pushed authorization request), объект запроса, или другие механизмы, препятствующие пользователю переписать параметры в URL.
Следовательно, после аутентификации клиентам рекомендуется проверить идентификационный токен, чтобы дважды проверить, соответствует ли 'acr' ожидаемому уровню.

Если явный уровень не запрашивается параметрами, {project_name} будет требовать аутентификации с первым условием LoA
в процессе аутентификации, например Имя Пользователя/Пароль в предыдущем примере. Когда пользователь уже был аутентифицирован на этом уровне
и на этом уровне истек, для повторной аутентификации пользователя не требуется, но значение «acr» в токене будет иметь значение 0. Этот результат рассматривается как аутентификация
на основе `Долгосрочного cookie браузера`, как указано в разделе 2 спецификации OIDC Core 1.0.

NOTE: Во время первой аутентификации пользователя, первый настроенный подпоток с *Условным - уровень аутентификации* всегда выполняется (независимо от запрашиваемого уровня), так как
пользователь еще не имеет никакого уровня. Поэтому мы рекомендуем, чтобы подпоток первого уровня содержал минимальные необходимые аутентификаторы для аутентификации пользователей. Кроме того, убедитесь, что подпотоки с разными значениями *Conditional - Level Authentication* упорядочиваются начиная с наименьшего из описанных
в примере выше. For example, if you configure a subflow with level 2 and then add another subflow with level 1, the level 2 subflow will be always asked during the first authentication, which may
not be the desired behavior.

NOTE: Конфликтующая ситуация может возникать, когда администратор задает несколько потоков, устанавливает разные уровни LoA для каждого и назначает потоки различным клиентам. Однако, правило всегда то же самое: если пользователь имеет определенный уровень, он должен иметь только такой уровень, чтобы подключиться к клиенту. Это зависит от администратора, чтобы убедиться, что LoA является последовательным.

NOTE: Авторизация с уровнем аутентификации предназначена для вариантов использования, когда на каждом уровне
требуется все методы аутентификации с предыдущих уровней.
Например, уровень X должен всегда включать все методы аутентификации, требуемые уровнем X-1.
Для вариантов использования, где конкретный уровень, такой как уровень 3, требует другой метод аутентификации по сравнению с предыдущими уровнями
может быть более целесообразно использовать сопоставление ACR с определенным потоком.
Подробнее см. <<_client-policy-auth-flow, Использование политики клиента для выбора аутентификации Flow>>.

*Пример сценария*

. Max Age настроен как 300 секунд для условия уровня.
. Запрос на вход отправлен без запроса какого-либо акра. Уровень 1 будет использоваться, и пользователю необходимо авторизоваться с помощью имени пользователя и пароля. У токена будет `acr=1`.
. Другой запрос на вход отправляется через 100 секунд. Пользователь автоматически аутентифицирован из-за SSO, и токен вернёт `acr=1`.
. Другой запрос на вход отправлен через еще 201 секунду (301 секунду с момента аутентификации в точке 2). Пользователь автоматически аутентифицирован из-за SSO, но токен возвращает `acr=0` из-за уровня 1 считается просроченным.
. Другой запрос на вход отправлен, но теперь он явно запросит ACR уровня 1 в параметре `claims`. User will be asked to re-authenticate with username/password
and then `acr=1` will be returned in the token.

*Претензия ACR в токен*

ACR претензия добавляется в токен с помощью карты протокола `acr loa level` протокола, определенного в области области клиента `acr`. This client scope is the realm default client scope
and hence will be added to all newly created clients in the realm.

Если вы не хотите, чтобы `acr` востребовал внутри токенов, или вам нужна пользовательская логика для его добавления, Вы можете удалить область деятельности клиента из вашего клиента.

Обратите внимание, когда запрос на вход инициирует запрос с параметром `claims`, запросив `acr` как претензию `essential`, а {project_name} всегда возвращает
один из указанных уровней. Если он не может возвращать один из указанных уровней (например, если запрашиваемый уровень неизвестен или больше настроенных условий
в потоке аутентификации), тогда {project_name} выбросит ошибку.

[[_step-up-authentication-saml]]
==== Расширенная аутентификация для SAML

Для протокола SAML, постепенная аутентификация использует элемент `<AuthnContextClassRef>` (аутентификация в контексте класса или ACR) для сопоставления уровня аутентификации (LoA). Этот элемент представляет собой URI ссылку, которая идентифицирует контекстное объявление аутентификации. Запрос LoA запрошен клиентом в запросе SAML через элемент `<RequestedAuthnContext>`.

[source,xml,subs=+attributes]
----
<samlp:AuthnRequest xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol" xmlns="urn:oasis:names:tc:SAML:2.0:assertion" xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion" AssertionConsumerServiceURL="https://sp.example.com/" Destination="https://localhost:8543/realms/demo/protocol/saml" ForceAuthn="false" ID="1cc6ba19-b34d-48d5-ac44-3c4b2598b6c3" IssueInstant="2025-12-10T16:29:41.177Z" ProtocolBinding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST" Version="2.0">
  <saml:Issuer>https://sp.example.com/</saml:Issuer>
  <samlp:NameIDPolicy Format="urn:oasis:names:tc:SAML:2.0:nameid-format:transient"/>
  <samlp:RequestedAuthnContext>
    <saml:AuthnContextClassRef>urn:oasis:names:tc:SAML:2.0:ac:classes:TimeSyncToken</saml:AuthnContextClassRef>
    <saml:AuthnContextClassRef>urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport</saml:AuthnContextClassRef>
  </samlp:RequestedAuthnContext>
</samlp:AuthnRequest>
----

Запрос запрашивает набор контекстов аутентификации, которые будут оцениваться {project_name} в порядке до тех пор, пока один из них не сможет быть удовлетворен. Это означает, что {project_name} знает, что URI объявление и есть уровень, который достаточно для запроса. Если ни один из указанных контекстов не может быть удовлетворен, то {project_name} возвращает сообщение `<Response>`, используя второй уровень `<StatusCode>` из `urn:oasis:names:tc:SAML:2.0:status:NoAuthnContext`.

[source,xml,subs=+attributes]
----
<samlp:Response xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol" xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion" Destination="https://sp.example.com/" ID="ID_70625c64-004a-44cc-b338-74802f0cc37d" InResponseTo="b935f66a-8185-40b6-990c-bd5f4971773e" IssueInstant="2025-12-10T17:00:46.894Z" Version="2.0">
  <saml:Issuer>https://localhost:8543/auth/realms/demo</saml:Issuer>
  <samlp:Status>
    <samlp:StatusCode Value="urn:oasis:names:tc:SAML:2.0:status:Responder">
      <samlp:StatusCode Value="urn:oasis:names:tc:SAML:2.0:status:NoAuthnContext"/>
    </samlp:StatusCode>
  </samlp:Status>
</samlp:Response>
----

Если {project_name} может выполнить запрос, вызывается ускоренный поток аутентификации, чтобы аутентифицировать пользователя на указанном уровне. SAML ответ, используя `<AuthnStatement>` элемент в успешном ответе, будет содержать `<AuthnContextClassRef>с контекстом, наконец.

Когда функция `step-up-authentication-saml` включена, <_mapping-acr-to-loa-realm, CR до уровня аутентификации (LoA) Mapping>> представляет собой таблицу с тремя значениями: OpenID Connect ACR, контекст SAML URI и уровень аутентификации (LoA). Сопоставление может быть определено для обоих типов клиентов. Она также может быть переопределена на уровне клиента, но в данном случае присутствуют только URI и LoA. Опции дополнительной аутентификации для клиентов SAML находятся во вкладке **Дополнительные** **Дополнительные настройки**. Смотрите главу <<_client-saml-configuration,Создание SAML-клиента>> .

Итак, когда расширенная аутентификация настроена для SAML, {project_name} обрабатывает указанный уровень контекста в SAML запросе, и минимальный ACR, разрешенный для клиента (если он присутствует), чтобы получить LoA (целочисленный уровень), который должен быть достигнут при аутентификации. Если нет доступного уровня, удовлетворяющего запросу, то ошибка возвращается за спецификацию. Если отображение URI/LoA возвращает уровень, удовлетворяющий запросу, то начинается поток аутентификации, требующий достижения уровня аутентификации.

Для поддержания обратной совместимости, {project_name} не возвращает ошибку и продолжает добавлять предыдущий ACR `urn:oasis:names:tc:SAML:2. :ac:classes:unspecified` ответ в следующих ситуациях:

* Функция `step-up-authentication-saml` не включена в {project_name}.
* SAML клиент не определяет никакие сопоставления между контекстным URI и LoA. Используйте клиентское сопоставление вместо общей картины реалмов, когда вам просто нужно применить пополнение для определенных клиентов SAML.
* `AuthnContextClassRef mapper` не выполняется. Это сопоставление предоставляется новой моделью клиента `AuthnContextClassRef`, которая по умолчанию добавлена к SAML клиентам. Он отвечает за добавление получаемого `<AuthnContextClassRef>` к ответу.
+
NOTE: Карта и клиентская область «AuthnContextClassRef» автоматически создаются и назначаются SAML клиентам, когда включена функция «step-up-authentication-saml» (для новых и мигрированных миров). Если функция была отключена при создании или миграции и затем хотите использовать ее клиентская область с картографом должна быть создана и назначена клиенту вручную.
* Поставка, рассчитываемая в момент запроса, не достигается в результате процесса аутентификации. Например, если поток аутентификации для аутентификации не является ускоренным процессом, или есть неправильная конфигурация между отображением URI/LoA и окончательным уровнем, достигнутым в ускоренном процессе аутентификации.

[[_registration-rc-client-flows]]
==== Регистрация или сброс учетных данных, запрашиваемых клиентом

Обычно при перенаправлении пользователя на {project_name} из клиентского приложения, запускается `browser`. Этот поток может позволить пользователю <<con-user-registration_{context}, register>> в случае, если
включена регистрация, а пользователь нажимает `Register` на экране входа. Также, если <<enabling-forgot-password,Forget password>> включено для реалма, пользователь может
нажмите `Забыли пароль` на экране входа, которая запускает поток «Сброс учетных данных», в котором пользователи могут сбросить учетные данные после подтверждения адреса электронной почты.

Иногда клиентское приложение может быть полезно напрямую перенаправлять пользователя на экран *Регистрации* или *Сброс учетных данных*. The resulting action will match the action of when the
user clicks *Register* or *Forget password* on the normal login screen. Автоматическое перенаправление на экран регистрации или сброса регистрационных данных может быть сделано следующим образом:

* Когда клиент хочет, чтобы пользователь был перенаправлен непосредственно на регистрацию, OIDC клиент должен добавить параметр `prompt=create` к запросу входа. As a deprecated alternative, clients can replace the very last
snippet from the OIDC login URL path (`/auth`) with `/registrations` . Таким образом, полный URL может быть похож на следующее: `https://keycloak.example.com/realms/your_realm/protocol/openid-connect/registrations`.
Рекомендуется `prompt=create` как https://openid.net/specs/openid-connect-prompt-create-1_0.html[стандарт спецификации].
* Когда клиент хочет, чтобы пользователь был перенаправлен непосредственно на поток «Сбросить учетные данные», OIDC клиент должен заменить последний snippet с пути OIDC входа (`/auth`) на `/forgot-credentials` .

WARNING: Предыдущие шаги являются единственным поддерживаемым методом для того, чтобы клиент напрямую запросил поток регистрационных данных или сбросов. В целях безопасности
он не поддерживается и не рекомендуется для клиентских приложений для обхода потоков OIDC/SAML и прямого перенаправления на другие конечные точки {project_name} (например, конечные точки в
`/realms/realm_name/login-actions` или `/realms/realm_name/broker`).

[[_user_session_limits]]
=== Ограничения сессий пользователя

Ограничение количества сеансов, которое может иметь пользователь. Сессии могут быть ограничены в одном мире или на одном клиенте.

Чтобы добавить лимиты сессий к потоку, выполните следующие действия.

. Нажмите *Добавить шаг* для потока.
. Выберите *Ограничение количества сессий пользователей* из списка.
. Нажмите *Добавить*.
. Нажмите *Обязательно* для того, чтобы установить требуемый тип аутентификации *Ограничение количества пользователей*.
. Нажмите *⚙️* (иконка передачи) для *Ограничения количества сессий пользователей*.
. Введите псевдоним для этой конфигурации.
. Введите требуемое максимальное количество сеансов, которое может иметь пользователь в этом реалме. Например, если 2 значения являются значениями, то в этом мире максимальное число сессий SSO составляет 2 сеанса. Если значение равно 0, то флажок отключен.
. Введите требуемое максимальное количество сессий, которое пользователь может иметь для клиента. Например, если 2 - это значение, то для каждого клиента максимальное число сессий SSO - 2 сеанса. Таким образом, когда пользователь пытается аутентифицироваться в клиентском `foo`, но этот пользователь уже авторизовался в 2 SSO сеансах для клиента `foo`, либо аутентификация будет запрещена, либо уже существующие сессии будут убиты на основании настроенного поведения. Если используется значение 0, этот флажок отключен.
Если разрешены лимиты сеансов и лимиты сеансов клиента, то имеет смысл иметь ограничения на сеансы работы с клиентом всегда ниже, чем лимиты сессий. Лимит на один клиент никогда не может превышать лимит всех SSO сеансов данного пользователя.
. Выберите поведение, необходимое при попытке пользователя создать сессию после достижения лимита. Доступные поведения:
- *Отклонить новую сессию* - при запросе нового сеанса и лимит сеанса не может быть создан.
- *Прекращение старой сессии* - при запросе нового сеанса и достижении лимита сеанса, старейшая сессия будет удалена и создана новая сессия.
. При необходимости добавьте пользовательское сообщение об ошибке, которое будет отображаться при достижении лимита.

Обратите внимание, что лимиты сессий пользователя должны быть добавлены к связанному потоку *браузера*, *Прямое предоставление потока*, *Сброс учетных данных*, а также *Почтовый поток*.
Авторизатор должен быть добавлен в точку, когда пользователь уже известен во время аутентификации (обычно в конце процесса аутентификации) и должен быть стандартно НЕОБХОДИМЫм. Note that it is not possible to have
ALTERNATIVE and REQUIRED executions at the same level.

Для большинства аутентификаторов, таких как `Direct grant flow`, `Reset credentials` или `Post broker login flow`, в конце процесса аутентификации рекомендуется добавить аутентификатор в качестве НЕОБХОДИМЫ.
Вот пример потока «Сброс учетных данных»:

image:images/authentication-user-session-limits-resetcred.png[Ограничения сессий аутентификации пользователя по сбросу учетных данных]

Для потока `Browser` попробуйте не добавить идентификатор сессии при потоке верхнего уровня. Эта рекомендация связана с аутентификатором `Cookie`, который автоматически повторно аутентифицирует пользователей на основе
на SSO cookie. Это на верхнем уровне и лучше не проверять лимиты сеансов во время повторной аутентификации SSO из-за уже существующей сессии пользователя. Итак, вместо этого стоит добавить отдельный подпоток ALTERNATIVE
, такой как следующий пример `authenticate-user-with-session-limit` на том же уровне, как `Cookie`. Затем вы можете добавить ПОТРЕБУЕТСЯ подпоток, в следующем разделе `real-authentication-subflow`example, как вложенный поток `authenticate-user-with-session-limit` и добавьте `User Session Limit` на том же уровне. Внутри `реальный поток аутентификации`,
вы можете добавить реальных аутентификаторов подобным образом к потоку браузера по умолчанию. Следующий пример потока позволяет пользователям аутентифицироваться с провайдером идентификации или
с паролем и OTP:

image:images/authentication-user-session-limits-browser.png[Ограничения на сеанс аутентификации пользователя]

Что касается `Post Broker login flow`, вы можете добавить `User Session Limits` в качестве единственного аутентификатора в процессе аутентификации до тех пор, пока у вас нет других аутентификаторов, которые вы запускаете после аутентификации с вашим провайдером.  Тем не менее, убедитесь, что этот поток настроен как `Post Broker Flow` на вашем поставщике удостоверений. Это требование необходимо для того, чтобы
аутентификация с идентификационными провайдерами также принимала участие в лимитах сеансов.

NOTE: В настоящее время администратор отвечает за поддержание согласованности между различными конфигурациями. Так что убедитесь, что все ваши потоки используют одинаковую конфигурацию
из `User Session Limits`.

NOTE: Функция лимита сессий для CIBA недоступна.
