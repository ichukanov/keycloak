[[_x509]]
=== X.509 аутентификация пользователя сертификата клиента

{project_name} поддерживает вход с клиентским сертификатом X.509, если вы настроили сервер на использование взаимной аутентификации SSL.

Типичный рабочий процесс:

* Клиент отправляет запрос на аутентификацию через SSL/TLS канал.
* Во время рукопожатия SSL/TLS сервер и клиент обменивают свои сертификаты x.509/v3.
* Контейнер ({appserver_name}) проверяет путь к сертификату PKIX и дату окончания срока действия сертификата.
* x.509 клиентский сертификат удостоверяет сертификат клиента, используя следующие методы:
** Проверяет статус отзыва сертификата с использованием точек распределения CRL или CRL.
** Проверяет статус отзыва Сертификата с помощью OCSP (Online Certificate Status Protocol).
** Проверяет, соответствует ли ключ в сертификате ожидаемый ключ.
** Проверяет, соответствует ли расширенный ключ сертификата ожидаемому расширенному ключу.
* Если одна из этих проверок не удается, аутентификация x.509 не удалась. В противном случае аутентификатор извлекает идентификацию сертификата и сопоставляет его существующему пользователю.

Когда сертификат сопоставляется с существующим пользователем, поведение меняется в зависимости от потока аутентификации:

* В Browser Flow, сервер предлагает пользователям подтвердить свою личность или войти с помощью имени пользователя и пароля.
* В Direct Grant Flow, сервер подписывается пользователем.

IMPORTANT: Обратите внимание, что веб-контейнер отвечает за проверку пути сертификата PKIX. X.509 аутентификатор на стороне
{project_name} предоставляет только дополнительную поддержку для проверки срока действия сертификата, статуса отзыва сертификата и использования ключа. Если вы
с помощью {project_name} развернутого позади обратного прокси, убедитесь, что ваш обратный прокси настроен для проверки пути PKIX. If you
do not use reverse proxy and users directly access the {appserver_name}, you should be fine as {appserver_name} makes sure that PKIX path is validated as long
as it is configured as described below.

==== Возможности

Поддерживаемые источники идентификации сертификата:

* Совпадение SubjectDN с помощью регулярных выражений
* Атрибут электронной почты субъекта X500
* Электронное письмо субъекта X500 от расширения альтернативного имени (RFC822Name Общее имя)
* Другое имя предмета X500 от альтернативного расширения предмета. Это другое имя пользователя обычно называется директорией (UPN).
* Атрибут общего имени субъекта X500
* Выдача матчей с использованием регулярных выражений
* Серийный номер сертификата
* Серийный номер сертификата и эмитент
* Отпечаток сертификата SHA-256
* Полный сертификат в формате PEM

===== Регулярные выражения

{project_name} извлекает идентификацию сертификата из субъекта DN или DN эмитента, используя регулярное выражение в качестве фильтра. Например, это регулярное выражение соответствует атрибуту электронной почты:

```
emailAddress=(.*?)(?:,|$)
```

Регулярное выражение применяется, если `Identity Source` имеет значение `Match SubjectDN используя регулярное выражение` или `Match IssuerDN с помощью регулярного выражения`.

====== Сопоставление личности сертификата с существующим пользователем

Сопоставление идентификации сертификата может привести извлеченную идентификацию пользователя к существующему имени пользователя, , или пользовательский атрибут, значение которого соответствует идентификатору сертификата. Например, установка электронной почты `Identity source` в _Subject's email_ или `User mapping method` на _Username or email_ делает X. 09 аутентификатор сертификата клиента использует атрибут электронной почты в теме сертификата DN в качестве критерия поиска существующего пользователя по имени пользователя или по электронной почте.

[IMPORTANT]
====
* Если вы отключите *Войти с помощью электронной почты* в настройках Realm, то к аутентификации сертификата применяются те же правила. Пользователи не могут войти с помощью атрибута электронной почты.
* Использование `Certificate Serial Number and IssuerDN` в качестве источника идентификации требует двух пользовательских атрибутов для серийного номера и IssuerDN.
* `SHA-256 Сертификат thumbprint` является шестнадцатеричным представлением сертификата SHA-256.
* Использование `полного сертификата в формате PEM` в качестве источника идентификации ограничивается пользовательскими атрибутами, сопоставленными с внешними источниками федерации, такими как LDAP. {project_name} не может хранить сертификаты в своей базе данных из-за ограничений длины, поэтому в случае LDAP, вы должны включить `Always Read Value From LDAP`.
====

[[_x509-config]]
==== Настройка аутентификации сертификата X.509

image:images/x509-configuration.png[X509 Конфигурация]

*Источник идентификации пользователя*:: Определяет способ извлечения идентификации пользователя из клиентского сертификата.
*Каноническое представление DN включено*:: Определяет, следует ли использовать канонический формат для определения отличительного имени. Формат добавляет к RFC 2253 дополнительные правила нормализации. Официальная ссылка:https://docs.oracle.com/ru/java/javase/25/docs/api/java.base/javax/security/auth/x500/X500Principal.html#getName(java.lang.String)[Java API documentation] подробно описывает эти дополнения. Эта опция влияет только на следующие источники идентификации пользователя:
* _Совпадение SubjectDN с помощью регулярного выражения_
* _Выдача матчей с помощью регулярного выражения_
* _Серийный номер сертификата и номер эмитента_ (часть IssuerDN)

WARNING: Не включайте эту опцию, чтобы сохранить обратную совместимость с существующими экземплярами {project_name}.

WARNING: Формат `canonical` выполняет модификации по представленному DN в сертификате (т.е. пробелы удаляются или полное имя преобразуется в верхний и нижний регистры с использованием английской локали). Это поведение может привести к столкновениям в пользователе, совпадающем с данными, если центры сертификатов (США) выдают сертификаты не подтверждают присвоенный DN (e. ., если DNS выдаются с использованием любой локали и возникают проблемы при выполнении верхнего и нижнего регистров на английском языке). Не включайте эту опцию, если вы не можете гарантировать, что каноническое представление избегает дублирования для последующего сопоставления.

*Включить шестнадцатеричное представление серийных номеров*:: Представляет ссылку:https://datatracker.ietf.org/doc/html/rfc5280#section-4.1.2.2[serial number] как hexadecimal. Серийный номер с битом знака, установленным на 1, должен быть опущен 00-октетом. Например, серийный номер с десятичным значением _161_, или _a1_ в шестнадцатеричном представлении кодируется как _00a1_, согласно RFC 5280. link:https://datatracker.ietf.org/doc/html/rfc5280#appendix-B[RFC 5280, appendix-B] для получения более подробной информации.
*Регулярное выражение*:: Регулярное выражение для использования в качестве фильтра для извлечения идентификатора сертификата. Выражение должно содержать одну группу.
*Метод сопоставления пользователей*:: Определяет способ сопоставления идентификации сертификата с существующим пользователем. _Username или email_ ищет существующих пользователей по имени пользователя или электронной почте. _Пользовательский атрибут Mapper_ ищет для существующих пользователей с пользовательским атрибутом, который соответствует идентификатору сертификата. Имя пользовательского атрибута настраивается.
*Имя атрибута пользователя*:: Пользовательский атрибут, значение которого совпадает с идентификатором сертификата. Использовать несколько пользовательских атрибутов, когда сопоставление атрибутов связано с несколькими значениями, например, «Серийный номер сертификата и IssuerDN».
*CRL проверка включена*:: Проверьте статус отзыва сертификата с помощью списка отозванных сертификатов. Расположение списка задано в атрибуте *CRL файл пути*.
*Включить точку распределения CRL для проверки статуса отзыва сертификата*:: Используйте CDP для проверки статуса отзыва сертификата. Большинство властей PKI включают CDP в свои сертификаты.
*Путь к файлу CRL*:: Путь к файлу, содержащему список CRL. Значение должно быть путь к файлу, если опция *Проверка CRL включена* включена.
*Прервать CRL, если не обновлено*:: CRL соответствующий link:https://datatracker.ietf.org/doc/html/rfc5280#section-5.1.2.5[RFC 5280] содержит поле обновления, указывающее на дату выпуска следующего CRL. По истечении этого времени CRL считается устаревшей, и его следует обновить. Если эта опция `true`, аутентификация не будет выполнена, если CRL устарел (рекомендуется). Если параметр установлен в `false`, то устаревшая CRL по-прежнему используется для проверки пользовательских сертификатов.
*Проверка OCSP включена*:: Проверяет статус отзыва сертификата с использованием протокола о состоянии сертификатов.
*Не удалось открыть поведение OCSP*:: По умолчанию проверка OCSP-кода должна возвращать положительный ответ, чтобы продолжить успешную аутентификацию. Иногда эта проверка может быть неубедительна: например, OCSP-сервер может быть недоступен, перегружен или сертификат клиента не может содержать URI OCSP-ответчика. Когда этот параметр включен, аутентификация будет отклонена только в том случае, если OCSP-отправитель получил отрицательный ответ и сертификат определенно отозван. Если правильный OCSP-ответ не доступен, то будет принята попытка аутентификации.

NOTE: OCSP retry поведение настроен на весь сервер через HTTP клиента провайдера. Смотрите <@links.server id="outgoinghttp"/> для подробной информации о настройке повторных параметров для всех исходящих HTTP-запросов, включая проверку OCSP.

*OCSP Responder URI*:: Переопределяет значение URI OCSP-ответчика в сертификате.
*Проверить использование ключа*:: Проверяет установленный бит расширения KeyUsage. Например, "digitalSignature,KeyEncipherment" проверяет, установлены ли биты 0 и 2 в расширении KeyUsage.
Оставьте этот параметр пустым, чтобы отключить проверку использования ключа. См. link:https://datatracker.ietf.org/doc/html/rfc5280#section-4.2.1.3[RFC 5280, Section-4.2.1.3] для получения дополнительной информации. {project_name} вызывает ошибку, когда возникает несоответствие использования ключа.
*Проверка расширенного использования ключа*:: Проверяет одно или несколько целей, определенных в расширении использования ключа. См. link:https://datatracker.ietf.org/doc/html/rfc5280#section-4.2.1.12[RFC 5280, Section-4.2.1.12] для получения дополнительной информации. Оставьте этот параметр пустым, чтобы отключить проверку расширенного использования ключей. {project_name} вызывает ошибку, когда отмечено как критическое значение при выпуске CA и возникает несоответствие расширений использования ключа.
*Проверить политику сертификатов*:: Проверяет один или несколько OID политики, как это определено в расширении политики сертификатов. См. link:https://datatracker.ietf.org/doc/html/rfc5280#section-4.2.1.4[RFC 5280, Section-4.2.1.4]. Оставьте пустым параметр, чтобы отключить проверку политики сертификации. Несколько политик должны быть разделены запятыми.
*Режим проверки политики сертификатов*:: Когда в параметре «Подтвердить политику сертификата» указывается несколько политик, он решает, должно ли сопоставление проверяться для всех политик присутствовать, или один матч достаточно для успешной аутентификации. Значение по умолчанию - `Все`, что означает, что все запрошенные политики должны присутствовать в клиентском сертификате.
*Игнорировать подтверждение личности*:: Если этот параметр включен, аутентификация по сертификату X.509 не требует от пользователя подтверждения личности сертификата. {project_name} входит в систему после успешной аутентификации.
*Пересмотр клиентского сертификата*:: Если установлено, доверительная цепочка сертификатов клиента будет всегда верифицирована на уровне приложения, используя сертификаты, присутствующие в настроенном магазине доверия. Это может быть полезно, если лежащий в основе веб-сервера не требует проверки клиентской цепочки сертификатов, например, потому что он находится за невалидируемым балансировщиком нагрузки или обратным прокси, или если количество допустимых CAs слишком велико для взаимных переговоров по SSL (большинство браузеров ограничивают максимальный размер пакета для SSL-согласования на 32767 байт, , которая соответствует примерно 200 объявленных CAs). По умолчанию эта опция отключена.

===== Пример использования CURL

Следующий пример показывает, как получить токен доступа для пользователя в области `test` с прямым потоком грантов. Этот пример использует раздел
*OAuth2 Resource Owner Password Credentials Grant* по ссылке:{securing_apps_link}[securing apps] и конфиденциальный клиент `resource-owner`:

[source,bash,subs="attributes+"]
----
curl \
  -d "client_id=resource-owner" \
  -d "client_secret=40cc097b-2a57-4c17-b36a-8fdf3fc2d578" \
  -d "grant_type=password" \
  --cacert /tmp/truststore.pem \
  --cert /tmp/keystore.pem:kssecret \
  "https://localhost:8543/realms/test/protocol/openid-connect/token"
----

Файл `/tmp/truststore.pem` указывает на файл с хранилищем доверия, содержащий сертификат сервера {project_name}. Файл `/tmp/keystore.pem` содержит
закрытый ключ и сертификаты, соответствующие пользователю {project_name} , который был бы успешно аутентифицирован по этому запросу. Он зависит от конфигурации аутентификатора относительно того, как
точно соответствует содержимому сертификата, сопоставленного с пользователем {project_name} , как описано в <_x509-config, раздел конфигурации>>. `kssecret` может быть паролем этого файла ключевого хранилища.

В зависимости от вашего окружения, может потребоваться больше параметров для CURL команд, например:

* Параметр `--insecure`, если вы используете самоподписанные сертификаты
* Параметр `--capath` включает в себя весь каталог, содержащий путь к сертификату
* Опции `--cert-type` или `--key-type` если вы хотите использовать файлы, отличные от `PEM`

Для получения подробной информации обратитесь к документации по инструменту "curl". Если вы используете другие инструменты, кроме `curl`,
обратитесь к документации по инструменту. Однако эта настройка будет аналогичной.  Если вы используете конфиденциальный
клиент, необходимо включить ключевое хранилище и надёжное хранилище, а также учетные данные клиента.

NOTE: Если возможно, предпочтительнее использовать <<_service_accounts, Сервисные учетные записи>> вместе с аутентификацией клиента MTLS (аутентификатор клиента `X509 Certificate`), а не с использованием
прямого гранта с X. Аутентификация 09 может потребовать совместного использования пользовательского сертификата с приложениями клиента. When using service account, the tokens are obtained on behalf
of the client itself, which in general is better and more secure practice.
