=== W3C Web аутентификация (WebAuthn)

{project_name} поддерживает https://www.w3.org/TR/webauthn/[W3C Web Authentication (WebAuthn)]. {project_name} работает с сайтом https://www.w3.org/TR/webauthn/#webauthn-relying-party[Relying Party (RP)].

[NOTE]
====
Успех работы WebAuthn зависит от того, что пользователь поддерживает аутентификацию, браузер и платформу. Убедитесь, что ваш аутентификатор, браузер и платформа поддерживают спецификацию WebAuthn.
====

[NOTE]
====
В спецификации WebAuthn используется `user.id` для сопоставления публичных регистрационных данных с конкретной учетной записью пользователя в Relying Party. Этот идентификатор пользователя является непрозрачной последовательностью байт с максимальным размером 64 байта. {project_name} передает внутренний ID базы данных регистрации, которая в общих пользователях является UUID из 36 символов. Но, если пользователь из внешнего провайдера федерации пользователей, внутренний {project_name} ID это ссылка:{developerguide_link}#storage-ids[storage ID] в форме `f:<provider-id>:<user-id>`, который может превышать 64 байта. Пожалуйста, учтите это и используйте короткие идентификаторы для компонента провайдера федерации и для пользователей, исходящих от этого провайдера при комбинировании SPI и WebAuthn.
====

==== Настройка

Процедура установки поддержки 2FA WebAuthn заключается в следующем:

[[_webauthn-register]]
===== Проверка подлинности WebAuthn включена

. Нажмите *Authentication* в меню.
. Нажмите на вкладку *Обязательные действия*.
. Проверьте действие *Webauthn Register* переключателя *ON*.

Включите переключатель *Действие по умолчанию* на *ВКЛЮЧЕНИЕ*, если вы хотите, чтобы все новые пользователи регистрировали свои учетные данные WebAuthn.

[[_webauthn-authenticator-setup]]
==== Включить WebAuthn аутентификацию в потоке браузера по умолчанию

. Нажмите *Authentication* в меню.
. Нажмите на *Браузер* поток.
. Найдите выполнение *WebAuthn Authenticator* внутри подпотока *Browser - Conditional 2FA*.
. Измените _requirement_ с _Disabled_ на _Alternative_ для этого выполнения.
+
image:images/webauthn-browser-flow-conditional-with-OTP.png[Web Authn flow conditional with OTP]

С помощью этой конфигурации пользователи могут выбирать между использованием WebAuthn и OTP для второго фактора. Так как вложенный поток является _conditional_, если они уже зарегистрировали один из соответствующих типов регистрационных данных. Если пользователь настроил оба типа учетных данных, по умолчанию будут показаны учетные данные с наивысшим приоритетом. Тем не менее, появится опция *Попробуйте еще один путь*, так что у пользователя есть альтернативные методы входа.

Если вы хотите заменить OTP для WebAuthn и поддерживать его в качестве условного условия:

. Изменить _requirement_ в формате *OTP на _Disabled_.
. Измените _requirement_ в *WebAuthn Authenticator* на _Alternative_.
+
image:images/webauthn-browser-flow-conditional.png[условие потока браузера Webauthn]

Если вам требуется для всех пользователей WebAuthn и принудительно их необходимо настроить учетные данные, если они не настроены:

. Измените _requirement_ в *Browser - Conditional 2FA* на _Required_.
. Изменить _requirement_ в формате *OTP на _Disabled_.
. Изменить _requirement_ в *WebAuthn Authenticator* на _Required_.
+
image:images/webauthn-browser-flow-required.png[Требуется поток браузера Webauthn]

Вы можете увидеть больше примеров конфигураций 2FA в <<twofa-conditional-workflow-examples>>.

==== Аутентифицироваться с WebAuthn аутентификатором

После регистрации WebAuthn аутентификатора пользователь осуществляет следующие операции:

* Открыть форму входа. Пользователь должен авторизоваться с помощью имени пользователя и пароля.
* Браузер пользователя просит пользователя авторизоваться с помощью аутентификации WebAuthn.

==== Управление WebAuthn администратором

===== Управление учетными данными

{project_name} управляет учетными данными WebAuthn, аналогично другим учетным данным из xref:ref-user-credentials_{context}[Управление учетными данными пользователя]:

* {project_name} назначает пользователям необходимое действие для создания учетных данных WebAuthn из списка *Сброс действий* и выберите *Webauthn Register*.
* Администраторы могут удалить учетные данные WebAuthn, нажав *Удалить*.
* Администраторы могут просматривать данные учётных данных, такие как AAGUID, выбрав *Показать данные...*.
* Администраторы могут установить метку для учетных данных, установив значение в поле *Метка пользователей* и сохранив данные.

Администраторы могут настраивать связанные с WebAuthn операции как *политику WebAuthn* в каждом реалме.

.Процедура

. Нажмите на вкладку *Политика*.
. Нажмите на вкладку *WebAuthn Policy*.
. Настроить элементы политики (см. описание ниже).
. Нажмите *Сохранить*.

Ниже приводятся настраиваемые элементы и их описания:

|Имя сервера для чтения в качестве Веб Authn Relying Party. Этот элемент является обязательным и применяется к регистрации WebAuthn аутентификатора. По умолчанию задано "маскирование". Подробнее см. https://www.w3.org/TR/webauthn/#dictionary-pkcredentialentity[WebAuthn Specification].

|Алгоритмы подписи
|Алгоритмы указывают, какой алгоритм подписи использовать для https://www.w3.org/TR/webauthn/#iface-pkcredential[Public Key Credential]. {project_name} использует открытый ключ для подписи и проверки https://www.w3.org/TR/webauthn/#authentication-assertion[Authentication Assertions]. Если алгоритмы не существуют, то адаптирован по умолчанию https://datatracker.ietf.org/doc/html/rfc8152#section-8.1[ES256] и https://datatracker.ietf.org/doc/html/rfc7518#section-3.1[RS256]. ES256 и RS256 являются дополнительным элементом конфигурации, применимым к регистрации WebAuthn аутентификаторов. |Идентификатор группы

Идентификатор должен быть эффективным доменом источника. Этот ID является необязательным элементом конфигурации, применяемым при регистрации WebAuthn аутентификаторов. Если эта запись пуста, то {project_name} адаптирует хост-часть базового URL-адреса {project_name}. Подробнее см. https://www.w3.org/TR/webauthn/[Specification].

|Настройки соответствия Атестации
|Реализация WebAuthn API в браузере (https://www.w3.org/TR/webauthn/#webauthn-client[WebAuthn Client]) является предпочтительным методом генерации утверждений Аттестации. Эта настройка является опциональным элементом конфигурации, применяемым к регистрации WebAuthn аутентификатора. Если опция не существует, то ее поведение такое же, как выбор «none». Подробнее см. https://www.w3.org/TR/webauthn/[Specification].

|Вложение аутентификатора
|Допустимый шаблон прикрепления WebAuthn аутентификатора для WebAuthn Клиента. Этот шаблон является необязательным элементом конфигурации, применяемым к регистрации аутентификатора WebAuthn. Подробнее см. https://www.w3.org/TR/webauthn/#enumdef-authenticatorattachment[WebAuthn Specification].

|Открываемые учетные данные
|Степень, в которой WebAuthn аутентификатор должен генерировать авторизацию открытого ключа как https://www.w3.org/TR/webauthn-3/[Client-side открываемые полномочия]. Принятые значения «required», «preferred» и «discouraged». Эта опция применяется к регистрации WebAuthn аутентификатора и заменяет и имеет приоритет устаревший параметр «Требовать обнаружения и раскрытия данных». Если оставить пустым ("не указано"), используется устаревшая опция `Require Discoverable Credential`. Подробнее см. https://www.w3.org/TR/webauthn/#dom-authenticatorselectioncriteria-residentkey[WebAuthn Specification].

|Требовать обнаруженные учетные данные
|*Устарело*, вместо этого используйте `Discoverable Credential`. Этот параметр планируется удалить в будущем и используется только в том случае, если «Открываемая учетная запись» останется как «не указана». Опция, требующая, чтобы аутентификатор WebAuthn генерировал авторизацию публичного ключа как https://www.w3.org/TR/webauthn-3/[Client-side discoverable Credential]. Эта опция применяется к регистрации WebAuthn аутентификатора. Если оставить пустым, его поведение такое же, как при выборе "Нет". Подробнее см. https://www.w3.org/TR/webauthn/#dom-authenticatorselectioncriteria-requireresidentkey[WebAuthn Specification].

|Опция, требующая, чтобы WebAuthn аутентификатор подтвердил верификацию пользователя. Это опциональный элемент конфигурации, применяющий к регистрации WebAuthn аутентификатора и аутентификации пользователя WebAuthn. Если ни один вариант не существует, его поведение такое же, как выбор "preferred". Подробнее см. https://www.w3.org/TR/webauthn/#dom-authenticatorselectioncriteria-userverification[Спецификация WebAuthn authenticator] и https://www.w3.org/TR/webauthn/#dom-publickeycredentialrequests-userverification[WebAuthn Specification for authenticator].

|Таймаут
|Значение тайм-аута в секундах для регистрации WebAuthn аутентификации и аутентификации пользователя с помощью WebAuthn аутентификатора. Если задано значение нуля, его поведение зависит от реализации WebAuthn аутентификатора. Значение по умолчанию: 0. Дополнительную информацию можно найти на https://www.w3.org/TR/webauthn/#dom-publickeycredentialcreationoptions-timeout[Спецификация WebAuthn для регистрации WebAuthn аутентификатора] и https://www.w3.org/TR/webauthn/#dom-publickeycredentialrequests-timeout[WebAuthn Specification for authenticator].

|Избегайте той же регистрации аутентификации
|Если этот параметр включен, {project_name} не может перезарегистрировать уже зарегистрированный WebAuthn аутентификатор.

|Допустимые AAGUID
|Список разрешенных AAGUID, которые WebAuthn аутентификатор должен зарегистрироваться. AAGUID (Attestation Global Unique Identifier) — это 128-битный идентификатор, указывающий тип аутентификатора (например, make и модель). Эта опция требует настройки **предпочтения транспортировки аттестации** (обычно 'Direct') для обеспечения передачи доверенного AAGUID. Если вы установите **Допустимые AAGUIDs** только те аутентификаторы могут зарегистрировать новые учетные данные WebAuthn.

==== Проверка аттестации выписки

При регистрации WebAuthn аутентификатора {project_name} проверяет достоверность аттестации, сгенерированной WebAuthn аутентификатором. {project_name} требует импортированные сертификаты якорей доверия в https://www.keycloak.org/server/keycloak-truststore[truststore].

Чтобы пропустить эту проверку, отключите этот магазин или установите в настройках политики WebAuthn пункт "Attestation Conveyance Preference" значение "none".

==== Управление учётными данными WebAuthn как пользователем

===== Зарегистрировать WebAuthn аутентификатор

Соответствующий метод регистрации WebAuthn аутентификации зависит от того, зарегистрировал ли пользователь учетную запись на {project_name}.

===== Новый пользователь

Если требуемое действие *Регистра WebAuthn* - это *Действие по умолчанию* в реалме, новые пользователи должны установить пароль после их первого входа.

.Процедура
. Открыть форму входа.
. Нажмите *Регистрация*.
. Заполните поля формы.
. Нажмите *Регистрация*.

После успешной регистрации, браузер просит пользователя ввести текст метки аутентификации WebAuthn.

===== Существующий пользователь

Если `WebAuthn Authenticator` настроен как требуется, как показано в первом примере то когда существующие пользователи пытаются войти в систему, они должны регистрировать свой WebAuthn аутентификатор автоматически:

.Процедура
. Открыть форму входа.
. Введите элементы в форме.
. Нажмите *Сохранить*.
. Нажмите *Login*.

После успешной регистрации браузер пользователя просит пользователя ввести текст ярлыка аутентификации WebAuthn.

[[_webauthn_aia]]
==== Регистрация учетных данных WebAuthn с помощью AIA

Учетные данные WebAuthn также могут быть зарегистрированы для пользователя, используя <<con-aia_{context},Application Initiated Actions (AIA)>>. Действия *Webauthn Register* (`kc_action=webauthn-register`) и *Webauthn Register Passwordless* (`kc_action=webauthn-register-passwordless`) доступны для приложений, если они включены в <<proc-setting-default-required-actions_{context}, Required actions tab>>.

Оба требуемых действия позволяют использовать параметр *skip_if_exists*, который позволяет пропустить выполнение AIA, если у пользователя уже есть учетные данные такого типа. `kc_action_status` будет *успешным*, если пропущен. Например, добавление опции в общее действие регистрации WebAuthn просто использует следующий параметр запроса `kc_action=webauthn-register:skip_if_exists`.

[[_webauthn_passwordless]]
==== Безпарольный WebAuthn вместе с двухфакторным

{project_name} использует WebAuthn для двухфакторной аутентификации, но вы можете использовать WebAuthn как первый фактор аутентификации. В этом случае пользователи с `passwordless` WebAuthn могут аутентифицироваться на {project_name} без пароля. {project_name} может использовать WebAuthn как механизм безпарольной аутентификации, так и механизм двухфакторной аутентификации в контексте области и единого потока аутентификации.

Администратор обычно требует, чтобы пароли, зарегистрированные пользователями для аутентификации WebAuthn, соответствовали различным требованиям. Например, пароли могут потребовать от пользователей аутентификации в Passkey с помощью PIN-кода или проверки Passkey с более сильным центром сертификации.

Из-за этого {project_name} разрешает администраторам настраивать отдельную `WebAuthn безпарольную политику`. Требуется `Webauthn Register Passwordless` действие типа и отдельный аутентификатор типа `WebAuthn Passwordless Authenticator`.

===== Настройка

Настройте поддержку WebAuthn без пароля:

. (если еще не существует) Зарегистрируйте новое необходимое действие для поддержки безпарольной работы WebAuthn. Используйте шаги, описанные в <_webauthn-register, Enable WebAuthn Authenticator Registration>>. Зарегистрируйте действие `Webauthn Register Passwordless`.
. Настроить политику. Вы можете использовать шаги и параметры конфигурации, описанные в <<_webauthn-policy, Managing Policy>>. Выполните конфигурацию в консоли администратора на вкладке *WebAuthn политики безпарольной политики*. Как правило, требования в отношении Passkey будут более сильными, чем в отношении двуфакторной политики. Например, вы можете установить *Требования для верификации пользователей* на *Обязательные* при настройке безпарольной политики.
. Настройте поток аутентификации. Используйте поток *WebAuthn Browser*, описанный в <_webauthn-authenticator-setup, добавляя WebAuthn Authentication к Browser Flow>>. Настройте поток следующим образом:
** Подпоток *WebAuthn Browser Forms* содержит *Username Form* как первый аутентификатор. Удалите аутентификатор *Имя Пользователя* Формы Пароль и добавьте *Идентификатор Форма Имя Пользователя*. Это действие требует от пользователя указать имя пользователя в качестве первого шага.
** Там будет необходимый подпоток, который можно назвать *безпарольным или двухфакторным*, например. Этот подпоток указывает на возможность аутентификации пользователя с учетными данными WebAuthn или с двухфакторной аутентификацией.
** Поток содержит *WebAuthn Passwordless Authenticator* в качестве первой альтернативы.
** Второй альтернативой будет подпоток с названием *Password And Two-factor Webauthn*, например. Этот подпоток содержит *Форму паролей* и *WebAuthn Authenticator*.

Окончательная конфигурация потока похожа на:

image:images/webauthn-passwordless-flow.png[PasswordLess flow]

Теперь вы можете добавить *Зарегистрировать WebAuthn без пароля* в качестве необходимого действия пользователю, уже известному {project_name}, чтобы протестировать это. Во время первой аутентификации пользователь должен использовать пароль и вторичный пароль WebAuthn. Пользователю не нужно предоставлять пароль и вторичные учетные данные WebAuthn, если они используют учетные данные WebAuthn.

[[_webauthn_loginless]]
==== LoginLess WebAuthn

{project_name} использует WebAuthn для двухфакторной аутентификации, но вы можете использовать WebAuthn как первый фактор аутентификации. В этом случае пользователи с `passwordless` WebAuthn могут аутентифицироваться на {project_name} без представления логина или пароля. {project_name} может использовать WebAuthn как механизм беспарольной аутентификации, так и механизм двухфакторной аутентификации в контексте Realm.

Администратор обычно требует, чтобы пароли, зарегистрированные пользователями для WebAuthn аутентификации отвечали различным требованиям. Авторизация требует от пользователей аутентификации по ключу Пароля (например, с помощью PIN-кода или отпечатка пальца) и что криптографические ключи, связанные с безлогичными учетными данными, хранятся физически на Passkey. Не все пароли соответствуют такому требованию. Проверьте у поставщика паролей, поддерживает ли ваше устройство проверку подлинности пользователя и идентификационные данные. Смотрите <<_webauthn-supported-keys, Поддерживаемые Passkeys>>.

{project_name} разрешает администраторам настроить `WebAuthn Passwordless Policy` таким образом, чтобы это позволяло аутентификацию без входа в систему. Обратите внимание, что аутентификация может быть настроена только с помощью `WebAuthn Passwordless Policy` и `WebAuthn Passwordless`. WebAuthn без логина и аутентификации WebAuthn может быть настроена на одном и том же мире, но будет иметь доступ к той же политике `WebAuthn без паролей`.

===== Настройка

Настройте поддержку аутентификации WebAuthn следующим образом:

. (Если еще не создан) Проверьте необходимое действие для *Регистрация WebAuthn без пароля* включено. Используйте шаги, описанные в <<_webauthn-register, Enable WebAuthn Authenticator Registration>>, но используйте *WebAuthn Register Passwordless* вместо *WebAuthn Register*.
. При необходимости настройте политику «WebAuthn Passwordless Policy». Выполните конфигурацию в консоли администратора, секции `Authentication` во вкладке `Политики` -> `WebAuthn Passwordless Policy`. По умолчанию, {project_name} устанавливает *Требования подтверждения пользователя* к *требованию* и *Доступные учетные данные* для правильной работы сценария без пароля. Обычно вместимость хранилища ограничена паролем, что означает, что вы не сможете хранить много видимых учетных данных на вашем пароле.
. Настройте поток аутентификации. Создайте новый поток аутентификации, добавьте выполнение "WebAuthn Passwordless" и установите параметры требования на *Обязательные*

Окончательная конфигурация потока похожа на:

image:images/webauthn-loginless-flow.png[LoginLess flow]

Теперь вы можете добавить необходимое действие `WebAuthn Register Passwordless` к пользователю, уже известному {project_name}, чтобы протестировать это. Пользователь с требуемым действием настроен должен авторизоваться (например имя пользователя/пароль) и будет предложено зарегистрировать Passkey для использования для безлогичной аутентификации.

===== Особые замечания поставщика

====== Список проверки совместимости

Для аутентификации с {project_name} требуется пароль для соответствия следующим функциям

** Соответствие FIDO2: не следует путать с FIDO/U2F
** Проверка пользователя: возможность парольного ключа аутентификации пользователя (не позволяет кому-то найти ваш Passkey иметь возможность аутентифицировать без пароля)
** Открываемая учётная запись: возможность Passkey хранить логин и криптографические ключи, связанные с клиентским приложением

====== Здравствуйте Windows

Для использования учетных данных на основе Windows Hello для аутентификации против {project_name}, настройте *Алгоритмы подписи* в параметре `WebAuthn Passwordless Policy`, чтобы включить значение *RS256*. Заметьте, что некоторые браузеры не разрешают доступ к паролю (например Windows Hello) в закрытых окнах.
