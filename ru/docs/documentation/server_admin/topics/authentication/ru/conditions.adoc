=== Условия в условных потоках

Как упоминалось в <<_execution-requirements, Execution requirements>, _Condition_ executions can be only contained in _Conditional_ subflow.
Если все _Условия_ выполняются вычисляются как true, то подпоток _Conditional_ действует как _Required_.
Вы можете обработать следующее выполнение в _Conditional_ подпотоке.
Если некоторые выполнения, включенные в _Conditional_ подпоток, вычисляются как false, то весь подпоток считается _Disabled_.

==== Доступные условия

`Состояние - роль пользователя`:: Это выполнение имеет возможность определить, имеет ли пользователь роль, определенную полем _User role_.
Если у пользователя есть необходимая роль, то выполнение считается верным, и оцениваются другие выполнения.
Администратор должен определить следующие поля:
Alias::: Описывает имя выполнения, которое будет показано в потоке аутентификации.
Роль пользователя::: Роль, которую пользователь должен выполнить для этого потока.
Для указания роли приложения синтаксис `appname.approle` (например, `myapp.myrole`).
`Состояние - Конфигурация пользователя`:: Это проверяет, настроены ли другие выполненные в процессе работы для пользователя.
Раздел «Требования к исполнению» содержит пример формы OTP.
«Условие - атрибут пользователя»:: Это проверяет, создал ли пользователь необходимый атрибут: опционально проверка может также оценивать атрибуты группы.
Существует возможность отрицать выход, что означает, что пользователь не должен иметь атрибут.
Раздел <<user-profile,User Attributes>> показывает, как добавить пользовательский атрибут.
Вы можете задать эти поля:
Alias::: Описывает имя выполнения, которое будет показано в потоке аутентификации.
Название атрибута::: Имя атрибута для проверки.
Ожидаемое значение атрибута::: Ожидаемое значение атрибута.
Включить атрибуты группы::: Если включено, условие проверяет, имеет ли один атрибут объединенной группы, соответствующий настроенному имени и значению: эта опция может повлиять на производительность
Отрицать вывод::: Вы можете отказаться от вывода.
Другими словами, атрибут не должен присутствовать.
`Состояние - выполняется подпоток`:: Условие проверяет, был ли предыдущий подпоток успешно исполнен (или не выполнен) в процессе аутентификации. Таким образом, поток может инициировать другие шаги, основанные на предыдущем подпотоке. Эти поля конфигурации существуют:
Имя потока::: Имя подпроцесса для проверки, было ли выполнено или не выполнено. Обязательно.
Результат проверки::: Когда условие вычисляется до истины. Если `executed` возвращает true, когда настроенный подпоток был выполнен с успехом вывода, false в противном случае. Если `not-executed` возвращает false, когда подпоток был выполнен с успехом вывода, true (отрицание предыдущей опции).
`Состояние - область клиента`:: Условие для определения того, присутствует ли сконфигурированная область деятельности клиента как клиентская область клиента, запрашивающего аутентификацию. Эти поля конфигурации существуют:
Название области действия клиента::: Имя области клиента, которая должна присутствовать как область клиента, запрашивающего аутентификацию. Если запрашиваемая область клиента является рамкой клиента клиента по умолчанию, то условие будет вычислено до истины. Если запрашиваемая область клиента является необязательной для клиента область для клиента, запрашивающего вход, условие будет выверено в true, если область действия клиента посылается клиентом в запросе на вход (например, по параметру `scope` в случае входа клиента OIDC/OAuth2). Обязательно.
Отрицать вывод::: Применить НЕ к результатам проверки. Если это правда, то условие будет определяться только в том случае, если настроенная область действия клиента не присутствует.
`Состояние - учетные данные`:: Это условие проверяет, был ли использован (или не используется) пользователем в процессе аутентификации. Параметры конфигурации:
Полномочия::: Список полномочий, подлежащих рассмотрению в соответствии с условием.
Включено::: Если *включено* истинно, условие будет вычисляться в `true`, если в процессе аутентификации используется любая из учётных данных, указанных в опции *credentials*, ложь в противном случае. Если *включено* является ложным, условие считается противоположным, это будет `true`, если никто из *учётных данных* не был использован и `false`, если один или несколько из них были использованы.

==== Ясно запретить или разрешить доступ в условиях потоков

Вы можете разрешить или запретить доступ к ресурсам при условном потоке.
Два аутентификатора «Запретить доступ» и «Разрешить доступ» доступ к ресурсам по условиям.

`Разрешить доступ`:: Аутентификатор всегда будет успешно аутентифицирован.
Этот аутентификатор не настраивается.
«Запретить доступ»:: Доступ всегда будет запрещен.
Вы можете определить сообщение об ошибке, которое будет показано пользователю.
Вы можете задать эти поля:
Alias::: Описывает имя выполнения, которое будет показано в потоке аутентификации.
Сообщение об ошибке::: Сообщение об ошибке, которое будет показано пользователю.
Сообщение об ошибке может быть предоставлено как сообщение или как свойство для использования с локализацией.
(то есть "_Вы не имеете роли 'admin'._", _my-property-deny_ в свойствах сообщений)
Оставьте пустым для сообщения по умолчанию, определяемого как свойство `access-denied`.

Вот пример, как запретить доступ всем пользователям, которые не имеют роли `role1` и показать сообщение об ошибке, определенное свойством `deny-role1`.
Этот пример включает в себя `Condition - User Role` и `Deny Access`.

image:images/deny-access-flow.png[Запретить потоку доступа]

image:images/deny-access-role-condition.png[Запретить настройки роли доступа]

image:images/deny-access-execution-cond.png[Запретить выполнение настроек]

Последнее - это определение свойства с сообщением об ошибке в теме `messages_ru.properties` (на английском языке):

[source]
----
deny-role1 = You do not have required role!
----

[#twofa-conditional-workflow-examples]
==== Примеры условного рабочего процесса 2FA

В разделе приведены примеры условных рабочих процессов, которые интегрируют второй фактор аутентификации (2FA) различными способами. Примеры копируют стандартный поток `browser` и изменяют конфигурацию внутри подпотока `forms`.

===== Условный подпоток 2FA

По умолчанию поток `browser` использует подпоток `Conditional 2FA`, который уже дает второй фактор аутентификации (2FA) с помощью формы OTP (One Time Password). Он также предоставляет коды WebAuthn и Recovery, но по умолчанию они отключены. В соответствии с этим подходом различные 2FA методы могут быть интегрированы в «Условие - Пользовательские настройки».

image:images/2fa-example1.png[2FA любая альтернатива]

Подпоток `forms` содержит другой условный подпоток `2FA` с `Condition - user configured`. В качестве альтернативных шагов допускаются три шага между двумя компонентами (OTP, Webauthn и Recovery Codes). Пользователь сможет выбрать один из трех вариантов, если они настроены для пользователя. Поскольку подпоток является условным, процесс аутентификации успешно завершится, если учетные данные не настроены.

Эта конфигурация обеспечивает то же поведение, что и при настройке с потоком *браузер* по умолчанию с обоими шагами _Disabled_ настроены на _Alternative_.

===== Условный 2FA подпоток и отказ в доступе

Второй пример остается прежним. После подпотока `2FA` другой поток `Запретить доступ, если нет 2FA` используется для проверки не выполнялся ли предыдущий файл `2FA`. В этом случае (пользователь не имеет настроенных учетных данных 2FA) доступ запрещен.

image:images/2fa-example2.png[2FA все альтернативные и запретить доступ]

`Condition - sub-flow executed` настроен на определение не выполнялся ли подпоток `2FA` ранее.

image:images/2fa-example2-config.png[Конфигурация для выполненного подпотока]

Шаг «Запретить доступ» отрицает аутентификацию, если не выполняется.

[[_conditional-2fa-otp-default]]
===== Условный 2FA подпоток с OTP по умолчанию

Последний пример очень похож на предыдущий. Вместо отказа в доступе, шаг «OTP формат» сконфигурирован по необходимости.

image:images/2fa-example3.png[2FA все альтернативы по умолчанию OTP]

С этим потоком, если у пользователя нет настроенных методов 2FA, настройки OTP будут принудительными, чтобы продолжить вход.
