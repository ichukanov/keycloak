{project_name} поддерживает протокол https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html[OpenID for Verifiable Credential Issuance (OpenID4VCI)] позволяющий выполнять роль эмитента в децентрализованных экосистемах идентификации. С помощью этого протокола вы можете выпускать подписанные цифровым подтверждением учетные данные (VC), которые полагаются на стороны (верификаторы) могут самостоятельно проверить без связи с {project_name}.

В этой главе объясняется, что такое проверяемые учетные данные, как работает протокол и проходит по каждому шагу, необходимому для настройки {project_name} для выдачи учетных данных.

=== Что такое проверяемые учетные данные?

Верифицируемые Учетные данные являются цифровым эквивалентом удостоверений личности, например паспорта, водительских прав или университетской степени. Они криптографически подписываются, взвешенные структуры данных, содержащие претензии о сущности (личности, организации или устройства).
Ключевые свойства VC:

- **Тампер-очевидный**: Любые изменения лишают криптографическую подпись.
- **Сохранение конфиденциальности**: Поддержка выборочного раскрытия информации (например, доказывает, что вы старше 18 лет, не раскрывая точную дату рождения).
- **Офлайн-проверенный**: верификатор может проверить действительность учетных данных без обращения к эмитенту.
- **Владелец контролируется**: Лицо, получающее учетные данные, контролирует когда и с кем передавать их.

==== Проверяемые учётные данные форматов

OpenID4VCI поддерживает несколько форматов учетных данных для кодирования и выдачи учетных данных:

- https://www.ietf.org/archive/id/draft-ietf-oauth-sd-jwt-vc-13.html[SD-JWT VC] – Выборочный токен для разглашения JSON Web Token Verifiable Credential
- https://github.com/decentralized-identity/jwt-vc-presentation-profile[JWT VC] – лицензия на верификацию сетевого токена JSON
- https://www.iso.org/standard/69084.html[mDL/mdoc] – Драйверная лицензия / формат документов для мобильных устройств

В настоящее время {project_name} поддерживает для выпуска SD-JWT VC и JWT VC. Поддержка mDL/mdoc запланирована на будущий релиз.

=== Модель держателя эмитента - верификатора

Доверяемые Учетные данные опираются на модель доверия, построенную вокруг трех различных ролей:

.Треугольник доверия — Модель верификатора держателя эмитента
image::images/oid4vci/triangle-of-trust.dio.svg[Diagram showing the Issuer-Holder-Verifier model, width=650]

* **Эмитент** — сущность (в данном случае {project_name}), которая подписывает и выпускает учетные данные. Губернатор _OpenID4VCI_.
* **Владелец** — физическое лицо или кошелёк, который получает, хранит и предъявляет учетные данные.
* **Верификатор** — доверенная сторона, которая проверяет подлинность и целостность учетных данных. Губернатор _OpenID4VP_.

Важное свойство приватности: издатель и верификатор никогда не общаются напрямую. Владелец контролирует какую информацию и с кем. Это означает, что эмитент не может отслеживать где, когда или как используются учетные данные.

=== Зачем использовать OpenID4VCI

OpenID4VCI предоставляет поддающиеся проверке учетные данные в экосистеме OpenID Connect вашей организации уже используется. Ключевые выгоды:

* **Interoperability** — построена поверх OAuth 2.0 и OpenID Connect, что делает возможным интеграцию с существующей инфраструктурой идентификации.
* **Конфиденциальность и безопасность** — поддерживает выборочное разглашение, полномочия на привязку ключей и проверку в автономном режиме.
* **Соответствие нормативным требованиям** — согласуется с такими структурами, как eIDAS 2.0 и формирующимися в мире правилами цифровой идентификации.
* **Эффективность разработчика** — Имеющиеся возможности управления аутентификацией, авторизацией и токенами {project_name}.

=== Приложения реального мира

Доверяемые полномочия открывают дверь для широкого круга практических применений:

* Цифровые удостоверения личности или водительские удостоверения, выданные правительствами, где граждане показывают только то, что необходимо (возраст, местожительство) для данной сделки.
* Проверяемые дипломы и свидетельства выдаваемые учебными заведениями, которые работодатели могут немедленно проверить без обращения в школу.
* Employee badges issued as VC for secure office access and remote authentication.
* Заявки на событие, которые являются очевидными и проверяются в автономном режиме.
* Полномочия членов профессиональных ассоциаций, предоставляющих доступ к закрытому контенту или местам проведения конференций.

=== Как работает выпуск мандатов: два основных теста

OpenID4VCI определяет два основных способа выдачи учетных данных. Который использовать зависит от того, должен ли пользователь аутентифицироваться интерактивно.

==== Код авторизации

Код авторизации Flow является интерактивным потоком, в котором держатель должен аутентифицировать и прямо дать согласие на выдачу удостоверений. Это идеально, когда требуется подтверждение пользователя перед выдачей учетных данных.

Этот поток повторно использует стандартную конечную точку авторизации OpenID Connect {project_name}, поэтому для этапа авторизации дополнительные конечные точки не требуются. Кошелек общается через зарегистрированный OIDC клиент, который должен иметь OID4VCI включен, и соответствующую область учетных данных клиента назначены.

**Как это работает:**

. **Пользователь** хочет учетные данные и инициализирует процесс через их кошелек.
. **Кошелек** отправляет запрос на авторизацию к конечной точке авторизации {project_name}(через OIDC клиент).
. {project_name} предлагает **Пользователю** войти в систему и дать согласие.
. **Пользователь** аутентифицирует и утверждает запрос учетных данных.
. {project_name} возвращает код авторизации **Wallet**.
. **Кошелек** обменивает код на конечной точке токена для токена доступа.
. **Кошелек** запрашивает верифицируемые учетные данные из контрольной точки (`/protocol/oid4vc/credential`), представляя токен доступа.
. {project_name} проверяет запрос, подписывает учетные данные и возвращает их в **Wallet**.

==== Пре-авторизованный кодовый поток

Поток кода до авторизации является неинтерактивным потоком. Эмитент создает предварительно одобренное предложение учетных данных, и кошелек может запросить учетные данные без аутентификации пользователя в реальном времени. Это полезно для массовых выпусков, автономных сценариев или когда пользователь уже был аутентифицирован другими способами.

Предложения для авторизации могут быть созданы через консоль администратора {project_name} , администратор REST API или программно через выделенную конечную точку (`/protocol/oid4vc/create-credential-offer`). Кошелек взаимодействует с зарегистрированным OIDC клиентом, у которого должен быть включен OID4VCI.

**Как это работает:**

. **Администратор** создает предварительно авторизованное предложение по учетным данным в {project_name} (через зарегистрированного клиента OIDC).
. {project_name} возвращает ранее авторизованный код и реквизитный URI.
. **Администратор** доставляет ранее утвержденный код **Wallet** (через QR-код, ссылку или электронную почту).
. **Кошелек** обменивает уже авторизованный код в точке Endpoint Token для ключа доступа.
. **Кошелек** запрашивает верифицируемые учетные данные из контрольной точки, представляющей токен доступа.
. {project_name} проверяет запрос и возвращает подписанные учетные данные.

=== Настройка выдачи учетных данных в Keycloak

В {project_name}проверяемые учетные данные управляются через *ClientScopes*, с каждым клиентским Scope представляющим один проверяемый тип учетных данных. Чтобы включить выдачу учетных данных, соответствующий ClientScope должен быть назначен клиенту OpenID Connect, в идеале *необязательно*.

Во время процесса авторизации OAuth2 можно запрашивать конкретные учётные данные, включив имя ClientScope в параметр `scope` запроса авторизации. После того, как пользователь успешно аутентифицировался, результирующий маркер доступа *MUST* включил запрошенную клиентScope в свою претензию `scope`. Чтобы убедиться, что опция ClientScope включена *Включать область символа*.

С помощью этого ключа доступа могут быть выданы проверенные учетные данные на контрольной точке.

==== Конфигурация управления ключами

Учетные данные подписываются с помощью ключа подписи реалма. Для SD-JWT VC выбранный ключ должен также предоставить цепочку сертификатов X.509, которая соответствует https://openid.net/specs/openid4vc-high-assurance-interoperability-profile-1_0-final.html#section-6.1.1[Требования к разрешению выпускающего HAIP]:

* Первый сертификат должен быть листовым сертификатом для ключа подписи учетных данных.
* Сертификат листа не должен быть самоподписан.
* Любые промежуточные сертификаты должны следовать сертификату листа в порядке цепочки.
* Якорь доверия не должен быть включен в заголовок JOSE `x5c`. Если настроенная цепочка заканчивается самоподписанным корневым сертификатом, {project_name} удаляет его при создании SD-JWT VC. Любой не подписанный само-подписанный якорь должен быть опущен из настроенной цепочки.

[IMPORTANT]
====
Не используйте сгенерированный ключ реалма для подписи SD-JWT VC. Созданный ключ либо не имеет сертификата, либо использует самоподписанный сертификат, так что выпуск SD-JWT VC не удался. Это ограничение не применяется к JWT VC.
====

Для OpenID4VC рекомендуется криптография эллиптических кривых с алгоритмом P-256 и `ES256`. Для настройки подходящего ключа подписи:

. Получить приватный ключ С-256 и соответствующий листовой сертификат, выданный центром сертификации. Включать промежуточные сертификаты, когда это применимо.
. Сохраните закрытый ключ и цепочку сертификатов в поддерживаемом хранилище ключей Java. Запись приватного ключа должна содержать сертификат листа первым, за которым следуют любые промежуточные сертификаты. Вы можете добавить самостоятельно подписанный корневой сертификат, но вы не должны добавлять не самоподписанный сертификат, который должен быть доверенным якорем.
. В консоли администратора перейдите в раздел *Настройки реалма* > *Ключи* > *Поставщики*.
. Добавьте поставщика *java-keystore* и настройте путь к ключевому магазину, тип, пароли и псевдоним ключей.
. Установил *Алгоритм* на `ES256` и *Использование ключа* на `sig`.
. Сделайте провайдер активным и назначьте ему достаточный приоритет, чтобы стать активным ключом области области `ES256`. В качестве альтернативы, явно выберите этот ключ в качестве *Подписывания ID ключа* при настройке области клиента регистрации.

[NOTE]
====
Ключевое хранилище может содержать самостоятельно подписанный корневой сертификат, чтобы {project_name} мог загрузить и проверить всю цепочку. {project_name} удаляет корневой сертификат из заголовка SD-JWT VC `x5c`. Он не удаляет не самоподписанный доверенный якорь, который поэтому должен быть опущен из настроенной цепочки.

Подробнее о местоположении ключевого хранилища и полях провайдера см. <<realm_keys,Configuring realm keys>>.
====

|Подписанные метаданные продолжительность жизни
|`oid4vci.signed_metadata.lifespan`
|`60` секунды
|Время жизни подписанных метаданных JWT возвращается, когда клиент запрашивает метаданные эмитента с помощью `Accept: application/jwt`.

|Подписанные метаданные подписи Алгоритм
|`oid4vci.signed_metadata.alg`
|`RS256`
|Алгоритм подписи асимметричных подписей, используемый для подписания метаданных JWT. Должно быть поддержано активными ключами реалма.

|Требовать шифрования
|`oid4vci.request.encryption.required`
|Выкл
|Если включено, все входящие запросы учетных данных должны быть зашифрованы как JWE. Открытые ключи шифрования издателя рекламируются в метаданных издателя.

|Требовать шифрование ответа
|`oid4vci.response.encryption.required`
|Выкл
|Если включено, все ответы учётных данных зашифрованы с использованием ключа шифрования кошелька.

|`oid4vci.request.zip.algorithms`
|Выкл
|Доступно только при необходимости шифрования запроса. Включение этой опции рекламирует поддержку сжатия DEFLATE в метаданных эмитента. Кошелек может сжимать JWE приложение, используя алгоритм `DEF`.

|Размер пакета
|`oid4vci.batch_credential_issuance.batch_size`
|`2`
|Максимальное количество учетных данных, которые могут быть выданы в одном пакетном запросе. Должно быть 2 или больше. Отключено, если не задано или неверно.

===== Понимание срока действия Учетных данных против Периода Обновления

{project_name} предоставляет отдельные настройки на основе времени для проверяемой валидации учетных данных:

* **Срок действия учетных данных** (`vc.expiry_in_seconds`) — Определяет срок действия токена обновления. По умолчанию: 1 год (31536000 секунд).
* **Интервал обновления учетных данных** (`vc.refresh_interval_in_seconds`) — Контролирует претензию `exp` (истечение срока действия) в реальном VC JWT, возвращенном в кошелёк. По умолчанию: 7 дней (604800 секунд), или срок действия учетных данных короче.

Это разделение дает возможность периодического цикла обновления:

. Кошелек получает VC с 7-дневным сроком
. Кошелек также получает токен обновления, действительный в течение 1 года
. Через 7 дней истекает срок действия VC (кошелек может проверить это локально)
. Кошелек использует токен обновления, чтобы получить новый токен доступа
. Кошелек запрашивает новый VC, который действителен в течение еще 7 дней
. Этот цикл продолжается до истечения срока действия токена обновления (через 1 год)
. По прошествии 1 года как токен обновления, так и запись в базе данных истекают, требуя повторной аутентификации

Этот дизайн предусматривает:

* **Повышенная безопасность** — регулярная регистрационная ротация снижает последствия хищения учетных данных
* **Защита конфиденциальности** — свежие учетные данные с обновленной меткой времени предотвращают долгосрочное соответствие
* **Удобство пользователя** — Автоматическое обновление без повторной аутентификации на срок до 1 года

[IMPORTANT]
====
Интервал обновления учетных данных не должен превышать срок действия учетных данных. {project_name} проверяет это ограничение при создании или обновлении рамок учетных данных. Если вы устанавливаете учетные данные время жизни короче 7 дней без явной настройки интервала обновления, интервал обновления автоматически регулируется для соответствия времени жизни учетных данных.
====

==== Присвоение авторских прав

Для выдачи клиенту определенного типа учетных данных, соответствующая область охвата клиента OID4VCI (которая определяет формат и требования учетных данных) должна быть назначена:

. В консоли администратора {project_name} перейдите к *Клиентам* и выберите клиента.
. Перейдите на вкладку *Области клиентов*.
. Нажмите *Добавить клиентскую границу*.
. Выберите область учетных данных, созданную ранее (например, `membership-credential`).
. Выберите **Необязательный** в качестве типа задания (рекомендуется для области регистрации).

Это гарантирует, что клиент может запрашивать и обрабатывать область во время потока авторизации, позволяя кошельку получать соответствующие проверенные учетные данные.

==== Создание клиента через REST API

Кроме того, вы можете создать и настроить клиентскую программу. Убедитесь, что атрибут `oid4vci.enabled` имеет значение `true`, а требуемая область доступа добавлена в `optionalClientScopes`.

. Создайте JSON файл (например, `my-wallet-client.json`) со следующим содержанием:
+
[source,json]
----
{
  "clientId": "my-wallet-client",
  "enabled": true,
  "protocol": "openid-connect",
  "publicClient": false,
  "serviceAccountsEnabled": true,
  "clientAuthenticatorType": "client-secret",
  "redirectUris": ["http://localhost:8080/*"],
  "directAccessGrantsEnabled": true,
  "defaultClientScopes": ["profile"],
  "optionalClientScopes": ["membership-credential"],
  "attributes": {
    "oid4vci.enabled": "true",
    "client.secret.creation.time": "1719785014",
    "client.introspection.response.allow.jwt.claim.enabled": "false",
    "login_theme": "keycloak",
    "post.logout.redirect.uris": "http://localhost:8080"
  }
}
----
- **clientId**: Уникальный идентификатор для клиента.
- **optionalClientScopes**: Ссылки области учетных данных (например, `membership-credential`) для VC запросов.
- **attributes.oid4vci.enabled**: Должно быть `true`, чтобы включить OID4VCI для этого клиента.
. Импортировать клиента, используя следующую команду `curl`:
+
[source,bash]
----
curl -k -X POST "https://localhost:8443/admin/realms/oid4vc-vci/clients" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d @my-wallet-client.json
----

=== Проверка конфигурации

Проверка установки, используя доступ к **конечной точке эмитента метаданных**:

. Откройте браузер или воспользуйтесь инструментом "curl", чтобы посетить:
+
[source,bash]
----
https://localhost:8443/.well-known/openid-credential-issuer/realms/oid4vc-vci
----
+
Успешный ответ возвращает объект JSON, содержащий детали, такие как:
- **Поддерживаемые требования**
- **Форматы аккредитивов**
- **метаданные эмитента**
