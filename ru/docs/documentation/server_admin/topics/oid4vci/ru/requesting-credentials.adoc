[[_oid4vci_credential_request]]
=== Запрос учетных данных

В этом разделе объясняется, как кошелек взаимодействует с {project_name} для запроса и получения подтвержденных учетных данных с помощью кода авторизации.

==== 1. Открытие метаданных эмитента

Кошельки часто начинаются с регистрационного предложения, например с QR-кода или ссылки. Предложение учетных данных содержит идентификатор эмитента (`credential_issuer`), который кошелек использует для определения конечной точки метаданных эмитента регистрационных данных.

Кошелек затем обнаруживает возможности издателя, вызвав конечную точку метаданных издателя. Эта конечная точка содержит подробную информацию о форматах учетных данных, поддерживаемых криптографическими методами привязки, и URL-адреса других необходимых конечных точек (таких, как авторизация, токен и конечные точки регистрации).

[source,bash]
----
curl -s -X GET "https://localhost:8443/.well-known/openid-credential-issuer/realms/{realm}"
----

Ответ JSON содержит объект `credential_configurations_supported`, в котором перечислены все доступные учетные данные и их конфигурации. Из этих метаданных кошелек определяет `credential_configuration_id` и идентифицирует `credential_endpoint` и `token_endpoint`.

[source,json]
----
{
  "credential_issuer": "https://localhost:8443/realms/{realm}",
  "credential_endpoint": "https://localhost:8443/realms/{realm}/protocol/oid4vc/credential",
  "batch_credential_endpoint": "https://localhost:8443/realms/{realm}/protocol/oid4vc/batch-credential",
  "nonce_endpoint": "https://localhost:8443/realms/{realm}/protocol/oid4vc/nonce",
  "authorization_servers": [
    "https://localhost:8443/realms/{realm}"
  ],
  "credential_configurations_supported": {
    "membership-credential": {
      "format": "jwt_vc_json",
      "scope": "membership-credential",
      "cryptographic_binding_methods_supported": [
        "jwk"
      ],
      "credential_signing_alg_values_supported": [
        "ES256",
        "RS256"
      ],
      "credential_definition": {
        "type": [
          "VerifiableCredential",
          "membership-credential"
        ]
      },
      "proof_types_supported": {
        "jwt": {
          "proof_signing_alg_values_supported": [
            "ES256"
          ]
        }
      },
      "credential_metadata": {
        "display": [
          {
            "name": "IdentityCredential",
            "locale": "en-US",
            "description": "Digitally verifiable identity credential",
            "background_color": "#12107c",
            "text_color": "#ffffff"
          }
        ],
        "claims": [
          {
            "path": [
              "credentialSubject",
              "given_name"
            ],
            "mandatory": true,
            "display": [
              {
                "name": "Given Name",
                "locale": "en-US"
              }
            ]
          },
          {

            ],
            "mandatory": true,

              {

}
----

==== 2. Запрос авторизации OIDC

Чтобы инициировать код авторизации, кошелек должен направлять пользователя на конечную точку авторизации {project_name}. Кошелек запрашивает доступ к конкретным учетным данным, используя либо стандартный OpenID Connect **Scopes**, либо более тонкий параметр **Подробности**.

===== Использование областей

Если учетные данные сопоставляются непосредственно с областями, то кошелек включает в себя область объявленных конфигураций учетных данных в параметре `scope` наряду с `openid`. Это имя области действия клиента и может отличаться от `credential_configuration_id`.

[source,http]
----
GET /realms/{realm}/protocol/openid-connect/auth
  ?response_type=code
  &client_id=my-wallet-client
  &redirect_uri=http://localhost:8080/callback
  &scope=openid membership-credential
  &code_challenge=xyz...
  &code_challenge_method=S256
----

===== Использование деталей авторизации (рекомендуется)

Кроме того, кошелек может использовать параметр `authorization_details` для запроса учётных данных. Это настоятельно рекомендуется для сложных конфигураций регистрационных данных. Параметр `authorization_details` представляет собой массив JSON, который задает точные запрошенные учетные данные.

[source,json]
----
[
  {
    "type": "openid_credential",
    "credential_configuration_id": "membership-credential"
  }
]
----

Чтобы передать это в URL, массив JSON должен быть кодирован в URL-коде:

[source,http]
----
GET /realms/{realm}/protocol/openid-connect/auth
  ?response_type=code
  &client_id=my-wallet-client
  &redirect_uri=http://localhost:8080/callback
  &scope=openid
  &authorization_details=%5B%7B%22type%22%3A%22openid_credential%22%2C%22credential_configuration_id%22%3A%22membership-credential%22%7D%5D
  &code_challenge=xyz...
  &code_challenge_method=S256
----

[TIP]
====
**Используйте Pushed Запросы авторизации (PAR)**: параметр `authorization_details` может быстро стать большим и превысить стандартные ограничения длины URL. Настоятельно рекомендуется использовать **конечную точку PAR** (`/realms/{realm}/protocol/openid-connect/ext/par/request`) для отправки загрузки авторизации через бэк-канал `POST` запрос. Конечная точка PR возвращает `request_uri`, который затем безопасно передается в конечную точку авторизации интерфейса.
====

==== 3. OIDC запрос на токен

После того, как пользователь успешно аутентифицирует и дает согласие, {project_name} перенаправляет пользователя на кошелек с кодом авторизации. Кошелек обменивает этот код для токена доступа в точке входа токена.

[source,bash]
----
curl -X POST "https://localhost:8443/realms/{realm}/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=authorization_code" \
  -d "code=AUTHORIZATION_CODE" \
  -d "client_id=my-wallet-client" \
  -d "client_secret=<YOUR_CLIENT_SECRET>" \
  -d "redirect_uri=http://localhost:8080/callback" \
  -d "code_verifier=PKCE_CODE_VERIFIER"
----

**Ответ на токен и идентификаторы учётных данных**

Если запрос авторизации был успешным, токен ответа включает в себя токен доступа и авторизованный `authorization_details`. Критически, {project_name} заполнит массив `credential_identifiers` внутри данных авторизации. Этот идентификатор должен быть извлечен, поскольку он необходим для последующего запроса учетных данных.

[source,json]
----
{
  "access_token": "eyJhbGci...",
  "token_type": "Bearer",
  "expires_in": 300,
  "scope": "openid membership-credential",
  "authorization_details": [
    {
      "type": "openid_credential",
      "credential_configuration_id": "membership-credential",
      "credential_identifiers": [
        "membership-credential"
      ]
    }
  ]
}
----

==== 4. Запрос учетных данных

С токена доступа и `credential_identifier` в руке, кошелек теперь может запрашивать учетные данные.

Во-первых, кошелек должен получить новый вызов nonce из конечной точки `/protocol/oid4vc/nonce`, и используйте его для создания криптографического доказательства владения (обычно это доказательство JWT подписано приватным ключом кошелька). Смотрите <_oid4vci_proofs,Proof Types and Key Binding in OID4VCI>>, чтобы узнать о поддерживаемых защитных типах и полезных нагрузках.

Затем кошелек отправляет запрос в точку завершения учётных данных (`/protocol/oid4vc/credential`):

[source,bash]
----
curl -X POST "https://localhost:8443/realms/{realm}/protocol/oid4vc/credential" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "credential_identifier": "membership-credential",
    "proofs": {
      "jwt": [
        "eyJhbGciOiJFUzI1NiIsInR5c...<base64url-encoded-jwt-proof>"
      ]
    }
  }'
----

[IMPORTANT]
====
Если токен доступа содержит `authorization_details`, `credential_identifier` в запросе учётных данных **должен совпадать** идентификатор, возвращаемый в Token Response. Если запрос не совпадает, он будет отклонен с ошибкой `unknown_credential_identifier`.
====

{project_name} проверяет токен доступа, проверяет подпись с предоставленным публичным ключом, проверяет требования пользователя (как обязательные требования), и возвращает подписанный валидатор полномочий.

**Пример ответа учётных данных (JWT VC)**

Для стандартного JWT VC (формат `jwt_vc_json`), в ответ включена строка подписанных учетных данных и новый nonce для любых последующих запросов:

[source,json]
----
{
  "format": "jwt_vc_json",
  "credential": "eyJhbGciOiJFUzI1NiIs...<base64url-encoded-jwt>",
  "c_nonce": "new_nonce_value_for_next_request",
  "c_nonce_expires_in": 86400
}
----

==== Запрос регистрационных данных SD-JWT

Запрос регистрационных данных SD-JWT (Селективное раскрытие JWT) соответствует тому же процессу, который описан выше, но цель `credential_configuration_id` должна соответствовать контурам клиента, настроенным на формат `dc+sd-jwt`.

Когда {project_name} обрабатывает запрос, он выдает учетные данные, где претензии скрываются за криптографическими солями (разглашения). Выдаваемый учетный ответ SD-JWT выглядит так:

[source,json]
----
{
  "format": "dc+sd-jwt",
  "credential": "eyJhbGciOiJFUzI1NiIsInR5cCI6ImRjK3NkLWp3dCJ9.eyJfaXNzIjoi...~<disclosure_1>~<disclosure_2>~",
  "c_nonce": "new_nonce_value_for_next_request",
  "c_nonce_expires_in": 86400
}
----

Строка `credential` — это объединенный формат, который объединяет JWT и base64url-encoded Disclosures, разделенные tildes (`~`). Привязка ключа держателя (из доказательств кошелька) безопасно встроена в претензию подтверждения `_sd_hash` внутри SD-JWT.
