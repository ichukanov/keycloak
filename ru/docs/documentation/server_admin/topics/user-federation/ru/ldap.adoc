==== Режим хранения

{project_name} импортирует пользователей из LDAP в локальную базу данных пользователей {project_name}. Эта копия базы данных пользователя синхронизируется по требованию или через периодическую фоновую задачу. Исключение для синхронизации паролей. {project_name} никогда не импортирует пароли. Проверка пароля всегда происходит на LDAP сервере.

Преимущество синхронизации заключается в том, что все функции {project_name} работают эффективно, потому что любые необходимые дополнительные данные для каждого пользователя хранятся локально. Недостаток заключается в том, что {project_name} каждый раз запрашивает конкретного пользователя в первый раз, {project_name} выполняет соответствующую вставку базы данных. Также, когда импортированные пользователи возвращаются в рамках операции поиска, Соответствующий поиск LDAP выполняется для каждого пользователя, чтобы проверить, существует ли пользователь в LDAP и выполнить базовую проверку.

Вы можете синхронизировать импорт с вашим LDAP сервером. Синхронизация импорта не требуется, когда LDAP карты всегда читают конкретные атрибуты из LDAP, а не базы данных.

Вы можете использовать LDAP с {project_name} без импорта пользователей в базу данных пользователя {project_name}. Сервер LDAP резервное копирование общей пользовательской модели, используемой {project_name}. Если LDAP не поддерживает данные, требуемые для {project_name} , эта функция не будет работать. Преимущество этого подхода заключается в том, что вы не используете ресурсы для импорта и синхронизации копий пользователей LDAP в базе данных пользователей {project_name}.

Переключатель *Импорт пользователей* на странице конфигурации LDAP управляет режимом хранения. Чтобы импортировать пользователей, переключите этот параметр на *ВКЛЮЧЕНИЕ*.

[NOTE]
====
Если вы отключите *Импорт пользователей*, вы не можете сохранить атрибуты профиля пользователя в базе данных {project_name}. Кроме того, вы не можете сохранять метаданные за исключением метаданных профиля пользователя, сопоставленных с LDAP. Эти метаданные могут включать в себя сопоставления ролей, группировки сопоставлений и другие метаданные, основанные на конфигурации LDAP карточек.

Когда вы пытаетесь изменить пользовательские данные, не относящиеся к LDAP, обновление пользователя невозможно. Например, вы не можете отключить пользователя с сопоставленными LDAP, если он не включил флаг `enabled` в атрибут LDAP.
====

[NOTE]
====
При работе с импортируемыми пользователями, {project_name} выполняет поиск LDAP при запросе пользователя, чтобы проверить пользователя и декорировать его так, чтобы настроенные карты работали правильно. Это означает, что необходимо проявлять особую осторожность при выполнении не отфильтрованных поисков пользователей, которые могут получить большое число пользователей в качестве поиска LDAP для каждого найденного импортируемого пользователя; возможно отрицательно влияет на производительность.

Операции, которые получают одного пользователя (например, при входе в систему), обычно кэшируются и не должны затрагиваться дополнительным LDAP поиском, который выполняется при первом получении пользователя.
====

==== Изменить режим

Пользователи и администраторы могут изменять метаданные пользователя, пользователи через консоль администраторов <<_account-service, Account Console>>. Конфигурация `Edit Mode` на странице конфигурации LDAP определяет привилегии на обновление LDAP.

ТОЛЬКО ЧТО:: Вы не можете изменить имя пользователя, email, имя, фамилию и другие атрибуты сопоставления. {project_name} показывает ошибку в любое время когда пользователь пытается обновить эти поля. Обновления паролей не поддерживаются.
ЗАПИСЬ:: Вы можете изменить имя пользователя, email, имя, фамилию и другие атрибуты сопоставления и пароли и автоматически синхронизировать их с LDAP магазином.
НЕЗНАЧНОЕ:: {project_name} хранит изменения в имени, email, имя, фамилия, и пароли в локальном хранилище {project_name} , поэтому администратор должен синхронизировать эти данные обратно с LDAP. В этом режиме развертывание {project_name} может обновить метаданные пользователя на серверах LDAP только для чтения. Эта опция применима также при импорте пользователей из LDAP в локальную базу данных пользователей {project_name}.

[NOTE]
====
При создании {project_name} поставщика LDAP {project_name} также создает набор начальных <_ldap_mappers,LDAP mappers>. {project_name} настраивает эти карты на основе комбинации *Поставщика*, *Изменить режим* и *Импортировать пользователей*. Например, когда режим редактирования - UNSYNCED, {project_name} настраивает карты для чтения конкретного атрибута пользователя из базы данных, а не с сервера LDAP. Однако, если вы позже измените режим редактирования, конфигурация карты не меняется, потому что невозможно определить, изменилась ли конфигурация в режиме UNSYNCED. Решить *Изменить режим* при создании LDAP провайдера. Эта заметка относится и к переключателю *Импорт пользователей*.
====

==== Другие параметры конфигурации

Отображаемое имя консоли:: Имя провайдера для отображения в консоли администратора.
Приоритет:: Приоритет провайдера при поиске пользователей или добавлении пользователя.
Регистрация синхронизации:: Включите этот переключатель в *ВКЛЮЧЕНИЕ*, если вы хотите, чтобы новые пользователи, созданные {project_name} , добавлены в LDAP.
Разрешить аутентификацию Kerberos:: Включить аутентификацию Kerberos/SPNEGO в области с пользовательскими данными, предоставленными LDAP. Дополнительную информацию см. <_kerberos,Kerberos section>>.
Удалить недействительных пользователей во время поиска:: Удалять пользователей из локальной базы данных, если они не доступны из пользовательского хранилища при выполнении поиска. Если это правда, пользователи больше не могут быть удалены из соответствующей памяти пользователей из локальной базы данных при попытке поиска пользователей. Если false, то пользователи, ранее импортированные из хранилища пользователя, будут храниться в локальной базе данных, как только чтение и отключено, даже если этот пользователь больше не доступен из пользовательского хранилища. Например, пользователь был удалён непосредственно из LDAP или «Пользователи DN» является недопустимым. Заметьте, что это поведение произойдет только тогда, когда пользователь еще не кэшируется.
Относительное создание DN:: Относительный DN от `Users DN`, где будут создаваться новые пользователи. Это позволяет создавать пользователей в подDN родительского `Users DN` при использовании области поиска `subtree`. Например, если `Users DN` имеет значение `ou=people,dc=myorg,dc=com` и `Relative User Creation DN` имеет значение `ou=engineering`, будут загружены из `Users DN` и всех подDNs, но новые пользователи будут храниться в `ou=engineering,ou=people,dc=myorg,dc=com`. Другими словами, {project_name} объединяет `Relative User Creation DN` с `Users DN` (запятая автоматически добавляется при объединении DNs) и использует этот DN для хранения пользователей

Аналогичное свойство также доступно в группе и роли картографа, позволяет добавлять группы и роли в подDN базового DN, который используется для поиска групп/ролей.

Другие опции:: Наведите курсор мыши на подсказки в консоли администратора, чтобы увидеть более подробную информацию об этих параметрах.

==== Подключение к LDAP через SSL

При настройке URL-адреса безопасного подключения к своему LDAP магазину (например,`ldaps://myhost.com:636`), {project_name} использует SSL для взаимодействия с LDAP сервером. Настройте хранилище с сервера {project_name} так, чтобы {project_name} мог доверять SSL-соединению с LDAP - см. https://www.keycloak.org/server/keycloak-truststore[Configuring a Truststore] {section}.

Свойство конфигурации `Use Truststore SPI` является устаревшим.  Обычно его следует оставить как "Всегда".

==== Подключение к нескольким серверам LDAP для отказа

Вы можете настроить несколько URL-адресов LDAP для отказов, введя их в виде списка *разделённого пробелом* в поле *URL соединения*. Например:

```
ldap://server1:389 ldap://server2:389
```

или для SSL-соединений:

```
ldaps://server1:636 ldaps://server2:636
```

При настройке нескольких URL-адресов, базовый Java JNDI провайдер пытается каждый URL слева направо. Если соединение с первым URL-адресом не удалось, он пытается следующий URL, и так далее до тех пор, пока соединение не завершится успешно. Это последовательный механизм отказа от работы, а не балансирование нагрузки — первый доступный сервер всегда используется.

Исправление происходит при создании соединения. Если сервер становится недоступным после установления соединения, текущая операция может завершиться неудачей, но последующие операции создают новые соединения и снова переходить к списку отказов.

[NOTE]
====
Все настроенные серверы LDAP должны быть *репликациями одной и той же директории* (например, контроллеры домена Active Directory в одном домене или реплицированные экземпляры OpenLDAP). Каждая запись LDAP должна иметь один и тот же уникальный идентификатор (например, `entryUID` или `objectGUID`) на всех серверах. Если серверы самостоятельно загружаются с одинаковыми данными, каждый сервер генерирует свои собственные уникальные идентификаторы, что вызовет синхронизацию и ошибки аутентификации при переходе на другой сервер.
====

[WARNING]
====
URL-адреса должны быть разделены *пробелами*. Не используйте запятые в качестве разделителей:

* `ldap://server1,ldap://server2` приводит к ошибке соединения.
* `ldap://server1, ldap://server2` (запятая после пробела) тихо сброшает первый URL из-за прерывания запятой, оставляя вас без отказов и предупреждения.
====

Настройки *Тайм-аута соединения* определяют, сколько {project_name} ждет TCP-соединение на каждый URL-адрес, прежде чем попробовать следующий. По умолчанию 5000 миллисекунд (5 секунд). Если сервер недоступен (например, из-за сетевого раздела или брандмауэра беззвучно бросают пакет), полный тайм-аут расходуется на каждый недоступный URL перед отказом продолжается. Отрегулируйте это значение в зависимости от вашего сетевого окружения на баланс между быстрым отказом и терпимостью при медленном соединении.

NOTE: Если сервер чисто остановлен (порт закрыт), отказ в соединении немедленно и отказ на следующий URL-адрес происходит без заметной задержки.

==== Синхронизация пользователей LDAP с {project_name}

Если вы установите опцию *Импорт пользователей*, LDAP провайдер импортирует пользователей LDAP в локальную базу данных {project_name}. Впервые пользователь регистрируется или возвращается как часть пользовательского запроса (напр. используя поле поиска в консоли администратора), провайдер LDAP импортирует пользователя LDAP в базу данных {project_name}. Во время аутентификации LDAP пароль проверяется.

По умолчанию {project_name} не поддерживает имя пользователя и атрибуты электронной почты с чувствительными к регистру значениями при хранении пользователей в локальной базе данных. Значение для этих атрибутов будет храниться в нижнем регистре в локальной базе данных.
Однако, если опция *Импорт пользователей* отключена, {project_name} не будет в нижнем регистре вводить имя пользователя и атрибуты электронной почты при запросе пользователей из LDAP.
Это поведение позволяет использовать учетные регистры имён и адреса электронной почты, когда *Импорт пользователей* отключен. Обратите внимание, что это поведение применяется только к атрибутам имени пользователя и электронной почты. Другие атрибуты остаются чувствительными к регистру.

При использовании LDAP с {project_name}рекомендуется не использовать учетные имена пользователей и адреса электронной почты с учетом регистра так как некоторые функции в {project_name} могут неправильно работать с учетными регистрами пользователей и электронными письмами.

Если вы хотите синхронизировать всех пользователей LDAP с базой данных {project_name} , настройте и включите *Синхронизацию* на странице конфигурации провайдера LDAP.

Существует два типа синхронизации:

Периодическая полная синхронизация:: Этот тип синхронизирует всех пользователей LDAP с базой данных {project_name}. Пользователи LDAP уже в {project_name}, но разные в LDAP, напрямую обновляются в базе данных {project_name}.
Периодическая синхронизация измененных пользователей:: При синхронизации, {project_name} создает или обновляет пользователей, созданных или обновляемых только после последней синхронизации.

Лучший способ синхронизировать это нажать *Синхронизировать всех пользователей* при первом создании LDAP провайдера, затем настроить периодическую синхронизацию измененных пользователей.

[[_ldap_mappers]]
==== LDAP картографы

LDAP карты являются «слушателями», инициированными LDAP провайдером. Они представляют собой еще один пункт расширения для интеграции LDAP. Маркеры LDAP срабатывают, когда:

* Пользователи войдут с помощью LDAP.
* Сначала зарегистрировались пользователи.
* Консоль Администратора запрашивает пользователя.

При создании поставщика LDAP федерации {project_name} автоматически предоставляет набор `mappers` для этого поставщика. Этот набор изменяется пользователями, которые также могут разрабатывать карты или обновить/удалять существующие.

Карта атрибутов пользователя:: Маппер определяет, какой атрибут LDAP сопоставляет атрибут пользователя {project_name}. Например, вы можете настроить атрибут `mail` LDAP на атрибут `email` в базе данных {project_name}. Для этой реализации карты всегда существует одноразовое сопоставление.
Полное имя Mapper:: Этот картограф определяет полное имя пользователя. {project_name} сохраняет имя в LDAP атрибуте (обычно `cn`) и сопоставляет его с атрибутами `firstName` и `lastname` в базе данных {project_name}. `cn` должен содержать полное имя пользователя для развертывания LDAP.

[NOTE]
====
Когда вы регистрируете новых пользователей в {project_name} и `Sync Registrations` ВКЛЮЧЕНО для LDAP провайдера, fullName mapper разрешает падать обратно к имени пользователя. Эта резервная копия полезна при использовании Microsoft Active Directory (MSAD). Общая настройка MSAD заключается в настройке атрибута `cn` LDAP как fullName и одновременно, используйте атрибут `cn` LDAP в качестве `RDN LDAP Attribute` в конфигурации провайдера LDAP. С этой настройкой {project_name} возвращается к имени пользователя. Например, если вы создаете {project_name} пользователя "john123" и оставьте первое имя и фамилию пустым, тогда полноимя_mapper сохраняет "john123" в качестве значения `cn` в LDAP. Когда вы вводите "John Doe" для имени и фамилии позже, fullname mapper обновляет LDAP «cn» до значения «John Doe», поскольку возвращается к имени пользователя.
====

Карта атрибутов с жестким кодом:: Этот картограф добавляет хардкодированное значение атрибута каждому пользователю {project_name} , связанному с LDAP. Этот картограф также может принудительно использовать значения свойств пользователя `enabled` или `emailVerified`.
Маппер роли:: Этот картограф настраивает сопоставления ролей из LDAP в сопоставления ролей {project_name}. Единый координатор ролей может сопоставлять роли LDAP (обычно группы из конкретной ветки дерева LDAP) на роли, соответствующие ролям определенного клиента или ролям клиента. Вы можете настроить больше карт ролей для одного LDAP провайдера. Например, вы можете указать эти сопоставления ролей групп в рамках `ou=main,dc=example,dc=org` с сопоставлением ролей, и сопоставления ролей групп в разделе `ou=finance,dc=example,dc=org` сопоставляются с соотвествием роли клиента `finance`.
Карточка с хардкодированной ролью:: Этот картограф предоставляет определенную роль {project_name} каждому пользователю {project_name} от поставщика LDAP.
Маппер групп:: Карта отображает группы LDAP из ветки дерева LDAP в группы внутри {project_name}. Этот картограф также распространяет сопоставления групп пользователей из LDAP в сопоставления групп пользователей в {project_name}.

[[_msad_mapper]]
Карта учетных записей MSAD:: Этот маппер специфичен для Microsoft Active Directory (MSAD). Он может интегрировать состояние учетной записи MSAD в состояние учетной записи {project_name} , например, включенную учетную запись или просроченный пароль. Этот mapper использует `userAccountControl` и `pwdLastSet` LDAP атрибуты, специфичные для MSAD и не являются LDAP стандартом. Например, если значение `pwdLastSet` равно `0`, то пользователь {project_name} должен обновить свой пароль. Результатом является добавленное пользователем действие UPDATE_PASSWORD. Если значение `userAccountControl` равно `514` (отключена учётная запись), пользователь {project_name} отключен.
Карта сертификатов:: Этот картограф отображает сертификаты X.509. {project_name} использует его совместно с аутентификацией X.509 и `Full certificate in PEM format` в качестве источника идентификации. Этот mapper ведет себя аналогично `User Attribute Mapper`, но {project_name} может фильтровать для атрибута LDAP, хранящего сертификат формата PEM или DER. Включите `Always Read Value From LDAP` с этим картографом.

Карта атрибутов пользователя, сопоставляющая основные атрибуты пользователя {project_name} , такие как имя пользователя, имя, фамилия и адрес электронной почты, с соответствующими атрибутами LDAP. Вы можете расширить их и предоставить свои дополнительные сопоставления атрибутов. Консоль администратора предоставляет подсказки для помощи в настройке соответствующих карточек.

[[_ldap_password_hashing]]
==== Хэширование пароля

Когда {project_name} обновляет пароль, {project_name} отправляет пароль в текстовом формате. Это действие отличается от обновления пароля в встроенной базе данных {project_name} , где {project_name} хеширует и соляет пароль перед отправкой его в базу данных. Для LDAP, {project_name} полагается на LDAP сервер хэш и соленый пароль.

По умолчанию, LDAP серверы такие как MSAD, RHDS, или FreeIPA хэш и пароль salt. Другие LDAP сервера, такие как OpenLDAP, хранят пароли в обычном тексте, если вы не используете пароль _LDAPv3, модифицируйте расширенный Operation_ как описано в https://datatracker.ietf.org/doc/html/rfc5280#section-4.2.1.3[RFC 3062]. Включить LDAPv3 Password Modify Extended Operation на странице конфигурации LDAP. Смотрите документацию вашего сервера LDAP для получения более подробной информации. https://directory.apache.org/apacheds/advanced-ug/4.1.1.4-ss-password-hash.html[Настройка хэша и соленых паролей автоматически], включив перехват пароля.

WARNING: Всегда проверяйте, что пользовательские пароли правильно хэшированы и не хранятся в виде простого текста, проверяя измененную запись каталога
используя атрибут `ldapsearch` и base64 декодируйте значение атрибута `userPassword`.

[[_ldap_password_policy]]
==== Включение изменения пароля после сброса

Вы можете заставить пользователей изменить свой пароль после того, как администратор сбрасывает свой пароль. Эта функция полезна для
соображений безопасности, так как она долгое время не позволяет пользователям использовать временный пароль, установленный администратором.

Для этого включить параметр `Enable LDAP password policy` для того, чтобы требуемое действие `UPDATE_PASSWORD` было добавлено к
пользователю всякий раз, когда сервер LDAP указывает, что пользователь должен обновить свой пароль.

{project_name} обычно настроен на подключение к LDAP серверу с использованием учетной записи администратора, даже когда пользователи
обновляют свой пароль. В этом случае некоторые LDAP серверы, если не настроены должным образом, будет всегда принудительно сменить пароль
после изменения пароля пользователем, потому что LDAP сервер увидит, что пароль был изменен администратором
, а не самим пользователем.

When enabling this feature, make sure your LDAP server is configured to not force users to change their password a
second time after the user changes their password. Если это не происходит, то может возникнуть цикл смены пароля, когда пользователь
вынужден менять свой пароль каждый раз при входе в систему.

[NOTE]
====
Эта возможность основана на https://datatracker.ietf.org/doc/html/draft-behera-ldap-password-policy-11[Политика паролей для LDAP (IETF draft-behera-ldap-password-policy)].
Для Microsoft Active Directory, используйте <_msad_mapper,MSAD Account Mapper>>.
====

[[_ldap_connection_pool]]
==== Настройка пула подключений

Для большей эффективности при управлении LDAP соединениями и для улучшения производительности при обработке нескольких соединений, вы можете
включить объединение соединений. By doing that, when a connection is closed, it will be returned to the pool for future use therefore
reducing the cost of creating new connections all the time.

Конфигурация пула подключений LDAP настроена с помощью следующих системных свойств:

[cols="2*", options="header"]
|===
|Наименование
|Описание

|`com.sun.jndi.ldap.connect.pool.authentication` |Список типов соединений, разделенных пробелами, которые могут быть пущены. Допустимые типы - "none", "simple" и "DIGEST-MD5"

|`com.sun.jndi.ldap.connect.pool.initsize` |Строковое представление целого, которое представляет количество соединений на идентификатор соединения, создаваемое при первоначальном создании соединения для идентификации

|`com.sun.jndi.ldap.connect.pool.maxsize` |Строковое представление целого, которое представляет максимальное количество соединений на идентификатор соединения, которое может поддерживаться параллельно. Слишком низкие значения могут привести к разногласиям в получении LDAP соединений. См. также `com.sun.jndi.ldap.connect.timeout`.

|`com.sun.jndi.ldap.connect.pool.prefsize` |Строковое представление целого, которое представляет предпочтительное число соединений на идентификатор соединения, которое должно поддерживаться параллельно

|`com.sun.jndi.ldap.connect.pool.timeout` |Строковое представление числа, представляющее количество миллисекунд, которое простаивает в пуле, не закрывая и удаляя из пула

|`com.sun.jndi.ldap.connect.pool.protocol` |Список типов соединений, разделенных пробелами, которые могут быть пущены. Допустимые типы - "простые" и "ssl"

|`com.sun.jndi.ldap.connect.pool.debug` |Строка, которая показывает уровень отладочного вывода для производства. Допустимыми являются "fine" (создание и удаление трассировки соединения) и "all" (вся отладочная информация)

|`com.sun.jndi.ldap.connect.timeout` |Строковое представление целого числа, которое показывает сколько времени в миллисекундах, получающих соединение. Это также применимо к времени ожидания из-за конверсии пула подключений. Эффективно по умолчанию 5000.
|===

По умолчанию для протоколов `plain` и `ssl` включено пул подключений.

Для получения более подробной информации см. link:https://docs.oracle.com/javase/jndi/tutorial/ldap/connect/config.html[Документацию о пуле подключения Java LDAP Configuration].

Чтобы установить любые из этих свойств, вы можете установить переменную окружения `JAVA_OPTS_APPEND`:

[source,bash]
----
export JAVA_OPTS_APPEND=-Dcom.sun.jndi.ldap.connect.pool.initsize=10 -Dcom.sun.jndi.ldap.connect.pool.maxsize=50
----

[[_ldap_troubleshooting]]
==== Устранение проблем

Полезно повысить уровень записи журнала до TRACE для категории `org.keycloak.storage.ldap`. With this setting, many logging messages are sent
to the server log in the `TRACE` level, including the logging for all queries to the LDAP server and the parameters, which were
used to send the queries. При создании LDAP вопроса на форуме пользователей или JIRA, попробуйте прикрепить журнал сервера к
включив TRACE. If it is too big, the good alternative is to include just the snippet from server log with the messages, which were
added to the log during the operation, which causes the issues to you.

- Когда вы создаете LDAP провайдера, в логине сервера появляется сообщение, начинающееся с:

```
Creating new LDAP Store for the LDAP storage provider: ...
```

Он отображает конфигурацию вашего LDAP провайдера. Прежде чем задавать вопросы или сообщать об ошибках, было бы неплохо включить это сообщение
для отображения конфигурации LDAP. В конце концов, вы можете заменить некоторые изменения конфигурации, которые вы не хотите включать, с некоторыми значениями плейсхолдеров
. Одним из примеров является `bindDn=some-placeholder` . For `connectionUrl`, feel free to replace it as well, but it is generally
useful to include at least the protocol, which was used (`ldap` vs `ldaps`)`. Точно так же может быть полезно включить подробную информацию о конфигурации
ваших LDAP мэпперов, которые отображаются с таким сообщением на уровне DEBUG:

```
Mapper for provider: XXX, Mapper name: YYY, Provider: ZZZ ...
```

Обратите внимание, что эти сообщения отображаются только с включенным протоколом DEBUG.

- Для отслеживания проблем пула производительности или подключения, попробуйте установить значение объекта `com.sun.jndi.ldap.connect.pool.debug` в `all`. Это изменение добавляет много дополнительных сообщений в журнал сервера с включением журнала для LDAP соединения
пул. В результате вы можете отслеживать проблемы, связанные с пулом соединений или производительностью. Подробнее см. <<_ldap_connection_pool,Настройка пула соединений>.

NOTE: После изменения конфигурации пула подключений, возможно, потребуется перезапустить сервер {project_name} для принудительной повторной инициализации
подключения провайдера LDAP.

Если больше нет сообщений для пула подключений даже после перезапуска сервера, может показать, что пул соединения не работает
с вашим LDAP сервером.

- For the case of reporting LDAP issue, you may consider to attach some part of your LDAP tree with the target data, which causes issues
in your environment. Например, если логин некоторого пользователя занимает много времени, вы можете прикрепить запись LDAP, показывающую количество атрибутов `member`
различных "group". В этом случае может быть полезно добавить, если эти групповые записи сопоставляются с некоторыми группами LDAP mapper (или Роли LDAP Mapper)
в {project_name} и так далее.
