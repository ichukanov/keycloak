= Привязка токена OIDC и SAML

[role="_abstract"]
Приложения, получающие идентификационные токены доступа, токены доступа или SAML, могут требовать различные роли и метаданные пользователя.

Вы можете использовать {project_name} в:

* Роли Хардкода, утверждения и пользовательские атрибуты.
* Потяните метаданные пользователя в токен или утверждение.
* Переименовать роли.

Вы выполняете эти действия во вкладке *Mappers* в консоли администратора.

image:images/mappers-oidc.png[]

У новых клиентов нет встроенных картографов, но они могут наследовать некоторые картографы из границ клиента. Смотрите <<_client_scopes, client scopes section>> для более подробной информации.

Protocol mappers map items (such as an email address, for example) to
a specific claim in the identity and access token. Функция картографа должна быть не понятной из его имени. Вы добавляете предварительно настроенные карты нажав *Добавить Builtin*.

У каждого картографа есть набор общих настроек. В зависимости от типа карты доступны дополнительные настройки. Нажмите *Редактировать* рядом с картографом, чтобы получить доступ к экрану конфигурации, чтобы настроить эти настройки.

image:images/mapper-config.png[]

Подробнее о каждой опции можно просмотреть, наведя курсор мыши над ее подсказкой.

Вы можете использовать большинство карт OIDC для управления местоположением владений. Вы решили включить или исключить претензию из _id_ и _access_ токенов, изменив *Добавить в идентификационный токен* и *Добавить в доступ к ключам*.

[[_protocol-mappers_priority]]
== Приоритетный порядок

Реализации Mapper имеют _приоритет order_. _Приоритет заказа_ не является свойством конфигурации карты карта. Это свойство конкретной реализации картографа.

Карты отсортированы по порядку в списке карт. Изменения в токене или утверждении применяются в таком порядке с наименьшим применением. Поэтому реализации, зависящие от других реализаций, обрабатываются в нужном порядке.

Например, для вычисления ролей, которые будут включены в токен:

. Разрешать аудитории на основе этих ролей.
. Обработать JavaScript скрипт, который использует роли и аудитории, уже доступные в токене.

[[_protocol-mappers_oidc-user-session-note-mappers]]
== Сессии OIDC пользователей

Детали сеанса пользователя определяются с помощью карты и автоматически включаются при использовании или включении функции на клиенте. Нажмите *Добавить встроенный*, чтобы включить информацию о сеансе.

Прошедшие сеансы пользователя содержат следующие подробности:

* *IMPERSONATOR_ID*: ID пользователя имперса.
* *IMPERSONATOR_USERNAME*: Имя пользователя имперсонирующего пользователя.

Служебные сессии предоставляют следующую информацию:

* *clientId*: ID клиента счета сервиса.
* *client_id*: ID клиента учетной записи сервиса.
* *clientAddres*: удаленный IP-адрес хоста устройства авторизации учетной записи сервиса.
* *clientHost*: Имя удаленного хоста устройства авторизации учетной записи службы.

== Script mapper

Используйте *Script Mapper*, чтобы сопоставить притязания к фишкам с помощью кода JavaScript, определенного пользователем. Подробнее об установке скриптов на сервер см. ссылку:{developerguide_jsproviders_link}[{developerguide_jsproviders_name}].

При развертывании сценариев вы сможете выбрать развернутые скрипты из списка доступных мэпперов.

== Сопряженный идентификатор темы карты

Тема _sub_ сопоставляется по умолчанию *Тема (Subject (sub)* сопоставление протокола в области клиента по умолчанию *основной*.

Чтобы использовать идентификатор темы в паре с использованием сопоставления протоколов, например *идентификатор предмета по пару*, можно удалить карту протокола *Subject (sub)* из *основной* области действия клиента.
Однако это не является строго обязательным, поскольку сопоставление протокола *Тема (под)* выполняется до сопоставления темы *Идентификатор предмета* пары, и поэтому значение пары переопределит значение, добавленное
Предметным картографом. Это связано с <_protocol-mappers_priority, priority>> субъекта mapper. Таким образом, единственным преимуществом удаления встроенной *Subject (sub)* mapper может быть
сохранить немного производительности, избегая использования протокола mapper, , которые не могут иметь никакого эффекта.

[[_using_lightweight_access_token]]
== Использование легкого токена доступа

Токен доступа в {project_name} содержит конфиденциальную информацию, включая личную идентификационную информацию (PII).
Поэтому, если сервер ресурсов не хочет разглашать такую информацию третьим лицам, таким как клиенты, {project_name} поддерживает лёгкие токены доступа, которые удаляют PII из токенов доступа.
Далее, когда сервер ресурсов приобретает PII, удалённый из токена доступа, он может получить PII, посылая токен доступа на конечную точку ввода токена {project_name}.

Информация, которая не может быть удалена из легкого токена доступа:: Протоколные карты могут контролировать, какую информацию поместить на токен доступа, а легкий токен доступа использует карты протокола. Поэтому следующая информация не может быть удалена из легкого доступа. +
`exp`, `iat`, `jti`, `iss`, `typ`, `azp`, `sid`, `scope`, `cnf`
Использование легкого токена доступа в {project_name}:: Применив исполнителя `use-lightweight-access-token` <<_client_policies, клиент политики>> к клиенту, клиент может получить легкий токен доступа вместо токена доступа. Легкий токен доступа содержит претензию, контролируемую картографом протокола, где включена опция `Добавить в легкий токен доступа`(по умолчанию OFF). Также, включив опцию 'Добавить в token introspection' карты протокола, клиент может получить претензию, посылая токен доступа на конечную точку ввода токена токена {project_name}.
Преобразование легкого токена доступа в обычный токен доступа:: Для получения токена полного доступа по легкому токену доступа, используйте ссылку:{securing_apps_token_exchange_link}[Обмен токено]. Клиент, имеющий легкий токен доступа, может обменять его на обычный токен доступа, содержащий все стандартные требования. Это полезно, когда вам нужно позвонить по API, которые требуют токены полного доступа или когда вам нужен доступ к претензиям, не входящим в легкий токен.
+
IMPORTANT: Для обмена токенов для работы с легких токенами доступа, вы должны настроить аудитории на клиенте, который выдает легкий токен с включённым параметром «Добавить в легкий токен». Обмен токенами требует, чтобы целевой клиент находился в «aud» (аудитория) требовании легкого токена.
Конечная точка зрения:: В некоторых случаях было бы полезно запустить конечную точку ввода токена с HTTP-заголовком `Accept: application/jwt` вместо `Accept: application/json`, , которые могут быть полезны особенно для легких токенов доступа. Смотрите подробности *Конечной точки Интроспекции токенов* по ссылке:{securing_apps_link}[защита приложений].
Ограничение конечной точки пользователя:: Конечная точка UserInfo отвергает легкие токены доступа по умолчанию, а не для прямого использования с UserInfo. Если вам нужна информация о пользователе из легкого токена доступа, используйте одну из этих альтернатив:
* Вызов конечной точки ввода токена вместо UserInfo - конечная точка инфорспекции предназначена для легких токенов и возвращает полные претензии
* обменивать легкий токен доступа для полного доступа по ссылке:{securing_apps_token_exchange_link}[Token Exchange] (см. *Преобразование легкого токена доступа в обычный токен* выше), затем позвоните UserInfo с полным токеном
+
Если вы должны использовать легкие токены с endpoint UserInfo во время миграции, вы можете включить опцию обратной совместимости в *OpenID Connect Compatibility Modes*, включив *Разрешить UserInfo с легким токеном доступа* на клиенте, который выпускает легкие токены.
