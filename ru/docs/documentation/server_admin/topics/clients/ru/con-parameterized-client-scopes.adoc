[[_parameterized_client_scopes]]
== Параметры границ клиента

[IMPORTANT]
====
Эта функция в настоящее время экспериментальная. Не используйте его в производстве. Спокойная совместимость не гарантирована, а будущие обновления могут повлечь за собой неприятные изменения.

Чтобы включить, запустите сервер с помощью `--features=parameterized-scopes`.
====

{project_name} поддерживает параметры границ клиента, которые позволяют клиентам передавать значение параметра вместе с именем области в запросе авторизации OAuth 2.0. В параметризированной области используется формат `scopeName:parameterValue`, где двоеточие (`:`) отделяет имя области от его параметра.

Например, можно запросить область действия клиента под названием `contract` как `contract:42`, где `42` это значение параметра. Это позволяет создавать токены доступа с точной информацией о ресурсах, не определяя отдельную область действия клиента для каждого из возможных значений.

=== Создание параметризованной области клиента

Чтобы создать параметризированную область клиента, выполните следующие действия:

. Щелкните *Область клиента* в меню.
. Нажмите *Создать клиентскую границу*.
. Введите *Название* для области (например, `project`).
. Включить переключатель *Параметризованные области видимости*.
. Выберите *Тип параметров* из доступных параметров (например, `String`).
. Если вы выбрали тип параметра `Custom`, введите шаблон регулярного выражения, который должен соответствовать значению параметра.
. Установите *Type* на *Нет* или *Необязательно*. При включенном переключении *Параметризованной области область*, опция *По умолчанию* недоступна.
. Нажмите *Сохранить*.

[[_parameterized_scopes_parameter_types]]
=== Типы параметров

При создании параметризованной области необходимо выбрать тип параметра, который определяет, как значение параметра проверяется в момент запроса. Доступны следующие встроенные типы:

[cols="1,3,1", options="header"]
|===
|Тип
|Описание
|Повторяемый по умолчанию

|`строка`
|Принимает любое строковое значение. По этому параметру проверка не проводится.
|Да

|'целое число'
|Принимает только целые числа. Значение параметра должно быть разрозненным как целое число.
|Да

|`boolean`
|Принимает только «true» или «false» (без учета регистра).
|Нет

|`username`
|Проверяет, что значение параметра является именем пользователя существующего пользователя в реалме. Когда Realm позволяет войти в систему с email, параметр также может быть электронной почтой. Кроме того, пользователь не может использовать этот охват данного типа.
|Да

|`делегирование`
|Расширяет тип `username` с дополнительной проверкой имя. Параметр должен быть именем пользователя (или адреса электронной почты, когда Realm позволяет войти с электронной почты) существующего активированного пользователя. Пользователь не может быть целевым, а текущий пользователь должен иметь права имперсации для целевого пользователя.
|Нет

|`custom`
|Проверяет значение параметра относительно шаблона регулярных выражений, определенного администратором. При выборе этого типа, вы должны предоставить корректный регулярный рост.
|Да
|===

[[_parameterized_scopes_use_case]]
=== Вариант использования: доступ к ресурсам

Рассмотрим приложение *ProjectHub*, управляющее проектами. Без параметризированных границ вам потребуется создать отдельную клиентскую область для каждого проекта, к которому клиент может получить доступ (например, `project-backend-api`, `project-mobile-app`). Такой подход не масштабируется и не создаются новые проекты.

С параметризированными областями вы определяете одну область проекта с типом параметра `string`. *ProjectHub* может запросить доступ к конкретному проекту в момент авторизации:

[source,bash,subs=+attributes]
----
scope=openid project:backend-api
----

{project_name} проверяет значение параметра по отношению к заданному типу параметров. Если валидация не удается, значение области действия отключается от запроса. Когда область <<_parameterized_scopes_repeatable, повторить>>, клиент может запросить несколько значений для одной и той же области в одном запросе:

[source,bash,subs=+attributes]
----
scope=openid project:backend-api project:mobile-app
----

Каждое значение проверяется самостоятельно. В результирующем токене доступа содержатся подтвержденные параметры области действия в его претензии `scope`, разрешение сервера ресурсов *ProjectService* для принудительного доступа на основе значения параметра.

Чтобы ограничить параметр известными идентификаторами проекта, используйте тип параметра `custom` с регулярным выражением, таким как `[a-z0-9\-]+`.

=== Экран согласия

Когда клиент включил *Обязательное Соглашение* и использует параметризованные области экрана, экран согласия отображает каждое значение области действия отдельно. Текст согласия соответствует формату `scopeName: parameterValue`.

Например, используя <<_parameterized_scopes_use_case, resource-specific access>> используйте вышеприведенный случай `scope=openid project:mobile-app project:backend-api` будет отображаться на экране согласия:

[[_parameterized_scopes_repeatable]]
=== Повторяемые области

По умолчанию клиент может запросить одну и ту же область с несколькими разными значениями параметров в одном запросе авторизации. Например, `scope=openid project:backend-api project:mobile-app` включает в себя два значения области области `project`.

Однако некоторые типы рамок не позволяют это сделать. Например, область `boolean` с элементами `scope:true` и `scope:false` в том же запросе противоречива. Аналогичным образом, область `delegation`, которая определяет одного целевого пользователя, не должна отображаться с несколькими значениями.

Каждый тип параметра определяет по умолчанию для того, является ли область повторной (см. таблицу <_parameterized_scopes_parameter_types, types>>). Вы можете переопределить это значение по умолчанию для отдельных областей:

. Откройте параметр клиентской области в консоли администратора.
. Переключатель *Повторяемый* для включения или отключения нескольких значений параметров.
. Нажмите *Сохранить*.

Когда клиент запрашивает несколько значений параметров для неповторяемой области, {project_name} отклоняет запрос с ошибкой `invalid_scope`.

=== Ограничения

Параметризированные рамки клиентов имеют следующие ограничения:

* Параметр области может быть только *необязательной* областью клиента. Его нельзя назначить в качестве клиентской границы по умолчанию для клиента.
* Параметрализованная область не может быть назначена как область по умолчанию. Он может быть назначен в качестве необязательной области применения.
* При назначении одного и того же клиента нескольких параметризованных областей с перекрывающимися именами префиксов, наиболее точная (самая длинная область префикса) область совпадает. Например, если у клиента есть и `read`, и `read:account` как параметризованные области, запрос `read:account:victim` связывает `read:account` с параметром `victim`, а не `read` с параметром `account:victim`.
