[[_client_scopes]]
= Области деятельности клиента

[role="_abstract"]
Используйте {project_name} для определения общей конфигурации клиента в сущности, которая называется _client scope_. _client scope_ настраивает <<_protocol-mappers, протокол mappers>> и <_role_scope_mappings, mappings>> для нескольких клиентов.

Клиентские рамки также поддерживают параметр OAuth 2 *scope*. Клиентские приложения используют этот параметр для запроса претензий или ролей в токене доступа, в зависимости от требования приложения.

[[_client_scopes_protocol]]
== Protocol

При создании клиентской области выберите *Протокол*. Клиенты, связанные с той же областью, должны иметь тот же протокол.

В каждом реалме есть набор встроенных в меню клиентских рамок.

* SAML протокол: *role_list*. Этот диапазон содержит один протокол сопоставления списка ролей в утверждении SAML.
* Протокол OpenID Connect: Доступно несколько областей клиента:
** *роли*
+
Эта область не определена в спецификации OpenID Connect и не добавляется автоматически в претензию *scope* в токене доступа. В этом диапазоне есть карты, которые используются для добавления ролей пользователя к токену доступа и
добавляет аудитории для клиентов, имеющих хотя бы одну роль клиента. Более подробно эти карты описаны в разделе <_oidc_token_role_mappings, разделе сопоставления фишек ролей >> и <<_audience_resolve, раздел Audienc>>.
** *веб-происхождения*
+
Эта область также не определена в спецификации OpenID Connect и не добавлена в *scope* с указанием ключа доступа. Эта область используется для добавления разрешенного веб-происхождения в токен доступа *allowed-origins* претензии.
** *microprofile-jwt*
+
Эта область обработки обрабатывает претензии, определенные в https://github.com/eclipse/microprofile/wiki/JWT_Auth[MicroProfile/JWT Auth Specification]. Этот диапазон определяет отображение пользовательских свойств для *верхних* претензий и карты ролей области для претензий *групп*. Эти карты могут быть изменены таким образом, чтобы можно было использовать различные свойства для создания конкретных претензий MicroProfile/JWT.
** *offline_access*
+
Этот диапазон используется в тех случаях, когда клиентам необходимо получить оффлайн токены. Подробнее о токенах в автономном режиме можно найти в <_offline-access, разделе Offline Access >> и в https://openid.net/specs/openid-connect-core-1_0.html#OfflineAccess[Описание подключения OpenID].
** *профиль*
** *email*
** *адрес*
** *телефон*

Клиентские области *профиль*, *email*, *адрес* и *телефон* определяются в описании https://openid.net/specs/openid-connect-core-1_0.html#ScopeClaims[OpenID Connect спецификации]. Эти рамки не имеют каких-либо сопоставлений рамок ролей, но они имеют определенные карты протоколов. Эти карты соответствуют требованиям, определенным в спецификации OpenID Connect.

Например, когда вы открываете область *телефон* клиента и открываете вкладку *Mappers*, вы увидите карты протоколов, которые соответствуют претензиям, определенным в спецификации области *телефон*.

image:images/client-scopes-phone.png[]

Когда *телефон* область действия клиента связана с клиентом, клиент автоматически наследует все схемы протокола, определенные в *телефон* области действия клиента. Маркеры доступа, выпущенные для этого клиента, содержат информацию о номере телефона о пользователе, предполагая, что у пользователя есть определенный номер телефона.

Встроенные клиентские рамки содержат контроллеры протоколов, как это определено в спецификации. Вы можете редактировать рамки клиента и создавать, обновлять или удалять любые схемы протоколов, или сопоставления ролей.

== Настройки согласия

Рамки действия клиента содержат параметры, связанные с экраном согласия. Эти опции полезны, если связанный клиент включен, если *Требуется согласие*.

Показывать на экране согласия:: Если включена *Отображать на согласительном экране*, и область добавляется к клиенту, который требует согласия, текст, указанный в *Текст экрана согласия*, будет отображаться на экране согласия. Этот текст показывается, когда пользователь аутентифицирован и прежде чем пользователь будет перенаправлен из {project_name} к клиенту. Если опция *Отображать на разрешенном экране* отключена, область действия клиента не будет отображаться на экране согласия.
Текст экрана согласия:: Текст, отображаемый на экране согласия, когда эта область действия клиента добавляется к клиенту, когда требуется согласие по умолчанию на имя области действия клиента. Значение этого текста может быть изменено путем указания переменной подстановки с помощью *${var-name}* строк. Персонализированное значение настроено в файлах свойств вашей темы. См. ссылку:{developerguide_link}[{developerguide_name}] для получения дополнительной информации о настройках.

== Включить в область действия токена

*Включено в область видимости токенов*. Если включено, имя этой области действия клиента будет добавлено в область видимости токена доступа, и фишке ответ и интроспектива токена Endpoint
claim `scope`. Если этот параметр выключен, область действия клиента будет исключена из токена и из ответа Endpoint Token Introspection. Как упоминалось выше, в некоторых встроенных областях действия клиента этот переключатель отключен, это означает, что
не включены в претензию `scope` даже если они применяются в отношении конкретного запроса.

[[_client_scopes_linking]]
== Связать область клиента с клиентом

Связь между областью действия клиента и клиентом настроена на вкладке *Клиентские Области* клиента. Вот как он ищет приложение `myclient`:

image:images/client-scopes-default.png[]

Между рамками клиента и клиентом существует два способа.

Области клиента по умолчанию:: Эта настройка применима к клиентам OpenID Connect и SAML. Границы клиентов по умолчанию применяются при выдаче токенов OpenID Connect или утверждений SAML для клиента. Клиент унаследовал протокол Mappers и сопоставления рамок роли, которые определены в пределах клиентской области. Для протокола OpenID Connect карты и сопоставления рамок роли всегда применяются, вне зависимости от значения, используемого для параметра области в запросе авторизации OpenID Connect.
Необязательные клиентские области:: Эта настройка применима только для клиентов OpenID Connect. Необязательные рамки клиента применяются при выдаче токенов для этого клиента, но только по запросу параметра *scope* в запросе авторизации OpenID Connect.

=== Пример

В данном примере предполагается, что у клиента есть *профиль* и *электронная почта*, привязанные к стандартным областям клиента, и *телефон* и *адрес*, привязанные к ним как необязательные рамки для клиентов. Клиент использует значение параметра области действия при отправке запроса к конечной точке авторизации OpenID Connect.

[source,bash,subs=+attributes]
----
scope=openid phone
----

Параметр области видимости содержит строку, значения области видимости разделены на пробелы. Значение *openid* — это мета-значение, используемое для всех запросов OpenID Connect. Токен будет содержать карты и сопоставления рамок ролей из рамок клиента по умолчанию *профиль* и *email*, а также *телефон*, необязательный объем клиентской области, запрошенный параметром области охвата.

[[_client_scopes_dedicated]]
=== Выделенный охват клиентов

Существует специальный диапазон клиента, который связан с каждым клиентом. Это выделенный круг клиентов, которая всегда отображается как первая область деятельности клиента, когда вы нажимаете на вкладку *Области клиента* конкретного клиента.
Например, для «myclient» клиента область охвата клиента отображается как «ориентированная на Myclient». Эта область действия клиента представляет собой карты протокола и сопоставления ролевых охватов, которые напрямую связаны с самим клиентом.

Невозможно отсоединить область действия выделенного клиента от клиента. Также невозможно связать эту область деятельности клиента с другим клиентом. In other words, the dedicated client scope is useful
just for protocol mappers and role scope mappings, which are specific to a single client. In case you want to share the same protocol mapper configuration among multiple clients, it is usually useful to create
a client scope in the realm tab *Client scopes* and then link this shared client scope to every client that should apply this shared configuration.

На вкладке *Область* выделенной области клиента, вы можете определить сопоставления ролей, применимые к этому клиенту. Вы также можете увидеть переключатель *Разрешенные полные рамки* на этой вкладке.
Подробности об этом переключателе описаны в <_role_scope_mappings, этом разделе>> и в <_oidc_token_role_mappings,этом разделе>>.

NOTE: В админе REST API и во внутренней памяти {project_name} , выделенные клиентом рамки не существуют, так как его протокольные карты и сопоставления ролей внутренне связаны с самим клиентом. Этого
выделенная область деятельности клиента на самом деле просто абстракция для консольного интерфейса администратора.

[[client-scopes-permissions]]
== Разрешения рамок клиента

При выдаче токенов пользователю, область действия применима только в том случае, если пользователю разрешено его использовать.

Когда область действия клиента не имеет определенных сопоставлений рамок ролей, каждому пользователю разрешено использовать эту область действия. Однако, когда рамки действия клиента имеют определенные сопоставления, пользователь должен быть членом по крайней мере одной из ролей. Должно быть пересечение между ролями пользователя и ролями рамок клиента. Составные роли учитываются при оценке этого перекрестка.

Если пользователю не разрешено использовать рамки клиента, при генерации токенов не будут использоваться протоколы или сопоставления рамок ролей. Область действия клиента не будет отображаться в значении _scope_ в маркере.

[[_downscoping]]
== Понизить границы

В OAuth/OIDC, *downscoping* - это процесс обмена существующим токеном доступа JWT для нового с более ограниченным набором прав (областей) и/или узкой аудиторией. In the OAuth 2.0 refresh token grant type, the https://datatracker.ietf. сам rg/doc/html/rfc6749#section-6[RFC 6749] ограничивает запрошенную область, заявив, что она не должна включать ни одну область, которая первоначально не была предоставлена владельцем ресурса. Таким образом, эта концепция *понижается* очень распространена и очень рекомендуется по соображениям безопасности.

{project_name} предоставляет исполнителю <<_client_policies,client policy>>, который обеспечивает это *downscoping* идея для других типов грантов. Исполнитель называется `downscope-assertion-grant-enforcer` и на данный момент применяется к ссылке:{securing_apps_token_exchange_link}#_standard-token-exchange[Standard token exchange]. Когда этот клиентский исполнитель применяется, обмен токенов допускается только для тех областей, которые уже присутствуют в первоначальном JWT (параметр `subject_token`). Возвращается ошибка, если запрашивается какая-либо другая дополнительная область, независимо от того, разрешена ли клиентская конфигурация эта область как опциональная или по умолчанию. Ограничения по умолчанию, которые настроены как *включить в область символа* *false* (например, `basic` или `acr` в конфигурации по умолчанию) являются единственным исключением. Эти области невидимы для запрашивающего лица и считаются обязательными для любого типа гранта. Как только этот исполнитель будет применен для клиента, *downscoping* является единственной опцией при обмене токена доступа, никаких дополнительных рамок никогда не будет предоставлено.

== Объяснены области применения

Термин _scope_ имеет несколько значений в спецификациях {project_name} и OAuth/OIDC. Ниже даны разъяснения по различным _сферам_ используемым в {project_name}:

Область действия клиента:: Клиентские рамки являются объектами {project_name} , которые настроены на уровне области и могут быть связаны с клиентами. Рамки действия клиента ссылаются на их имя, когда запрос отправлен в конечную точку авторизации {project_name} с соответствующим значением параметра *scope*. Смотрите раздел <<_client_scopes_linking, область видимости клиента >> для получения более подробной информации.
Сопоставление рамок ролей:: Это доступно под вкладкой *Область* границ клиента или клиента. Используйте *сопоставление рамок ролей* для ограничения ролей, которые могут быть использованы в токенах доступа. Смотрите <_role_scope_mappings, раздел сопоставления ролей>> для получения подробной информации.
Области авторизации:: *Область авторизации* охватывает действия, которые могут быть выполнены в приложении. См. ссылку:{authorizationguide_link}[Руководство служб авторизации] для получения более подробной информации.
