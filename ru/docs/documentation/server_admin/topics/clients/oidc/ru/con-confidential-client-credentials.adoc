[[_client-credentials]]
= Конфиденциальные данные клиента

image:images/client-credentials.png[Вкладка учетных данных]

Выпадающий список *Аутентификатор Клиента* содержит тип учетных данных для вашего клиента.

*ID клиента и секрет*

Этот выбор является настройкой по умолчанию. Случайный секрет генерируется автоматически, но его можно переопределить с заданным значением, если необходимо. Секрет клиента также может ссылаться на значение, хранящееся в <_vault-administration,external vault>>. Нажмите *Перегенерировать*, чтобы воссоздать случайный секрет при необходимости.

Как указано в спецификации OAuth2 и OpenID Connect в заголовке `Authorization: Basic`
можно аутентифицировать клиента либо с помощью секрета клиента (вместе с `client_id`), либо отправив `client_id` и `client_secret` в качестве параметров в теле метода HTTP POST. Вы можете настроить *Разрешенный метод аутентификации
для ограничения только одним указанным методом, если вы хотите аутентифицировать клиента, например, только с помощью метода `Authorization: Basic`, но никогда не с параметрами запроса
посылаются в теле метода HTTP POST.

*Подписанный JWT клиент*
image:images/client-credentials-jwt.png[Signed JWT]

*Подписанный JWT* позволяет клиенту аутентифицироваться с помощью самоподписанных утверждений. Это позволяет клиенту аутентифицироваться без общей секретности.

В этом аутентификаторе вы можете привести в исполнение *алгоритм подписи*, используемый клиентом (любой алгоритм действителен по умолчанию), и *Максимальный срок действия* для токена JWT (токены, полученные после этого периода, не будут приняты, поскольку они слишком старые, Обратите внимание, что токены должны быть выданы непосредственно перед аутентификацией, по умолчанию 60 секунд).

При выборе этого типа учетных данных вам также придется генерировать приватный ключ и сертификат для клиента в закладке "Ключи". Закрытый ключ будет использоваться для подписи JWT, в то время как сертификат используется сервером для проверки подписи.

image:images/client-oidc-keys.png[Вкладка ключей]

Нажмите на кнопку «Генерировать новые ключи», чтобы запустить этот процесс.

image:images/generate-client-keys.png[]

. Выберите формат архива, который вы хотите использовать.
. Введите *пароль ключа*.
. Введите *пароль магазина*.
. Нажмите *Создать*.

При создании ключей {project_name} будет хранить сертификат и вы скачаете закрытый ключ и сертификат для вашего клиента.

Вы также можете сгенерировать ключи с помощью внешнего инструмента, а затем импортировать сертификат клиента, нажав на *Импорт Сертификата*.

image:images/import-client-cert.png[Import Certificate]

. Выберите архивный формат сертификата.
. Введите пароль магазина.
. Выберите файл сертификата, нажав *Импорт файла*.
. Нажмите *Импорт*.

Импорт сертификата не требуется, если вы нажмете *Использовать URL-адрес JWKS*. В этом случае вы можете указать URL-адрес, в котором опубликован открытый ключ на https://datatracker.ietf.org/doc/html/rfc7517[JWK] формате. С этой опцией, если ключ был изменен, то {project_name} импортирует ключ.

Если вы используете клиент, защищенный адаптером {project_name} , вы можете настроить URL-адрес JWKS в этом формате при условии, что это будет https://myhost. om/myapp это корневой URL-адрес вашего клиентского приложения:

[source,bash,subs=+attributes]
----
https://myhost.com/myapp/k_jwks
----

См. ссылку:{developerguide_link}[{developerguide_name}] для получения более подробной информации.

*Подписано JWT, выпущенное провайдером идентификации*

*Подписанный JWT* позволяет клиенту аутентифицироваться с утверждениями клиента, выданными идентификатором провайдера. Примеры вариантов
включают в себя:

* Утверждения клиента от провайдера OpenID Connect
* SPIFFE JWT SVIDs
* Учетные записи Kubernetes

Перед использованием этого механизма проверки подлинности следует настроить поставщика идентификации, способного проверять утверждения клиентов.

Идентификационные компании, которые поддерживают утверждения клиентов:

* <<_identity_broker_oidc,OpenID Connect>> (поддержка утверждений клиента должна быть включена)
* <<_identity_broker_spiffe,SPIFFE>>

image:images/client-federated-jwt.png[]

* Идентификатор провайдера - псевдоним поставщика идентификации для использования
* Тема - идентификатор внешнего клиента для клиента (значение "sub" претензии клиента)

*Подписано JWT с помощью Client Secret*

Если вы выберите эту опцию, вы можете использовать JWT подписанный секретным ключом клиента вместо закрытого ключа.
Секрет клиента также может ссылаться на значение, хранящееся в <_vault-administration,external vault>>.

Секрет клиента будет использоваться для подписи JWT клиентом.

Как и в *Подписанном JWT* аутентификаторе, вы можете настроить алгоритм *Подпись* и *Макс. срок действия* для токена JWT.

*Сертификат X509*

{project_name} подтвердит, если клиент использует правильный сертификат X509 во время TLS Handshake.

image:images/x509-client-auth.png[]

Валидатор также проверяет Subject DN клиентского сертификата и администратора корневых сертификатов (CA) Subject DN (якорный якорь). Таким образом, {project_name} гарантирует, что сертификат, предоставленный клиентом, является ожидаемым и выдан правильным CA. Как надежный магазин или магазин mTLS используется во всех сферах, эта дополнительная проверка безопасности избегает помех между СА.

Сертификат Subject DN может использовать выражение проверки регулярности вместо точного DN. Если вы хотите принять все сертификаты для конкретного CA Subject DN, можно использовать выражение `(.*?)(?:$)`). Тем не менее, эта конфигурация устарела и будет удалена в будущей версии.

Для {project_name} существует два способа получения идентификатора клиента из запроса:

* Параметр `client_id` в запросе (описан в разделе 2.2 https://datatracker.ietf.org/doc/html/rfc6749[OAuth 2.0 Specification]).
* Поставьте `client_id` в качестве параметра формы.
