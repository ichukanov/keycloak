= Базовая конфигурация

Вкладка *Настройки* содержит множество опций для настройки этого клиента.

image:images/client-settings-oidc.png[Настройки вкладки]

== Общие настройки

*ID клиента*:: Строка с буквенно-цифровым идентификатором, которая используется в OIDC запросах и в базе данных {project_name} для идентификации клиента.
*Имя*:: Имя клиента в экране интерфейса {project_name}. Чтобы локализовать
имя, настройте строковое значение замены. Например, строковое значение, такое как $\{myapp}.  См. ссылку:{developerguide_link}[{developerguide_name}] для получения дополнительной информации.
*Описание*:: Описание клиента.  Этот параметр также может быть локализован.
*Всегда отображать в консоли*:: Всегда отображать этого клиента в консоли аккаунта, даже если у этого пользователя нет активного сеанса.

== Настройки доступа

*Корневой URL*:: Если {project_name} использует какие-либо настроенные относительные URL, это значение добавляется к ним.
*Домашний URL*:: Предоставляет URL-адрес по умолчанию, когда сервер авторизации должен перенаправлять или ссылаться на клиента.
*Допустимые URI перенаправления*:: Обязательное поле.  Введите шаблон URL и нажмите *+*, чтобы добавить и *-*, чтобы удалить существующие URL, и нажмите *Сохранить*. Точное (чувствительное к регистру) сопоставление строк используется для сравнения допустимых URI перенаправления.
+
Вы можете использовать маски в конце шаблона URL. Например, `$$http://host.com/path/*$$`. Во избежание проблем с безопасностью, если передаваемый URI содержит *пользовательскую информацию* или его *путь* управляет доступом к родительскому каталогу (`/. /`) сравнение шаблонов не проводится, но стандартное и безопасное сопоставление строк.
+
Полная маска `$$*$` корректный URI перенаправления также может быть настроена на разрешение любого *http* или *https* перенаправления. Пожалуйста, не используйте его в производственной среде.
+
Эксклюзивные шаблоны редиректов URI обычно более безопасны. Смотрите xref:unspecific-redirect-uris_{context}[Unspecific Redirect URI] для получения дополнительной информации.
Веб-сайты:: Введите шаблон URL и нажмите +, чтобы добавить и - для удаления существующих URL. Нажмите "Сохранить".
+
Эта опция обрабатывает link:https://fetch.spec.whatwg.org/[Cross-Origin Resource Sharing (CORS)].
Если в браузере JavaScript попытается выполнить HTTP запрос AJAX на сервер, домен которого отличается от кода, от которого был код
JavaScript, запрос должен использовать CORS. Сервер должен обрабатывать CORS-запросы, иначе браузер не будет отображать или разрешить обработку запроса. Этот протокол защищает XSS, CSRF и другие атаки на основе JavaScript.
+
Указанные здесь URL-адреса домена встроены в токен доступа, отправленный клиентскому приложению. Клиентское приложение использует эту информацию, чтобы решить, следует ли ссылаться на CORS-запрос на него. Только {project_name} адаптеры поддерживают эту функцию. См. ссылку:{securing_apps_link}[{securing_apps_name}] для получения дополнительной информации.

[[_admin-url]]
Админ URL:: Обратная конечная точка для клиента. Сервер использует этот URL-адрес для выполнения обратных вызовов, таких как толкание политики отзыва, выполнение выхода из бэкканала, и другие административные операции. Для {project_name} servlet адаптеров может быть корневым URL-адресом сервлета.
Сообщения обратного вызова, отправленные на этот URL, отправляются в конкретном формате {project_name} , который не является стандартом OIDC. Этот формат поддерживается только для клиентов, обеспеченных
унаследованными адаптерами {project_name} Java OIDC или link:https://docs.wildfly.org/37/WildFly_Elytron_Security.html#Keycloak_Integration[Elytron Wildfly OIDC адаптер].

== Настройка способностей

*Аутентификация Клиента*:: Тип OIDC клиента.
* _ON_
+
Для клиентов на сервере, выполняющих вход в браузер и требующих клиентских секретов при выполнении запроса ключа доступа. Этот параметр должен использоваться для приложений на сервере.
Клиенты с включенной аутентификацией клиентов именуются конфиденциальными клиентами. Подробнее см. <<_client-credentials>>.
* _ВЫКЛЯ_
+
Для клиентских клиентов, выполняющих вход в браузер. Поскольку невозможно удостовериться в том, что секреты могут быть надежно сохранены клиентам, важно ограничить доступ настройкой правильного перенаправления URI.
Клиенты с отключенной аутентификацией являются публичными клиентами.
*Авторизация*:: Включает или отключает поддержку тонкой авторизации для этого клиента.
*Стандартный цвет*:: Если включено, этот клиент может использовать OIDC xref:_oidc-auth-flows-authorization[Код авторизации].
*Предоставление прямого доступа*:: Если включено, этот клиент может использовать OIDC xref:_oidc-auth-flows-direct[Предоставление прямого доступа].
*Неявный Блок*:: Если включено, этот клиент может использовать OIDC xref:_oidc-auth-flows-implicit[Implicit Flow].
*Роли сервисных счетов*:: Если включено, этот клиент может аутентифицироваться на {project_name} и получить токен доступа, посвященный этому клиенту. В соответствии с OAuth2 это позволяет поддерживать `Client Credentials Grant` для этого клиента.
*Стандартная Обмен Токенов*:: Если включено, этот клиент может использовать ссылку:{securing_apps_token_exchange_link}#_standard-token-exchange[Стандартный обмен токено].
*Авторизация 2.0 Авторизация*:: Если включено, этот клиент может использовать OIDC xref:con-oidc-auth-flows_server_administration_guide[Авторизация устройства].
*Грант OIDC CIBA*:: Если этот параметр включен, этот клиент может использовать OIDC xref:con-oidc-auth-flows_{context}[Предоставление бэкканальной аутентификации клиента].

[[_proof-key-for-code-exchange]]
*Метод PKCE*

Если злоумышленник крадет код авторизации законного клиента, Proof Key for Code Exchange (PKCE) запрещает злоумышленнику получать токены, которые применяются к коду. С помощью этой опции
вы можете указать, какой метод проверки PKCE необходим для этого клиента.

Администратор может выбрать один из этих вариантов:

*(пусто)*:: {project_name} не применяет PKCE, если клиент не посылает соответствующие параметры PKCE в конечную точку авторизации {project_name}. Поэтому PKCE все еще можно использовать, но это не требуется.
*S256*:: {project_name} применяется к клиенту PKCE, чей метод проверки кода является S256.
*обычный*:: {project_name} применяется к клиенту PKCE, чей метод проверки кода является простым.

Более подробную информацию см. https://datatracker.ietf.org/doc/html/rfc7636[RFC 7636 Proof Key for Code Exchange by OAuth Public Clients].

*Требовать токены привязки DPoP*

DPoP связывает токен доступа и токен обновления вместе с публичной частью пары ключей клиента. Подробнее см. <_dpop-bound-tokens, DPoP>>.

== Настройки входа

*Тема входа*:: Тема для использования для входа, OTP, предоставления регистрации и забытых страниц с паролем.
*Требуется согласие*:: Если включено, пользователи должны дать согласие на доступ к клиенту.
+
Для клиентских клиентов, выполняющих вход в браузер. Поскольку невозможно удостовериться в том, что секреты могут быть надежно сохранены клиентам, важно ограничить доступ настройкой правильного перенаправления URI.
*Отображать клиент на экране*:: Этот переключатель применяется, если *Обязательное Соглашение* *выключено.
* _Выкл_
+
Экран согласия будет содержать только согласия, соответствующие заданному клиентскому охвату.
* _Вкл_
+
На экране согласия будет также один элемент о самом клиенте.
*Текст с согласия клиента*:: Применяется, если *Требуется согласие* и *Отображение клиента на экране* включено. Содержит текст, который будет на экране согласия о разрешениях для этого клиента.

== Настройки выхода

[[_front-channel-logout]]
*Выход из фронт-канала*:: Если включена *Выход из фронт-канала*, приложение должно иметь возможность выходить пользователей через фронт-канал по ссылке:https://openid. et/specs/openid-connect-frontchannel-1_0.html[OpenID Connect Front-Channel Logout]. Если этот параметр включен, вы также должны указать URL-адрес `Front-Channel Logout`.
*URL выхода на фронт-канал*:: URL, который будет использоваться {project_name} для отправки запросов о выходе клиентам через фронт-канал. Если не указано, то по умолчанию он используется для домашнего URL-адреса. Эта опция применима только если опция 'Выход из фронтального канала' включена.
*Требуется сеанс выхода на фронт-канал*:: Определяет, включены ли параметры sid (ID сеанса) и iss (эмитент) в запрос выхода при использовании URL на фронт-канал Выход.

[[_back-channel-logout-url]]
*URL выхода из пропусков канала*:: URL, который приведет к выходу клиента из системы, когда он будет отправлен в этот реалм (через end_session_endpoint). Выход выполняется отправкой токена выхода, как указано в спецификации OIDC Backchannel. Если он пропущен, запрос на выход может быть отправлен на указанный `Admin URL` (если настроен) в формате, специфичном для {project_name} адаптеров. Если даже `Admin URL` не настроен, запрос на выход из системы не будет отправлен клиенту. Эта опция применима только в том случае, если опция 'Выход из фронтального канала' выключена.
*Требуется сеанс выхода из бэкканала*:: Определяет, включена ли заявка на идентификатор сессии в токен выхода при использовании *Backchannel Logout URL*.
*Выход из Backchannel отменяет сеансы в автономном режиме*:: Определяет, включено ли событие revoke_offline_access в токен выхода при использовании URL Backchannel. {project_name} отменит сеансы оффлайн при получении токена выхода с этим событием.

[[_logout-confirmation]]
*Подтверждение выхода из системы*:: Когда включено, {project_name} показывает страницу подтверждения для пользователя после успешного выхода из системы, которая гласит “Вы вышли из системы”. Эта настройка в первую очередь влияет на браузерные логины, включая xref:_oidc-logout[OIDC Logout], инициированные клиентом (RP-Initiated Logout). Если для этого клиента предоставляется и проверяется `post_logout_redirect_uri`, страница подтверждения включает ссылку (или кнопку), чтобы перейти к этому URL вместо автоматического перенаправления.
