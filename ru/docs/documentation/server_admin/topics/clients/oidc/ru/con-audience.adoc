[[audience-support]]
= Поддержка аудитории

Эти клиенты _frontend clients_, которые могут напрямую перенаправить пользователя на {project_name} для запроса аутентификации браузера. Затем конкретный клиент получит набор токенов после успешной аутентификации.

_Services_ (_Resource Servers_ в https://datatracker.ietf.org/doc/html/draft-ietf-oauth-mtls-08#section-4.2[OAuth 2 specification]) также доступны для обработки запросов от клиентских приложений и предоставления ресурсов этим приложениям.
Эти службы требуют от _Access token_ (токен предъявителя) для отправки им с _frontend application_ или с другого сервиса для аутентификации запроса.

Необходимо принять меры для того, чтобы убедиться, что токены доступа имеют ограниченные привилегии, а конкретный токен доступа не может использоваться службой для доступа к другим сторонним услугам.
В среде, где доверие к службам является низким, вы можете столкнуться со сценарием:

. `frontend client application `frontend-client` requires authentication against {project_name}.
. {project_name} аутентифицирует пользователя.
. {project_name} выдает токен для приложения `frontend-client`.
. Приложение «frontend-client» использует токен для вызова службы «service1».
. Сервис «service1» возвращает ответ приложению. Но предположим, что эта услуга попытается использовать токен и сохранить его для дальнейшего использования.
. `service1` затем вызывает другую службу `service2` с помощью токена приложений, который ранее был выслан ему. `service2` не проверяет, что токен не должен был быть
использован для вызова и он будет обрабатывать запрос и возвращать успешный ответ. Это приводит к нарушенной безопасности, поскольку `service1` неправильно использовал токен для доступа к другим сервисам от имени клиентского приложения `frontend-client`.

Этот сценарий маловероятен в условиях с высоким уровнем доверия между службами, но не в условиях, где уровень доверия является низким.

Чтобы предотвратить любое неправомерное использование ключа доступа, токен доступа может содержать претензию "aud", представляющую аудиторию. Претензия `aud` обычно должна представлять клиентские идентификаторы всех служб, в которых должен использоваться токен
. В условиях низкого доверия между службами рекомендуется:

* Ограничить аудиторию на токене, чтобы убедиться, что токены доступа содержат лишь ограниченное количество аудитории.
* Настройте ваши сервисы для верификации аудитории на токене.

Чтобы предотвратить использование «service1» из приведенного выше примера, безопасный вариант потока может выглядеть следующим образом:

. Интерфейсное приложение `frontend-client` аутентифицируется против {project_name}.
. {project_name} аутентифицирует пользователя.
. {project_name} выдаёт токен приложению `frontend-client`. `frontend-client` знает, что нужно вызвать `service1`, чтобы он поместил `scope=service1-scope` в запрос аутентификации, отправленный {project_name}.
Область `service1-scope` является <_client_scopes,Client scope>, который может быть создан администратором. В <<_audience_setup,разделы ниже>> есть некоторые параметры, как настроить такие клиентские рамки.
Токен владения будет выглядеть так:
+
[source,json]
----
"aud": "service1"
----
+
Это объявляет, что клиент может использовать этот токен доступа для вызова сервиса «service1».
. Приложение «frontend-client» использует токен для вызова службы «service1».
. `service1` служит запросу `frontend-application` клиентского приложения. Но предположим, что эта услуга попытается использовать токен и сохранить его для дальнейшего использования.
. Затем «service1» попытается вызвать «service2» с токеном. Вызывание не удалось, поскольку сервис «service2» проверяет аудиторию на токен и обнаруживает, что ее аудитория только для «service1». Поэтому `service2` отклонит запрос и вернет ошибку в `service1`. Это поведение ожидается и безопасность не нарушается.

== Возможность звонить в другую услугу

В некоторых условиях может быть желательно, чтобы `service1` мог потребоваться извлечь дополнительные данные из `service2` для возврата данных первоначальному клиентскому приложению `frontend-client`. In order to make this
possible to work, there are few possibilities:

* Убедитесь, что первоначальный токен доступа, выданный «frontend-client», будет содержать как «service1», так и «service2» как аудиторию. Если предположить, что существуют правильные рамки клиента, то `frontend-client` возможно может использовать
в качестве значения параметра `scope=service1-scope service2-scope` в качестве значения параметра scope`. После этого выданный токен будет содержать претензию "aud":
+
[source,json]
----
"aud": [ "service1", "service2" ]
----
+
Такой токен доступа может использоваться для вызова как «service1», так и «service2». Поэтому `service1` сможет успешно использовать такой токен для вызова `service2` для получения дополнительных данных.
* Предыдущий подход к обеим службам в token audience позволяет "service1" вызывать `service2`. Однако это означает, что `frontend-client` также может напрямую использовать токен доступа для вызова `service2`.
В некоторых случаях это может быть нежелательным. Вы можете использовать `service1` для вызова `service2`, но в то же время вы не хотите, чтобы `frontend-client` мог напрямую вызвать `service2`. The solution
to such scenario might be the use of the link:{securing_apps_token_exchange_link}[Token exchange]. В этом случае первоначальный токен по-прежнему будет иметь только "service1" в аудитории.
Однако после того, как токен отправлен на `service1`, `service1` может послать запрос на обмен токена на другой токен, который будет иметь `service2` в качестве аудитории. Пожалуйста, смотрите
ссылку:{securing_apps_token_exchange_link}[{securing_apps_token_exchange_name}] для подробной информации о том, как его использовать.

[[_audience_setup]]
== Настройка

При настройке проверки аудитории:

* Убедитесь, что службы настроены на проверку аудитории на токен доступа, отправленный им. Это может быть сделано именно для вашего клиента OIDC адаптера, который вы используете, чтобы защитить ваше OIDC клиентское приложение.
* Убедитесь, что токены доступа, выпущенные {project_name} , содержат все необходимые аудитории.
+
В токен можно добавить аудиторию двумя способами:
** Использование ролей клиентов, как описано в секции <_audience_resolve, Разрешение аудитории>>.
** Аудитория с жестким кодом, как описано в разделе <<_audience_hardcoded, Hardcoded audience section>>.

[[_audience_resolve]]
== Автоматически добавлять аудиторию на основе ролей клиента

Маппер протокола _Резолирование аудиенции_ определяется по умолчанию в _roles_. Карта проверяет для клиентов, у которых есть хотя бы одна роль клиента для текущего токена. Идентификатор клиента каждого такого клиента добавляется в качестве аудитории, которая полезна
если ваши сервисные клиенты полагаются на роли клиента. Сервисный клиент обычно может быть клиентом без включения каких-либо потоков, у которого не может быть никаких токенов, выданных непосредственно самому себе. Она представляет собой _сервер ресурсов OAuth 2_.

Раздел сопоставления роли токенов <<_oidc_token_role_mappings,>> содержит подробную информацию о том, как добавлены роли клиента в токен. Пожалуйста, также смотрите пример ниже.

=== Пример - сопоставления ролей токенов и претензий аудитории

Ниже приведен пример шагов, как использовать роли клиента для того, чтобы претендовать на «aud», добавленную в токен:

. Создайте <<proc-creating-oidc-client_{context},OIDC client>> `service1`. Возможно отключить *Стандартный поток* или любые другие потоки для этого клиента
так как это клиент сервиса, , который никогда не может напрямую аутентифицироваться самостоятельно. Возможным исключением может быть *Стандартный ключ обмена токенов*, если это необходимо, как описано выше.
. Перейдите на вкладку *Роль* этого клиента и создайте роль клиента `service1-role`.
. Создайте пользователя `john` в том же мире и назначьте ему роль `service1-role` клиента `service1`, созданную на предыдущем шаге.
<<proc-assigning-role-mappings_{context},This section>> содержит некоторую информацию о том, как это сделать.
. Создать область деятельности клиента под названием `service1-scope`. Может быть отмечено *Включать в область символа* как *ON*. Смотрите <<_client_scopes,этот раздел>> для подробностей о том, как создать и установить новую область применения.
. Перейдите на вкладку *Область* `service1-scope` и добавьте роль `service1-role` клиента `service1` в <<_role_scope_mappings, или сопоставления рамочных условий>> этой области действия клиента
. Создайте в реалме другого клиента «фронтенд-клиент».
. Щелкните на вкладку *Клиентские границы* этого клиента и выберите первую выделенную область клиента `frontend-client-dedicated` и затем перейдите на вкладку *Scope* и отключите *Full scope allowed* switch
. Вернитесь на вкладку *Области клиента* этого клиента и нажмите *Добавить область клиента* и свяжите `service1-scope` как *Необязательно*. Смотрите <<_client_scopes_linking, Клиентский раздел Связывания>> .
. Нажмите на подвкладку *Evaluate* в области *Клиента*, как описано в <<_client_scopes_evaluate,this section>. При заполнении пользовательских «john» и подвкладки *Генерировал токен доступа*, можно видеть, что
нет никаких претензий `aud`, так как в генерируемом примере нет ни одной роли клиента. However when adding also the scope `service1-scope` to the *Scope* field, it can be seen that there is client
role `service1-role` as it is in *Role scope mappings* of the `service1-scope` and also in the role mappings of the user `john`. Из-за того, что претензия «aud» будет также содержать «service1».

image:images/audience_resolving_evaluate.png[]

Если вы хотите, чтобы аудитория `service1` всегда использовалась для токенов, выданных клиенту `frontend-client` (без использования параметра `scope=service1-scope`), это может быть отлично, чтобы вместо этого сделать что-либо из них:

* Назначить `service1-scope` как *По умолчанию* область клиента, а не *Необязательно*
* Добавьте отображение рамок ролей `service1-role` непосредственно на <<_client_scopes_dedicated,Выделенная область клиента>> клиента. В этом случае вам вообще не понадобится `service1-scope`.

Обратите внимание, что этот подход основан на ролях клиентов, также требует, чтобы сам пользователь (пользователь `john` в примере выше) являлся членом некоторой роли клиента `service1`. В противном случае, если
не является никакой назначенной роли клиента, аудитория `service1` не будет включена. Если вы хотите, чтобы аудитория была включена вне зависимости от роли клиента, смотрите раздел <<_audience_hardcoded,Hardcoded audience>> .

[NOTE]
====
Сам фронтенд клиент автоматически не добавляется в токен доступа, что позволяет легко дифференцировать токен доступа и токен ID, поскольку токен доступа не будет содержать клиента, для которого токен выдан в качестве аудитории.

If you need the client itself as an audience, see the
<<_audience_hardcoded, hardcoded audience>> option. Тем не менее, использование одного и того же клиента, что и внешний интерфейс, и REST сервис не рекомендуется.
====

[[_audience_hardcoded]]
== Аудитория с жестким кодом

Когда служба использует роли Realm или не полагается на роли в токене вообще, может быть полезно использовать жесткую аудиторию. Твердокодированная аудитория – это протокольный картер, который добавит идентификатор клиента клиента в качестве аудитории к токену.
Вы можете использовать любое пользовательское значение, например URL, если вы хотите использовать другую аудиторию, чем идентификатор клиента.

Вы можете добавить карту протокола непосредственно к клиенту фронтенда. Если карта протокола добавляется напрямую, то всегда будет добавлена и аудитория.

Для большего контроля над картографом протокола, вы можете создать карту протокола в выделенной области клиента, которая будет вызвана, например, *service2*.

Вот пример шагов для твердой аудитории

. Создать клиент «service2»
. Создать круг клиентов «service2-scope».
. На вкладке *Mappers* этой области клиента, выберите *Настройка нового карта* и выберите *Audience*
. Выберите *Включенную клиентскую аудиторию* в качестве `service2` и сохраните карту
+
image:images/audience_mapper.png[]
. Связать только что созданный клиентский охват с некоторыми клиентами. Например, он может быть привязан как *Необязательно* клиентская область к клиенту `frontend-client`, созданному в <<_audience_resolve,предыдущий пример>.
. Вы можете опционально <<_client_scopes_evaluate, Evaluate Client Scopes>> для клиента, в котором была привязана область действия клиента (например, `frontend-client`) и генерировать пример токена доступа.
Аудитория `service2` будет добавлена аудитории сгенерированного ключа доступа, если `service2-scope` включен в параметр _scope_, когда вы назначили его в качестве опциональной области клиента.

В вашем конфиденциальном клиентском приложении убедитесь, что используется параметр _scope_. Значение типа _scope=service2-scope_ должно быть включено, когда вы хотите выдать токен для доступа к `service2`.

Смотрите по ссылке:{securing_apps_base_link}/javascript-adapter[{project_name} JavaScript adapter], если ваше приложение использует адаптер JavaScript для того, как отправить _scope_ параметр с желаемым значением.

Если вы предпочитаете не включать в запросы параметр `scope`, вместо этого вы можете связать `service2-scope` как *по умолчанию* клиентскую область или использовать выделенную область клиента, где вы настраиваете этот картер.
Это полезно, если вы хотите всегда применять аудиторию для всех запросов аутентификации OIDC клиента `frontend-client`.

NOTE: Как _Audience_ так и _Audience Resolve_ по умолчанию добавляют аудитории только к токену доступа. ID Токен обычно содержит только одну аудиторию, идентификатор клиента, для которого был выпущен токен, требование об OpenID Connect. Однако, токен доступа не обязательно имеет идентификатор клиента, который был выдан, если не добавил _Audience_mapper.

== Проверка аудитории проспекции токена

Конечная точка интроспекции токена OAuth2 проверяет, что клиент присутствует в заявлении аудитории токена (`aud`), прежде чем разрешить интроспективность. Это предотвращает интроспективные токены, которые не предназначались для клиентов.

Если вам нужно отключить эту проверку во время миграции, вы можете включить функцию обратной совместимости в *OpenID Connect Compatibility Modes*, включив *Разрешить интроспекцию токена без проверки аудитории* у клиента, выполняющего интроспекцию. link:https://www.keycloak.org/server/all-provider-config#_openid_connect[OpenID Connect provider configuration] для настройки общесистемного сервера.
