= Расширенная конфигурация

После заполнения полей на вкладке *Настройки*, вы можете использовать другие вкладки для выполнения расширенной конфигурации.

ifeval::[{project_community}==true]

Например, вы можете использовать вкладки *Ролл* или *Клиентские рамки* для настройки ролей клиента, определенных для клиента или управления его рамками. Также смотрите остальные разделы в этой главе о других возможностях.

endif::[]

== Расширенная вкладка

При нажатии на вкладку *Дополнительные* отображаются дополнительные поля.  Для получения подробной информации о конкретном поле, нажмите на значок вопроса для этого поля.  Однако в этом разделе подробно описываются некоторые поля.

== Прекрасная конфигурация OpenID Connect

*Logo URL*

URL-адрес, который ссылается на логотип для клиентского приложения.

*URL политики*

URL-адрес, который клиент передает конечному пользователю, чтобы прочитать о том, как будут использоваться данные профиля.

*Условия предоставления услуг*

URL-адрес, который Клиент доверяющей стороны предоставляет конечному пользователю для ознакомления с условиями обслуживания Вернувшейся стороны.

[[_jwe-id-token-encryption]]
*Подписан и зашифрован ID Token Support*

{project_name} может шифровать токены ID согласно спецификации https://datatracker.ietf.org/doc/html/rfc7516[Json Web Encryption (JWE)] . Администратор определяет, зашифрованы ли идентификационные токены для каждого клиента.

Для шифрования ключа ID используется ключ шифрования (CEK). {project_name} и клиент должны договориться, какой ЦЭК используется и как он доставлен. Метод, используемый для определения CEK, является режимом управления ключами. Режим управления ключами, поддерживаемый {project_name} , является шифрованием ключей.

В шифровании ключа:

. Клиент генерирует асимметричную криптографическую ключевую пару.
. Открытый ключ используется для шифрования CEK.
. {project_name} генерирует CEK по ID токену
. {project_name} шифрует идентификационный токен, используя этот сгенерированный CEK
. {project_name} шифрует CEK с помощью публичного ключа клиента.
. Клиент расшифрует шифрование CEK с помощью закрытого ключа
. Клиент расшифрует идентификационный токен, используя расшифрованный CEK.

Нет компании, кроме клиента, может расшифровать идентификационный токен.

Клиент должен передать свой открытый ключ для шифрования CEK {project_name}. {project_name} поддерживает загрузку публичных ключей по URL, предоставленному клиентом. Клиент должен предоставить открытые ключи в соответствии с описанием https://datatracker.ietf.org/doc/html/rfc7517[Json Web Keys (JWK)] .

Процедура:

. Откройте вкладку *Ключи* клиента.
. Переключить *JWKS URL* на ON.
. Введите URL публичного ключа клиента в текстовом окне *JWKS URL*.

Алгоритмы шифрования Key определены в спецификации https://datatracker.ietf.org/doc/html/rfc7518#section-4.1[Json Web Algorithm (JWA)] . {project_name} поддержка:

* RSAES-PKCS1-v1_5(RSA1_5)
* RSAES OAEP с параметрами по умолчанию (RSA-OAEP)
* RSAES OAEP 256 с использованием SHA-256 и MFG1 (RSA-OAEP-256)

Процедура выбора алгоритма:

. Откройте вкладку *Дополнительно* клиента.
. Откройте *Fine Grain OpenID Connect Configuration*.
. Выберите алгоритм из меню раскрытия *ID Token Encryption Content Engorithm*.

[[_mtls-client-certificate-bound-tokens]]
*OAuth 2.0 токены доступа к взаимным доменам сертификата TLS*

Взаимная TLS связывает токен доступа и токен обновления вместе с сертификатом клиента, который обменивается во время рукопожатия TLS. Эта привязка не позволяет атакующему использовать украденные токены.

Этот тип токена является идентификатором держателя-ключа. В отличие от токена предъявителя, получатель токена держателя ключа может проверить, является ли отправитель токена законным.

Если эта настройка включена, рабочий процесс:

. Запрос токена отправляется на конечную точку токена в потоке кода авторизации или гибридного потока.
. {project_name} запрашивает клиентский сертификат.
. {project_name} получает клиентский сертификат.
. {project_name} успешно проверяет клиентский сертификат.

Если проверка не удалась, то {project_name} отвергает токен.

В следующих случаях {project_name} будет проверять клиент, отправляющий токен доступа или токен обновления:

* Запрос на обновление токена отправляется на конечную точку токена с идентификатором держателя-ключа.
* Запрос UserInfo отправлен в конечную точку UserInfo с маркером доступа владельца.
* Запрос на выход отправлен на конечную точку выхода не совместимую с OIDC {project_name} с токеном обновления владельца ключа.

Смотрите https://datatracker.ietf.org/doc/rfc8705/[Mutual TLS Client Certificate Bound Access Tokens] в OAuth 2.0 Mutual TLS Client Authentication and Certificate Bound Access Tokens для более подробной информации.

[NOTE]
====
Токены ограничения на отправку, такие как X. 09 tokens (tokens mTLS с требованием подтверждения `x5t#S256`), не могут быть использованы в качестве параметра `subject_token` по ссылке:{securing_apps_token_exchange_link}#_standard-token-exchange[Standard Token Exchange].
====

[NOTE]
====
{project_name} клиентские адаптеры не поддерживают верификацию токена владельца ключа. {project_name} адаптеры воспринимают доступ и обновляют токены как токены на предъявителя.
====

[[_client_advanced_settings_oidc]]
*Расширенные настройки для OIDC*

Расширенные настройки OpenID Connect позволяют вам настроить переопределения на уровне клиента для <_timeouts, сеанса и токенов таймаута>>.

image:images/client-advanced-settings-oidc.png[Дополнительные настройки]

|===
|Конфигурация |Описание

|Маркер доступа
|Значение переопределяет параметр Realm с одинаковым именем.

|Идёт сеанс Клиента
|Значение переопределяет параметр Realm с одинаковым именем. Значение должно быть короче *SSO Session Idle*.

|Максимальный сеанс клиента
|Значение переопределяет параметр Realm с одинаковым именем. Значение должно быть короче *SSO Session Max*.

|Оффлайн сеанс Клиента
|Этот параметр позволяет настроить короткий автономный тайм-аут простоя для клиента. Время ожидания истекло, пока сеанс не простаивает до того, как {project_name} отменит его токен в автономном режиме. Если не установлено, используется реалм <_offline-session-idle,Offline Session Idle>>.

|Максимальный оффлайн сеанс клиента
|Этот параметр позволяет настроить более короткий автономный период жизни для клиента. Время жизни - максимальное время, прежде чем {project_name} отменит соответствующий токен в автономном режиме. Этому параметру нужно <_offline-session-max-limited,Offline Session Max Limited>> включиться глобально, и по умолчанию <_offline-session-max,Offline Session Max>.
|===

[[_mapping-acr-to-loa-client]]
*Карта ACR до уровня аутентификации (LoA) *

В дополнительных настройках клиента можно определить, какое значение "Authentication Context Class Reference (ACR)" сопоставлено с каким параметром "Level of Authentication (LoA)".
Это сопоставление может быть указано также в области, как указано в <_mapping-acr-to-loa-realm,ACR в LoA Mapping>>. Лучшей практикой является настройка этого сопоставления на уровне
реалмов, что позволяет делиться одинаковыми настройками между несколькими клиентами.

`По умолчанию ACR Values` можно использовать для указания значений по умолчанию, когда запрос на вход отправлен от этого клиента на {project_name} без параметра `acr_values` и без
параметра `claims`, который прикреплен к категории `acr`. https://openid.net/specs/openid-connect-registration-1_0.html#ClientMetadata[Официальная спецификация динамической регистрации OIDC].

WARNING: Обратите внимание, что ACR значения по умолчанию используются в качестве уровня по умолчанию, однако он не может быть надежно использован для принудительного входа с конкретным уровнем.
Например, предположим, что вы настроили значения ACR по умолчанию на уровень 2. Тогда по умолчанию для аутентификации с уровнем 2.
Однако, если пользователь явно прикрепляет параметр к запросу логина, например, `acr_values=1`, то будет использован уровень 1. As a result, if the client
really requires level 2, the client is encouraged to check the presence of the `acr` claim inside ID Token and double-check that it contains the requested level 2.
Чтобы применить использование определенного ACR со стороны {project_name} , используйте параметр `Minimum ACR Value`.
Это позволяет администраторам применять ACR даже для приложений, которые не могут проверить запрошенную претензию `acr` внутри токена.

image:images/client-oidc-map-acr-to-loa.png[alt="ACR to LoA mapping"]

Подробнее см. <_step-up-flow,Step-up Authentication>> и https://openid.net/specs/openid-connect-core-1_0.html#acrSemantics[официальные спецификации OIDC].
