[[user-profile]]
= Управление атрибутами пользователя

В {project_name} пользователь связан с набором атрибутов. These attributes are used to better describe and identify
users within {project_name} as well as to pass over additional information about them to applications.

Профиль пользователя определяет хорошо определенную схему представления атрибутов пользователя и того, как они управляются в реалме.
Предоставляя последовательный просмотр информации о пользователе, позволяет администраторам контролировать различные аспекты управления атрибутами
, а также упростить расширение {project_name} для поддержки дополнительных атрибутов.

Although the user profile is mainly targeted for attributes that end-users can manage (e.g.: first and last names, phone, etc)
it also serves for managing any other metadata you want to associate with your users.

Среди других возможностей, профиль пользователя позволяет администраторам:

* Определить схему для атрибутов пользователя
* Определяет, требуется ли атрибут на основе контекстной информации (напр. если требуется только для пользователей, или администраторов, или и то и другое, или в зависимости от запрашиваемой границы.)
* Определить специальные права для просмотра и редактирования атрибутов пользователя, возможность соблюдать жесткие требования к конфиденциальности, в которых некоторые атрибуты не могут быть видны или изменены третьими лицами (включая администраторов)
* Динамически применять соответствие профилю пользователя таким образом, чтобы информация пользователя всегда обновлялась и соответствовала метаданным и правилам, связанным с атрибутами
* Определить правила проверки на основе атрибутов путем использования встроенных валидаторов или написания пользовательских
* Динамически отображать формы, с которыми пользователи взаимодействуют как регистрация, обновление профиля, брокерство, и личную информацию в консоли аккаунта, в соответствии с определениями атрибутов и без необходимости вручную изменять темы.
* Настроить интерфейсы управления пользователями в консоли администрирования, чтобы атрибуты отображались динамически на основе схемы профиля пользователя

Конфигурация профиля пользователя использует формат <<_user-profile-json-configuration,JSON>> для представления атрибутов и их метаданных. Из консоли администратора,
вы можете управлять конфигурацией, нажав в меню `Realm Settings` в левой части и нажав на вкладку `User Profile` на этой странице.

В следующих разделах мы рассмотрим, как создать собственную схему вашего профиля или конфигурацию и как управлять атрибутами.

== Понимание настроек по умолчанию

По умолчанию, {project_name} предоставляет базовую конфигурацию профиля пользователя, охватывающую некоторые из наиболее распространенных атрибутов пользователя:

[cols="2*", options="header"]
|===
|Наименование
|Описание

|`username` |Имя пользователя

|`email` |Предпочтительный адрес электронной почты конечного пользователя.

|`имя` |Имя или имя конечного пользователя

|`lastName` |Фамилия(и) или фамилия (фамилии) конечного пользователя
|===

In {project_name}, both `username` and `email` attributes have a special handling as they are often used to identify, authenticate,
and link user accounts. Для этих атрибутов вы можете изменить их настройки, и вы не можете их удалить.

[NOTE]
====
Поведение атрибутов `username` и `email` соответственно меняется в настройках `Login` в вашем реалме. Например,
изменение `Email как имя пользователя` или `Edit username` перезапишет любую конфигурацию, которую вы указали в конфигурации профиля пользователя.
====

Как вы увидите в следующих разделах, вы можете изменить конфигурацию по умолчанию, добавив свои собственные атрибуты
или изменив настройки для любого из доступных атрибутов, чтобы лучше соответствовать вашим потребностям.

== Понимание контекстов профиля пользователя

В {project_name}пользователи управляются через различные контекста:

* Регистрация
* Обновить профиль
* Просмотр профиля при аутентификации через брокера или социального провайдера
* Консоль аккаунта
* Администрация (например: администраторская консоль и API администратора REST API)

Except for the `Administrative` context, all other contexts are considered end-user contexts as they are related to user self-service
flows.

Знание этих контекстов важно понимать, где конфигурация вашего профиля пользователя вступит в силу при управлении пользователями.
Regardless of the context where the user is being managed, the same user profile configuration will be used to render UIs and validate
attribute values.

Как вы увидите в следующих разделах, вы можете ограничить определенные атрибуты доступными только из административного контекста и полностью отключить их
для конечных пользователей. Другое решение также верно, если вы не хотите, чтобы администраторы имели доступ к определенным атрибутам пользователя, но только к конечному пользователю.

== Понимание Управляемых и Неуправляемых Атрибутов

По умолчанию, {project_name} распознает только атрибуты, определенные в конфигурации вашего профиля.
Сервер игнорирует любой другой атрибут, который там явно не определен.

Строго относиться к каким пользовательским атрибутам могут быть установлены ваши пользователи, а также к тому, как их значения валидированы,
{project_name} может добавить еще один защитный барьер в ваш реалм и помочь вам избежать неожиданных атрибутов и значений, связанных с вашими пользователями.

При этом атрибуты пользователей можно классифицировать следующим образом:

* *Управляет*. Это атрибуты, контролируемые вашим профилем пользователя, которым вы хотите разрешить конечным пользователям и администраторам
управлять из любого контекста профиля пользователя.
Для этих атрибутов требуется полный контроль над тем, как и когда они управляются.
* *Неуправляемый*. Это атрибуты, которые вы явно не определяете в вашем профиле пользователя, поэтому по умолчанию {project_name}игнорирует их.

Хотя неуправляемые атрибуты отключены по умолчанию, вы можете настроить свой реалм, используя различные политики для определения того, как они обрабатываются сервером.
Для этого нажмите в меню «Параметры реалма» в левой части нажмите на вкладку «Общие», и выберите любой из следующих опций в настройках `Unmanaged Attributes`:

* *Отключено*. Это политика по умолчанию, так что неуправляемые атрибуты отключены во всех контекстах профиля пользователя.
* *Включено*. Эта политика позволяет использовать неуправляемые атрибуты для всех контекстов профиля пользователя.
* *Администратор может просматривать*. Эта политика позволяет использовать неуправляемые атрибуты только в административном контексте только для чтения.
* *Администратор может редактировать*. Эта политика позволяет использовать неуправляемые атрибуты только из административного контекста для чтения и записей.

Эти политики дают вам более точный контроль над тем, как сервер будет обрабатывать неуправляемые атрибуты.
Вы можете полностью отключить или поддерживать неуправляемые атрибуты при управлении пользователями через административный контекст.

Когда неуправляемые атрибуты включены (даже если частично), вы можете управлять ими из консоли администрирования на вкладке «Атрибуты» в пользовательском интерфейсе.
Если у политики установлен параметр `Disabled` эта вкладка недоступна.

As a security recommendation, try to adhere to the most strict policy as much as possible (e.g.: `Disabled` or `Admin can edit`) to prevent unexpected
attributes (and values) set to your users when they are managing their profile through end-user contexts.
Избегайте установки политики `Включить` и предпочтительно определить все атрибуты, которые конечные пользователи могут управлять в конфигурации профиля пользователя под вашим контролем.

[NOTE]
====
Политика `Включить` предназначена для миграции миров из предыдущих версий {project_name} и избежания нарушения
поведения при использовании пользовательских тем и расширении сервера своими пользовательскими атрибутами.
====

Как вы увидите в следующих разделах, вы также можете ограничить аудиторию для атрибута, выбрав, что она должна быть видна или доступна для записи пользователям и/или администраторам.

Для неуправляемых атрибутов максимальная длина составляет 2048 символов.
Чтобы указать другую минимальную или максимальную длину, измените неуправляемый атрибут на управляемый атрибут и добавьте валидатор `length`.

WARNING: {project_name} кэширует пользовательские объекты во внутренних кэшах.
Чем дольше атрибуты, тем больше потребляет память.
Поэтому рекомендуется ограничить размер атрибутов длины.
Рассмотрим возможность хранения больших объектов за пределами {project_Name} и ссылки на них по ID или URL.

== Управление профилем пользователя

Конфигурация профиля пользователя управляется на основе каждого реалма. Для этого нажмите на ссылку
в меню `Realm Settings` и нажмите на вкладку `User Profile`.

image:images/user-profile-tab.png[]

В субвкладке `Атрибуты` у вас есть список всех управляемых атрибутов.

На субвкладке `Атрибуты группы` вы можете управлять группами атрибутов. Группа атрибутов позволяет связать атрибуты так, чтобы они отображались вместе при отрисовке форм для пользователя.

В подвкладке `JSON Editor` вы можете просматривать и редактировать <_user-profile-json-configuration,JSON>>. Вы можете использовать эту вкладку
для захвата текущей конфигурации или управления ею вручную. Любые изменения, внесенные в эту вкладку, отражены в других вкладках и наоборот.

В следующем разделе вы узнаете, как управлять атрибутами.

== Управление атрибутами

На субвкладке `Атрибуты` вы можете создавать, редактировать и удалять управляемые атрибуты.

Чтобы определить новый атрибут и связать его с профилем пользователя, нажмите на кнопку *Создать атрибут* в верхней части списка атрибутов.

image:images/user-profile-create-attribute.png[]

При настройке атрибута вы можете определить следующие параметры:

Наименование:: Название атрибута, используемое для уникальной идентификации атрибута.
Отображать имя:: Удобное имя атрибута, в основном используемое при отрисовке пользовательских форм. Он также поддерживает <<_using-internationalized-messages,Использование интернационализированных сообщений>>.
Множество значений:: Если этот параметр включен, атрибут поддерживает несколько значений и UI отображаются соответствующим образом, чтобы разрешить установку многих значений. При включении этой настройки
убедитесь, что добавьте валидатор для установки жесткого ограничения на количество значений.
Значение по умолчанию:: Определяет значение, которое будет автоматически назначено атрибуту, если пользователь не предоставит его.
Убедитесь, что это значение по умолчанию соответствует всем настроенным валидаторам атрибута.
Группа атрибутов:: Группа атрибутов, к которой принадлежит атрибут, если таковые имеются.
Включено когда:: Включает или отключает атрибут. Если установлено значение `Всегда`, атрибут доступен из любого контекста профиля пользователя.
Если установлено значение `Область запрошена`, атрибут доступен только в том случае, если клиент, действующий от имени пользователя, запрашивает набор
одного или нескольких рамок. You can use this option to dynamically enforce certain attributes depending on the client scopes
being requested. Для консоли администрирования область не вычисляется и атрибут всегда включен.
Это происходит потому, что атрибуты фильтрации по областям работают только при запуске потоков аутентификации конечного пользователя.
Требуется:: Установите условия, чтобы отметить атрибут как требуемый. Если отключено, атрибут является необязательным.
Если включено, вы можете установить параметр `Обязательно для`, чтобы отметить атрибут как требуемый в зависимости от контекста пользовательского профиля, чтобы
атрибут необходим для конечных пользователей (через контекст конечного пользователя) или для администраторов (через административный контекст), или и то и другое.
Вы также можете установить параметр `Обязательно когда`, чтобы отметить атрибут как требуемый, только когда запрашивается набор одного или более клиентских областей охвата.
Если установлено значение `Всегда`, атрибут требуется из любого контекста профиля пользователя.
Если установлено значение `Область запрошена`, атрибут требуется только в том случае, если клиент, действующий от имени пользователя, запрашивает набор
одного или нескольких областей действия. Для Учетных и административных консолей рамки не оцениваются и атрибут не требуется.
Это происходит потому, что атрибуты фильтрации по областям работают только при запуске потоков аутентификации.
Разрешение:: В этом разделе вы можете определить разрешения на чтение и запись, когда атрибут управляется от конечного пользователя или административного контекста.
Параметр `Кто может редактировать` помечает атрибут как доступный для записи пользователем `User` и/или `Admin`, из пользовательского и административного контекста соответственно.
Параметр «Кто может просматривать» помечает атрибут как «Пользователь» и/или «Администратор» из конечного пользователя и административного контекста, соответственно.
Проверка:: В этом разделе вы можете определить валидации, которые будут выполняться при управлении значением атрибута.
{project_name} предоставляет набор встроенных валидаторов, которые вы можете выбрать, с возможностью добавить свои собственные. For more details, look at
the <<_validating-attributes,Validating Attributes>> section.
Аннотация:: В этом разделе вы можете связать аннотации с атрибутом. Аннотации в основном полезны для передачи дополнительных метаданных фронтендам для целей рендеринга.
Для получения более подробной информации обратитесь к разделу <_defining-ui-annotations>> .

При создании атрибута атрибут доступен только в административных контекстах, чтобы избежать неожиданно разоблачения атрибутов конечным пользователям.
В самом деле, атрибут не будет доступен конечным пользователям, если они управляют своим профилем через контекст конечного пользователя. Вы можете в любое время изменить настройки `Разрешения`
на ваши потребности.

[[_validating-attributes]]
== Проверка атрибутов

Вы можете включить валидацию для управляемых атрибутов, чтобы убедиться, что значение атрибута соответствует определенным правилам.
Для этого вы можете добавить или удалить валидаторы из настроек `Validations` при управлении атрибутом.

image:images/user-profile-validation.png[]

Проверка происходит в любое время при написании атрибута, и они могут бросать ошибки, которые будут показаны в UI, когда значение
не прошло валидацию.

По соображениям безопасности, каждый атрибут, который можно редактировать пользователям, должен иметь проверку для ограничения размера введенных значений.
Если валидатор `length` не задан, то максимальная длина 2048 символов по умолчанию {project_name} по умолчанию

*options*: массив строк, содержащих разрешенные значения.

|up-username-not-idn-homograph

|многоценный
|Проверяет размер многозначного атрибута.
|
*min*: целое число для определения минимально допустимого количества значений атрибута.

*max*: целое число для определения максимально допустимого количества значений атрибута.

[[_defining-ui-annotations]]
== Определение аннотаций интерфейса

In order to pass additional information to frontends, attributes can be decorated with
annotations to dictate how attributes are rendered. Эта возможность в основном полезна при расширении {project_name} тем
для динамического отображения страниц на основе аннотаций, связанных с атрибутами.

Используются, например, для <_changing-the-html-type-for-an-attribute,Изменение HTML `type` для атрибутов>> и <_changing-the-dom-representation-of-an-attribute, висит представление DOM атрибута>>, как вы
увидите в следующих разделах.

image:images/user-profile-annotation.png[]

Аннотация - это пара ключ/значение, совместно с интерфейсом, чтобы они могли изменить способ представления HTML-элемента, соответствующего атрибуту.
Вы можете установить любую аннотацию, которую хотите присвоить атрибуту, пока аннотация поддерживается темой вашего реалма.

[NOTE]
====
Единственное ограничение, которое у вас есть, заключается в том, чтобы избежать использования аннотаций с использованием префикса `kc` в их ключах, потому что эти аннотации
с использованием этого префикса зарезервированы для {project_name}.
====

[[_managing_options_for_select_fields]]
=== Определение опций для выбора и выбора полей

Варианты для выбора и мультивыбора полей взяты из валидации, применяемой к атрибуту
убедитесь, что варианты проверки и поля в пользовательском интерфейсе всегда являются согласованными. По умолчанию, параметры взяты из встроенных опций валидации.

Вы можете использовать различные способы предоставления красивых человеко-читаемых этикеток для выбора и выбора опций. Самый простой
— когда значения атрибута совпадают с метками пользовательского интерфейса. Дополнительная конфигурация в данном случае не требуется.

image:images/user-profile-select-options-simple.png[]

Когда значение атрибута не подходит для пользовательского интерфейса, вы можете использовать простую поддержку интернационализации, предоставленную
в `inputOptionLabelsI18nPrefix` аннотации. Она определяет префикс для интернационализационных ключей, значение параметра добавляется к этому префиксу.

image:images/user-profile-select-options-simple-i18n.png[]

Локализованные тексты ярлыков пользовательского интерфейса для значения параметра должны быть предоставлены `userprofile.jobtitle.sweng` и `userprofile.jobtitle.swarch`
ключей, затем, используя обычный механизм локализации.

Вы также можете использовать аннотацию `inputOptionLabels` для предоставления меток для отдельных параметров. Она содержит карту меток для опции - ключ в карте
значения опции (определено в валидации), и значение на карте является пользовательским интерфейсом для самого текста или для его интернационализации (например, `${i18n.key}`).

[NOTE]
====
Вы должны использовать профиль пользователя `JSON Editor` для входа на карту как значение аннотации `inputOptionLabels`.
====

Пример непосредственно введенных ярлыков для отдельных опций без интернационализации:

[source,json]
----
"attributes": [
<...
{
  "name": "jobTitle",
  "validations": {
    "options": {
      "options":[
        "sweng",
        "swarch"
      ]
    }
  },
  "annotations": {
    "inputType": "select",
    "inputOptionLabels": {
      "sweng": "Software Engineer",
      "swarch": "Software Architect"
    }
  }
}
...
]
----

Пример интернационализированных этикеток для отдельных вариантов:

[source,json]
----
"attributes": [
...
{
  "name": "jobTitle",
  "validations": {
    "options": {
      "options":[
        "sweng",
        "swarch"
      ]
    }
  },
  "annotations": {
    "inputType": "select-radiobuttons",
    "inputOptionLabels": {
      "sweng": "${jobtitle.swengineer}",
      "swarch": "${jobtitle.swarchitect}"
    }
  }
}
...
]
----

Локализованные тексты должны быть предоставлены `jobtitle.swengineer` и `jobtitle.swarchitect`, затем, с использованием общего механизма локализации.

Пользовательская валидатор может быть использован для предоставления параметров благодаря аннотации атрибута `inputOptionsFromValidation`.
Эта проверка должна иметь конфигурацию `options` с набором параметров. Интернационализация работает так же, как и для опций
предоставленных встроенной проверкой «options».

[[_changing-the-dom-representation-of-an-attribute]]
=== Изменение DOM-представления атрибута

Вы можете включить дополнительное поведение клиента, установив аннотации с префиксом `kc`. These annotations are going to
translate into an HTML attribute in the corresponding element of an attribute, prefixed with `data-`, and a script with
the same name will be loaded to the dynamic pages so that you can select elements from the DOM based on the custom `data-` attribute
and decorate them accordingly by modifying their DOM representation.

Например, если вы добавите атрибут аннотации `kcMyCustomValidation`, атрибут HTML `data-kcMyCustomValidation` добавлен в
соответствующий HTML элемент атрибута, и JavaScript модуль загружен из пользовательской темы в `<THEME TYPE>/resources/js/kcMyCustomValidation. s`.
Смотрите {developerguide_link}[{developerguide_name}] для получения дополнительной информации о том, как установить пользовательский модуль JavaScript в вашу тему.

Модуль JavaScript может запускать любой код для настройки DOM и отображаемых элементов для каждого атрибута. Для этого
вы можете использовать модуль `userProfile.js` для регистрации дескриптора аннотации следующим образом:

[source,javascript]
----
import { registerElementAnnotatedBy } from "./userProfile.js";

registerElementAnnotatedBy({
  name: 'kcMyCustomValidation',
  onAdd(element) {
    var listener = function (event) {
        // do something on keyup
    };

    element.addEventListener("keyup", listener);

    // returns a cleanup function to remove the event listener
    return () => element.removeEventListener("keyup", listener);
  }
});
----

`registerElementAnnotatedBy` - это метод регистрации дескрипторов аннотаций. Дескриптор - это объект с функцией `name`,
ссылки на имя аннотации,
и 'onAdd`. Всякий раз, когда страница отображается или атрибут с аннотацией добавляется в DOM, функция `onAdd`
вызывается, чтобы вы могли настроить поведение элемента.

Функция `onAdd` также может возвращать функцию для очистки. For instance, if you are adding event listeners
to elements, you might want to remove them in case the element is removed from the DOM.

Кроме того, вы также можете использовать любой код JavaScript, который вы хотите, если `userProfile.js` недостаточно для ваших нужд:

[source,javascript]
----
document.querySelectorAll(`[data-kcMyCustomValidation]`).forEach((element) => {
    var listener = function (evt) {
        // do something on keyup
    };

    element.addEventListener("keyup", listener);
  });
----

== Управление группами атрибутов

На субвкладке `Атрибуты` вы можете создавать, редактировать и удалять группы атрибутов. Группа атрибутов позволяет вам определить контейнер для корреляционных атрибутов таким образом, чтобы он отображался вместе, когда в формах пользователя.

image:images/user-profile-attribute-group-list.png[]

[NOTE]
====
Нельзя удалить группы атрибутов, которые связаны с атрибутами. Для этого необходимо сначала обновить атрибуты, чтобы удалить привязку.
====

Чтобы создать новую группу, нажмите на кнопку *Создать группу атрибутов* в верхней части списка групп атрибутов.

image:images/user-profile-create-attribute-group.png[]

При настройке группы вы можете определить следующие параметры:

Наименование:: Название атрибута, используемое для уникальной идентификации атрибута.
Отображать имя:: Удобное имя атрибута, в основном используемое при отрисовке пользовательских форм. Он также поддерживает <<_using-internationalized-messages,Использование интернационализированных сообщений>>.
Отобразить описание:: Удобный текст, который будет отображаться как подсказка при отображении пользовательских форм. Он также поддерживает <<_using-internationalized-messages,Использование интернационализированных сообщений>>.
Аннотация:: В этом разделе вы можете связать аннотации с атрибутом. Аннотации в основном полезны для передачи дополнительных метаданных фронтендам для целей рендеринга.

[[_user-profile-json-configuration]]
== Использование конфигурации JSON

Конфигурация профиля пользователя хранится с помощью хорошо определенной схемы JSON. Вы можете выбрать редактирование конфигурации профиля пользователя напрямую, нажав на подвкладку `JSON Editor`.

image:images/user-profile-json-config.png[]

Схема JSON определяется следующим образом:

[source,json]
----
{
  "unmanagedAttributePolicy": "DISABLED",
  "attributes": [
    {
      "name": "myattribute",
      "multivalued": false,
      "displayName": "My Attribute",
      "group": "personalInfo",
      "required": {
        "roles": [ "user", "admin" ],
        "scopes": [ "foo", "bar" ]
      },
      "permissions": {
        "view": [ "admin", "user" ],
        "edit": [ "admin", "user" ]
      },
      "validations": {
        "email": {
          "max-local-length": 64
        },
        "length": {
          "max": 255
        }
      },
      "annotations": {
        "myannotation": "myannotation-value"
      }
    }
  ],
  "groups": [
    {
      "name": "personalInfo",
      "displayHeader": "Personal Information",
      "annotations": {
        "foo": ["foo-value"],
        "bar": ["bar-value"]
      }
    }
  ]
}
----

Схема поддерживает столько атрибутов и групп, сколько вам нужно.

Свойство `unmanagedAttributePolicy` определяет неуправляемую политику атрибутов, установив одно из следующих значений. For more details,
look at the <<_understanding-managed-and-unmanaged-attributes,Understanding Managed and Unmanaged Attributes>>.

* `ОТКЛЮЧИТЬ`
* `ВНИМАНИЕ`
* `ADMIN_VIEW`
* `ADMIN_EDIT`

=== Схема атрибутов

Для каждого атрибута вы должны определить имя и параметры `required`, `permission` и `annotations`.

Свойство `required` определяет, требуется ли атрибут. {project_name} позволяет вам устанавливать атрибут как требуемый на основе различных условий.

Если свойство `required` определяется как пустой объект, то атрибут всегда требуется.

[source,json]
----
{
  "attributes": [
    {
      "name": "myattribute",
      "required": {}
  ]
}
----

С другой стороны, вы можете сделать атрибут обязательным только для пользователей, или администраторов, или и то и другое. равно как отметить атрибут как требуемый только в том случае, если запрашивается конкретная область действия, когда пользователь аутентифицируется в {project_name}.

Чтобы отметить атрибут, необходимый для пользователя и/или администратора, установите свойство «роли»:

[source,json]
----
{
  "attributes": [
    {
      "name": "myattribute",
      "required": {
        "roles": ["user"]
      }
  ]
}
----

Свойство `roles` предполагает массив, значения которого могут быть `user` или `admin`, в зависимости от того, требуется ли атрибут для пользователя или администратора, соответственно.

Аналогичным образом вы можете сделать атрибут требуемым, если набор одного или нескольких областей запрашивается клиентом при аутентификации пользователя. Для этого вы можете использовать свойство `scopes` следующим образом:

[source,json]
----
{
  "attributes": [
    {
      "name": "myattribute",
      "required": {
        "scopes": ["foo"]
      }
  ]
}
----

Свойство `scopes` является массивом, значения которого могут быть любой строкой, представляющей область клиента.

Свойство атрибута `permissions` можно использовать для определения прав на чтение и запись атрибута. Разрешения устанавливаются на основе того, могут ли эти операции выполняться по атрибуту пользователем или администратором или и тем и другим.

[source,json]
----
{
  "attributes": [
    {
      "name": "myattribute",
      "permissions": {
        "view": ["admin"],
        "edit": ["user"]
      }
  ]
}
----

Свойства `view` и `edit` ожидают массива, значения которого могут быть `user` или `admin`, в зависимости от того, доступен ли атрибут или редактируется пользователем или администратором, соответственно.

Когда разрешение `edit` предоставлено, разрешение `view` выдается неявно.

Свойство атрибута `annotation` может быть использовано для привязки дополнительных метаданных к атрибутам. Аннотации в основном полезны для передачи дополнительной информации об атрибутах интерфейса, отображающих пользовательские атрибуты на основе конфигурации профиля пользователя. Каждая аннотация - это пара ключ/значение.

[source,json]
----
{
  "attributes": [
    {
      "name": "myattribute",
      "annotations": {
        "foo": ["foo-value"],
        "bar": ["bar-value"]
      }
  ]
}
----

=== Схема группы атрибутов

Для каждой группы атрибутов необходимо определить параметры «имя» и, по желанию, «аннотации».

Свойство атрибута `annotation` может быть использовано для привязки дополнительных метаданных к атрибутам. Аннотации в основном полезны для передачи дополнительной информации об атрибутах интерфейса, отображающих пользовательские атрибуты на основе конфигурации профиля пользователя. Каждая аннотация - это пара ключ/значение.

== Настройка пользовательского интерфейса

Пользовательские интерфейсы из всех контекстов профиля пользователя (включая консоль администрирования) отображаются динамически соответственно к конфигурации вашего профиля
пользователя.

Механизм рендеринга по умолчанию предоставляет следующие возможности:

* Показать или скрыть поля, основанные на разрешениях, установленных для атрибутов.
* Отображение маркеров обязательных полей в зависимости от ограничений, установленных к атрибутам.
* Изменить тип поля ввода (текст, дата, число, выборка, множественный выбор) для атрибута.
* Отметить поля только для чтения в зависимости от разрешений, установленных в атрибуте.
* Поля сортировки в зависимости от атрибутов заказа.
* Поля группы, принадлежащие той же группе атрибутов.
* Динамическая группировка полей, принадлежащих одной и той же группе атрибутов.

=== Сортировка атрибутов

Порядок атрибутов задается перетаскиванием строк атрибутов на странице списка атрибутов.

image:images/user-profile-attribute-list-order.png[]

Порядок, который вы устанавливаете на этой странице, соблюдается при отображении полей в динамических формах.

=== Атрибуты группировки

Когда динамические формы будут отображены, они попытаются группировать атрибуты, принадлежащие одной и той же группе атрибутов.

image:images/user-profile-update-profile.png[]

[NOTE]
====
Когда атрибуты связаны с группой атрибутов, порядок атрибутов также важен для того, чтобы убедиться, что атрибуты внутри одной группы были близки друг к другу, внутри одного заголовка группы. В противном случае если атрибуты внутри группы не имеют последовательного порядка, вы можете иметь один и тот же заголовок группы отображается несколько раз в динамической форме.
====

== Enabling Progressive Profiling

Чтобы удостовериться, что профили конечных пользователей соответствуют конфигурации, администраторы могут использовать `VerifyProfile` необходимые действия, чтобы в конечном итоге заставить пользователей обновить свои профили при аутентификации на {project_name}.

[NOTE]
====
Действие `VerifyProfile` похоже на действие `UpdateProfile`. Однако он использует все возможности, предоставляемые профилем пользователя, для автоматического обеспечения соответствия конфигурации профиля пользователя.
====

Если этот параметр включен, действие `VerifyProfile` будет выполнять следующие шаги при аутентификации пользователя:

* Проверьте, полностью ли профиль пользователя соответствует конфигурации пользовательского профиля в реалме. Это означает, что валидации
и убедитесь, что все они успешны.
* Если нет, выполните дополнительный шаг во время аутентификации, чтобы пользователь мог обновить любой недостающий или недопустимый атрибут.
* Если профиль пользователя соответствует конфигурации, не выполняется дополнительный шаг и пользователь продолжает процесс аутентификации.

Действие `VerifyProfile` включено по умолчанию. Чтобы отключить его, нажмите на ссылку
`Authentication` в левом меню и нажмите на вкладку `Required Actions`. На этой вкладке используйте переключатель *Включено* действия `VerifyProfile`, чтобы отключить его.

image:images/user-profile-register-verify-profile-action.png[]

== Использование интернационализированных сообщений

If you want to use internationalized messages when configuring attributes, attributes groups, and annotations, you can
set their display name, description, and values, using a placeholder that will translate to a message from a message bundle.

Для этого вы можете использовать метку-заполнитель для разрешения ключей сообщений, таких как `${myAttributeName}`, где `myAttributeName` является ключом для сообщения в наборе сообщений. For more details,
look at link:https://www.keycloak.org/ui-customization/localization#_localizing_messages_in_a_theme[Localizing messages in a theme] about how to add message bundles to custom themes.
