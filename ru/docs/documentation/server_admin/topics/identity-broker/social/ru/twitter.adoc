==== Твиттер

IMPORTANT: Twitter Identity Broker является устаревшим для удаления. Он полагается на наследие Твиттера OAuth 1.0a конечных пунктов.
Вместо этого настройте общий *OAuth v2* провайдер идентификации против конечных точек OAuth (ранее Twitter), как описано в <_twitter_oauth2_migration>>.
Брокер остается включенным по умолчанию, но планируется удалить в будущем релизе.

.Предпосылки
. Twitter аккаунт разработчика.

//-

.Процедура
. Нажмите на *Identity Providers* в меню.
. Из списка *Добавить провайдера* выберите *Twitter*.
+
image:images/twitter-add-identity-provider.png[Добавить Identity Provider]
. Скопируйте значение *Redirect URI* в буфер обмена.
. В отдельной вкладке браузера создайте приложение в https://developer.twitter.com/apps/[Twitter Application Management].
.. Введите имя приложения и нажмите *Далее*.
.. Обратите внимание на значение *API Key* и *API Key Secret* и нажмите *Настройки приложения*.
.. В разделе *Параметры аутентификации пользователя* нажмите кнопку *Установить*.
.. Выберите *Web App* в качестве *Type of App*.
.. Вставьте значение *Redirect URL* в поле *Callback URI / Redirect URL*.
.. Значение *URL веб-сайта* может быть действительным URL-адресом, за исключением `localhost`.
.. Нажмите *Сохранить* и затем *Готово*.
. В {project_name}вставьте значение `API Key` в поле *Client ID*.
. В {project_name}вставьте значение `API Key Secret` в поле *Client Secret*.
. Нажмите *Добавить*.

[[_twitter_oauth2_migration]]
===== Использование общего поставщика OAuth v2 для подключения к X/Twitter

X (ранее Twitter) поддерживает OAuth 2.0, так что встроенный провайдер идентификации *OAuth v2* может быть использован как замена устаревшего провайдера Twitter.
Смотрите https://docs.x.com/fundamentals/authentication/oauth-2-0/overview[X OAuth 2.0 documentation] для подробностей.

NOTE: Начиная с 2026 года, вам необходим платный план API, например платный тарифный план. Исходный свободный план не будет работать, и вы увидите ошибку `403 required_enrollment` при вызове {project_name} в конечную точку информации пользователя.

// https://devcommunity.x.com/t/an-appeal-to-x-consumer-apps-need-workable-api-pricing/266858

В начале 2026 года использование `+https://api.x.com/2/users/me+` API с планом pay-per-use бесплатно.
Проверьте с X по мере изменения цен.

.Процедура
. В https://developer.twitter.com/apps/[X portal] откройте ваше приложение и перейдите в *Настройки аутентификации пользователя*.
.. Установите *Тип приложения* на конфиденциальный клиент (например, *Web App*).
.. Обратите внимание на *OAuth 2.0 ID клиента* и *Секретарь*.
. Нажмите *Identity Providers* в меню {project_name}.
. Из списка *Добавить провайдера* выберите *OAuth v2*.
. Скопируйте значение *Redirect URI* и вставьте его в поле *Callback URI / Redirect URL* вашего приложения.
. Настройте провайдера со следующими значениями:
+
[%autowidth]
|===
|Настройка |Значение

|Использовать конечную точку поиска |Выкл

|URL авторизации |`+https://x.com/i/oauth2/authorize+`

|URL токена |`+https://api.x.com/2/oauth2/token+`

|URL информации пользователя |`+https://api.x.com/2/users/me?user.fields=confirmed_email+`

|Использовать PKCE |На

|Метод PKCE |S256

|ID клиента |*OAuth 2.0 ID клиента* вашего X приложения

|Секрет клиента |*Клиент* вашего X приложения

|Аутентификация клиента |*Секрет клиента отправлен в качестве базового автора*

|Запрос ID пользователя |`data.id`

|Имя пользователя |`data.username`

|Электронная почта |`data.confirmed_email`
|===
. Нажмите *Добавить*.
. Продолжить редактирование провайдера для обновления областей:
+
[%autowidth]
|===
|Настройка |Значение

|Расширенные -> Области |`users.read tweet.read`
|===

NOTE: Указанная область `tweet.read` необходима, в противном случае конечная точка пользовательской информации возвращает ошибку 403.

NOTE: X `/2/users/me` использует атрибуты пользовательской точки `data`, поэтому вышеописанные претензии используют пунктирную нотацию пути (например, `data.id`).

===== Перенос существующих пользователей со старого провайдера на нового провайдера

Пользователи, аутентифицировавшиеся со старым поставщиком Twitter, не смогут аутентифицироваться с помощью нового OAuth 2. , если они не записываются с ним.
Если они зарегистрируются, они должны будут связать их существующую учетную запись путем аутентификации с новым провайдером и с существующей учетной записью.
Кроме того, после удаления старого провайдера все пользователи потеряют ссылку провайдера идентификации на Twitter и больше не смогут войти с помощью X.

Чтобы избежать этого, переместите существующих пользователей следующим образом. Как обычно, сначала проверьте процедуру в испытательной среде.

. Создайте нового поставщика идентификации OAuth 2.0 для X/Twitter и убедитесь, что он работает.
. Выключить {project_name} для предотвращения обновления поставщика идентификационных данных и предотвращения устаревших кэшей (предпочтительно).
Кроме того, очистите кэш пользователя после миграции через REST API или консоль администратора или выполните перезапуск всех узлов.
. Создайте резервную копию базы данных, чтобы вы могли восстановиться, если миграция завершилась неудачей.
. В таблице `FEDERATED_IDENTITY` обновите столбец `IDENTITY_PROVIDER` до псевдонима нового OAuth 2. провайдер для записей, указывающих на старый псевдоним для затрагиваемого `REALM_ID`.
. Запустите {project_name} и убедитесь, что пользователи, которые использовали старый провайдер, могут войти в систему с новым провайдером.
