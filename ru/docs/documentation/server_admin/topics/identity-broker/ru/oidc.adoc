=== OpenID Connect v1.0 identity провайдеров

{project_name} брокеров идентификации провайдеров на основе протокола OpenID Connect. Эти идентификационные провайдеры (IDPs) должны поддерживать xref:con-oidc-auth-flows_{context}[Код авторизации Flow], определенный в спецификации для аутентификации пользователей и авторизации доступа.

.Процедура
. Нажмите на *Identity Providers* в меню.
. Из списка `Добавить провайдера` выберите `OpenID Connect v1.0`.
+
image:images/oidc-add-identity-provider.png[Добавить Identity Provider]
. Введите начальные параметры конфигурации. Смотрите <<_general-idp-config, General IDP Configuration>> для получения дополнительной информации о параметрах конфигурации.
+
.Конфигурация подключения OpenID
|===
|Конфигурация |Описание

|URL авторизации
|Конечная точка URL авторизации, требующая протокола OIDC.

|URL токена
|Ключ URL конечной точки, требующей протокола OIDC.

|URL выхода
|Конечная точка URL выхода из протокола OIDC. Это значение необязательно.

|Выход из бэк-канала
|Фон и вне диапазона, REST запрос IDP для выхода пользователя. Некоторые IDP выполняют выход через браузер перенаправления только потому, что они могут идентифицировать сеансы с помощью cookie браузера.

|URL информации пользователя
|Конечная точка, которую определяет протокол OIDC. Эта конечная точка указывает на информацию профиля пользователя.

|Аутентификация Клиента
|Определяет метод аутентификации Клиента {project_name} использует с кодом авторизации. В случае подписи JWT с приватным ключом, {project_name} использует закрытый ключ реалма. В других случаях определите клиентскую тайну. Дополнительную информацию см. на https://openid.net/specs/openid-connect-core-1_0.html#ClientAuthentication[Client Authentication specifications].

|ID клиента
|Мир, выступающий клиентом OIDC для внешнего IDP. Для взаимодействия с внешним IDP область должна иметь идентификатор клиента OIDC, если вы используете код авторизации.

|Секрет клиента
|Секрет клиента от внешнего <_vault-administration,vault>>. Этот секрет необходим, если Вы используете код авторизации.

|Алгоритм подписи назначения клиента
|Алгоритм подписи, чтобы создать JWT утверждение в качестве клиентской аутентификации.
В случае подписи JWT с приватным ключом или секретным ключом клиента в качестве jwt, требуется его регистрация. Если алгоритм не задан, следующий алгоритм адаптируется. `RS256` адаптирован в случае JWT подписанного с приватным ключом.  `HS256` адаптирован в случае секрета Клиента как jwt.

|Аудитория к назначению клиента
|Зрители должны использовать для утверждения клиента. Значение по умолчанию — URL-адрес конечной точки IDP токена.

|Издатель
|{project_name} проверяет требования эмитента в ответах от IDP, против этого значения.

|Области по умолчанию
|Список OIDC областей действия {project_name} посылается с запросом на аутентификацию. Значение по умолчанию: `openid`. Пробел разделяет каждую область изображения.

|Prompt
|Параметр подсказки в спецификации OIDC. С помощью этого параметра вы можете принудительно переавторизоваться и другие опции. Смотрите спецификацию для более подробной информации.

|Принимает запросы=не переадресовывать от клиента
|Определяет, принимает ли IDP запросы переадресации аутентификации, содержащие параметр запроса `prompt=none`. Если реалм получает запрос авторизации в `prompt=none`, Realm проверяет, аутентифицирован ли пользователь в данный момент и возвращает ошибку `login_required`, если пользователь не вошел в систему. Когда {project_name} определяет IDP по умолчанию для запроса авторизации (используя параметр `kc_idp_hint` или с IDP по умолчанию для этого реалма), вы можете переслать запрос авторизации с помощью `prompt=none` на идентификатор по умолчанию. IDP по умолчанию проверяет подлинность пользователя там. Поскольку не все ВПЛ поддерживают запросы с помощью `prompt=none`, {project_name} использует этот переключатель для указания на то, что IDP по умолчанию поддерживает этот параметр перед перенаправлением запроса аутентификации.

Если пользователь не аутентифицирован в IDP, клиент все еще получает ошибку `login_required`. Если пользователь является подлинным в IDP, клиент все еще может получить ошибку `interaction_required`, если {project_name} должен отобразить страницы с аутентификацией, которые требуют взаимодействия с пользователем. Эта аутентификация включает необходимые действия (например, изменение пароля), экран согласия и экраны, на которых установлен поток `первый брокерский логин` или `post broker login`.

|Требуется параметр короткого состояния
|Этот переключатель должен быть включен, если провайдер идентификации не поддерживает длинное значение параметра `state`, посланного в первоначальном запросе аутентификации OIDC (EG. более 100 символов). В этом случае {project_name} попытается сделать сокращенный параметр `state` и может опустить некоторые клиентские данные для отправки в исходном запросе. Это может привести к ограничению функциональности в некоторых весьма угловых сценариях (ЭГ. в случае, если IDP перенаправляет на {project_name} с ошибкой в ответе аутентификации OIDC, {project_name} может потребоваться отображать страницу ошибки вместо того, чтобы переадресовать клиенту в случае истечения срока действия регистрации).

|Проверка подписей
|Определяет, если {project_name} проверяет подписи на внешнем токене IDP, подписанном этим IDP. Если *ON*, {project_name} должен знать публичный ключ внешнего OIDC IDP. Для производительности {project_name} кэширует публичный ключ внешнего поставщика идентификатора OIDC.

|Использовать JWKS URL
|Этот переключатель применим, если `Validate Signatures` *ON*. Если *Использовать URL-адрес JWKS* *ON*, {project_name} загружает публичные ключи IDP из URL-адреса JWKS. Скачивание новых ключей, когда поставщик идентификации генерирует новый клавиатур. Если *OFF*, {project_name} использует открытый ключ (или сертификат) из своей базы данных, , так что при изменении клавиатуры IDP, импортируйте новый ключ в базу данных {project_name}.

|URL-адрес JWKS
|URL указывает на местоположение IDP JWK ключей. Для получения дополнительной информации смотрите https://datatracker.ietf.org/doc/html/rfc7517[спецификация JWK]. Если вы используете внешний {project_name} в качестве IDP, вы можете использовать URL-адрес, например http://broker-keycloak:8180{kc_realms_path}/test/protocol/openid-connect/certs, если ваш брошенный {project_name} запущен на http://broker-keycloak:8180 и его мир `test`.

|Проверка открытого ключа
|Публичный ключ в формате PEM, который {project_name} использует для проверки внешних подписей IDP. Этот ключ применяется, если `Использовать JWKS URL` *OFF*.

|Проверка ID открытого ключа
|Эта настройка применяется, если *Использовать JWKS URL* *OFF*. Этот параметр определяет ID открытого ключа в формате PEM. Поскольку нет стандартного способа вычисления идентификатора ключа из ключа, внешние поставщики идентификации могут использовать различные алгоритмы из того, что использует {project_name}. Если значение этого поля не указано, {project_name} использует валидационный открытый ключ для всех запросов, независимо от идентификатора ключа, отправленного внешним IDP. Когда *ON*, это значение поля является ID ключа, который используется {project_name} для проверки подписей от провайдеров и должен соответствовать идентификатору ключа, указанному IDP.

|Параметры перенаправленного запроса
|Определите параметры запроса, которые будут направлены внешнему AS от первоначального запроса авторизации, отправленного на конечную точку авторизации. Можно ввести несколько параметров, разделяя запятыми (,). Доступные параметры
для пересылки являются любыми стандартными параметрами не OpenID Connect/OAuth или стандартными параметрами, которые доступны в виде клиентской заметки от сеанса аутентификации.

|Поддерживать утверждения клиентов
|Эта настройка позволяет использовать утверждения клиента, выданные провайдером для проверки подлинности клиентов. Для этого необходимо задать эмитента и ключи этого поставщика. Ключи могут быть установлены с помощью опции 'JWKS URL' или 'Validating public key'.

|Разрешить повторное использование утверждений клиента
|По умолчанию утверждение клиента не может быть использовано несколько раз. Если клиент не может получить новое утверждение клиента для каждого запроса, эта опция может быть включена для повторного использования того же утверждения клиента.

|Позволяет ID клиента как аудитория для утверждений
|Если включено, Идентификатор Клиента, настроенный в поставщике идентификации - это единственная допустимая аудитория для утверждений, используемых в аутентификации клиентов Federated client authentication и JWT Authorization Grants (lient Assertions and JWT Authorization Grant). Идентификатор клиента используется вместо token-url/issuer-url, определенного в соответствующих спецификациях. Обратите внимание, что это поведение не покрыто ни одним стандартом.
|===

Вы можете импортировать все эти данные конфигурации, указав URL или файл, указывающий на метаданные поставщика OpenID. Если вы подключились к {project_name} внешней IDP, вы можете импортировать настройки IDP из `<root>{kc_realms_path}/{realm-name}/.well-known/openid-configuration`. Эта ссылка является документом JSON, описывающим метаданные о IDP.

Если вы хотите использовать https://datatracker.ietf. rg/doc/html/rfc7516[Json Web Encryption (JWE)] ID токены или ответы UserInfo на провайдер, IDP должен знать открытый ключ для использования с {project_name}. Провайдер использует <<realm_keys, realm keys>> для различных алгоритмов шифрования для расшифровки токенов. {project_name} предоставляет стандартную xref:con-server-oidc-uri-endpoints_{context}[JWKS endpoint], которую IDP может использовать для автоматической загрузки ключей.
