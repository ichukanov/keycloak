[[_identity_broker_oauth]]
=== OAuth v2 идентификационные данные

брокеров {project_name} на основе OAuth v2 протокола. Эти идентификационные провайдеры (IDPs) должны поддерживать xref:con-oidc-auth-flows_{context}[Код авторизации Flow], определенный в спецификации для аутентификации пользователей и авторизации доступа.

.Процедура
. Нажмите на *Identity Providers* в меню.
. Из списка `Добавить провайдера` выберите `OAuth v2`.
. Введите начальные параметры конфигурации. Смотрите <<_general-idp-config, General IDP Configuration>> для получения дополнительной информации о параметрах конфигурации.
+
.Настройки OAuth2
|===
|Конфигурация |Описание

|URL авторизации
|Конечная точка URL авторизации.

|URL токена
|Конечная точка URL маркера.

|URL информации пользователя
|С конечной точки, с которой будет получена информация о пользователе. When invoking this endpoint, {project_name} will send
the request with the access token issued by the identity provider as a bearer token. В результате он ожидает, что ответ будет документом
JSON с претензиями, которые должны быть использованы для получения данных профиля пользователя, таких как ID, имя пользователя, электронную почту и фамилию.

|Аутентификация Клиента
|Определяет метод аутентификации Клиента {project_name} использует с кодом авторизации. В случае подписи JWT с приватным ключом, {project_name} использует закрытый ключ реалма. В других случаях определите клиентскую тайну. Дополнительную информацию см. на https://openid.net/specs/openid-connect-core-1_0.html#ClientAuthentication[Client Authentication specifications].

|ID клиента
|Мир, выступающий клиентом OIDC для внешнего IDP. Для взаимодействия с внешним IDP область должна иметь идентификатор клиента OIDC, если вы используете код авторизации.

|Секрет клиента
|Секрет клиента от внешнего <_vault-administration,vault>>. Этот секрет необходим, если Вы используете код авторизации.

|Алгоритм подписи назначения клиента
|Алгоритм подписи, чтобы создать JWT утверждение в качестве клиентской аутентификации.
В случае подписи JWT с приватным ключом или секретным ключом клиента в качестве jwt, требуется его регистрация. Если алгоритм не задан, следующий алгоритм адаптируется. `RS256` адаптирован в случае JWT подписанного с приватным ключом.  `HS256` адаптирован в случае секрета Клиента как jwt.

|Аудитория к назначению клиента
|Зрители должны использовать для утверждения клиента. Значение по умолчанию — URL-адрес конечной точки IDP токена.

|Области по умолчанию
|Разделенный пробелом список областей действия {project_name} посылается с запросом на аутентификацию.

|Prompt
|Параметр подсказки в спецификации OIDC. С помощью этого параметра вы можете принудительно переавторизоваться и другие опции. Смотрите спецификацию для более подробной информации.

|Принимает запросы=не переадресовывать от клиента
|Определяет, принимает ли IDP запросы переадресации аутентификации, содержащие параметр запроса `prompt=none`. Если реалм получает запрос авторизации в `prompt=none`, Realm проверяет, аутентифицирован ли пользователь в данный момент и возвращает ошибку `login_required`, если пользователь не вошел в систему. Когда {project_name} определяет IDP по умолчанию для запроса авторизации (используя параметр `kc_idp_hint` или с IDP по умолчанию для этого реалма), вы можете переслать запрос авторизации с помощью `prompt=none` на идентификатор по умолчанию. IDP по умолчанию проверяет подлинность пользователя там. Поскольку не все ВПЛ поддерживают запросы с помощью `prompt=none`, {project_name} использует этот переключатель для указания на то, что IDP по умолчанию поддерживает этот параметр перед перенаправлением запроса аутентификации.

Если пользователь не аутентифицирован в IDP, клиент все еще получает ошибку `login_required`. Если пользователь является подлинным в IDP, клиент все еще может получить ошибку `interaction_required`, если {project_name} должен отобразить страницы с аутентификацией, которые требуют взаимодействия с пользователем. Эта аутентификация включает необходимые действия (например, изменение пароля), экран согласия и экраны, на которых установлен поток `первый брокерский логин` или `post broker login`.

|Требуется параметр короткого состояния
|Этот переключатель должен быть включен, если провайдер идентификации не поддерживает длинное значение параметра `state`, посланного в первоначальном запросе авторизации OAuth2 (EG. более 100 символов). В этом случае {project_name} попытается сделать сокращенный параметр `state` и может опустить некоторые клиентские данные для отправки в исходном запросе. Это может привести к ограничению функциональности в некоторых весьма угловых сценариях (ЭГ. в случае, если IDP перенаправляет на {project_name} с ошибкой в ответе авторизации OAuth2, {project_name} может потребоваться отображать страницу ошибки вместо того, чтобы переадресовать клиенту в случае истечения срока действия регистрации).
|===

После того, как пользователь аутентифицируется с провайдером идентификации и перенаправляется обратно на {project_name}, брокер получит информацию о профиле пользователя из конечной точки, определенной в параметре «Информация о пользователе». Для этого
{project_name} вызовет эту конечную точку, используя токен доступа, выданный идентификационным провайдером в качестве токена предъявителя. Хотя стандарт OAuth2 поддерживает токены доступа в формате JWT, этот брокер предполагает, что токены доступа непрозрачны и что информация о пользовательском профиле должна быть получена с отдельной конечной точки.

Для того чтобы соотнести претензии с документа JSON, возвращенного конечной точкой профиля пользователя, вы можете установить следующие параметры, чтобы они были сопоставлены с атрибутами пользователя при федерации пользователя:


.Требования пользователя
|===
|Конфигурация |Описание

|ID требования
|Имя претензии из документа JSON, возвращенного конечной точкой профиля пользователя, представляющей уникальный идентификатор пользователя. Если не указано, по умолчанию `sub`.

|Имя пользователя
|Имя претензии из документа JSON, возвращенное конечной точкой профиля пользователя с именем пользователя. Если не указано, по умолчанию «preferred_username».

|Электронная почта
|Имя претензии из документа JSON, возвращенное конечной точкой профиля пользователя, представляющей адрес электронной почты пользователя. Если не указано, по умолчанию `email`.

|Имя владения
|Имя претензии из документа JSON, возвращенное конечной точкой профиля пользователя, содержащей полное имя пользователя. Если не указано, по умолчанию `name`.

|Данное имя
|Имя претензии из документа JSON, возвращенное конечной точкой профиля пользователя, представляющей заданное имя пользователя. Если не указано, по умолчанию `given_name`.

|Семейное имя
|Имя претензии из документа JSON, возвращенного конечной точкой профиля пользователя, содержащей имя семейства. Если не указано, по умолчанию `family_name`.
|===

Вы можете импортировать все эти данные конфигурации, предоставив URL-адрес или файл, указывающий на метаданные сервера авторизации. Если вы подключились к {project_name} внешней IDP, вы можете импортировать настройки IDP из `<root>{kc_realms_path}/{realm-name}/.well-known/openid-configuration`. Эта ссылка является документом JSON, описывающим метаданные о IDP.
