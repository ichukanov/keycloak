= Понимание движка рабочих процессов

Жизненный цикл и выполнение рабочих процессов в {project_name} управляется движком рабочих потоков.
Движок отвечает за обработку событий, создание рабочих процессов и обработку их шагов.
После создания рабочего процесса, движок выполняет цепочку шагов и управляет ею.

Выполнение цепочки шагов выполняется асинхронно и отделяется от запроса, вызвавшего событие, которое
вызвало рабочий процесс. This means that workflows are not scheduled nor executed immediately within the context of the request,
but rather sent to a task thread pool and scheduled to be executed later by the engine. Это позволяет повысить производительность и масштабируемость, так как шаги могут быть выполнены
в фоновом режиме без блокировки основного потока запроса.

Для незамедлительных шагов движок обрабатывает их, как только в пул потока задач будет передан выполнение рабочего процесса. Это означает, что немедленные шаги выполняются
сразу же, как только выполнение рабочего процесса подбирается рабочим потоком из пула.

Для запланированных этапов двигатель постоянно следит за состоянием всех активных рабочих процессов в реалме. This is done by a background
task that runs periodically to check for any workflow executions that have steps ready to be executed. The schedule steps of a workflow are also executed asynchronously
by the background task, using the same task thread pool as immediate steps.

== Настройка интервала выполнения запланированных шагов

По умолчанию, фоновое отслеживание задач выполняется каждые 12 часов, но этот интервал можно настроить, установив следующий параметр конфигурации сервера:

* `spi-events-listener--workflow-event-listener--step-runner-task-interval`: Определяет интервал, при котором фоновая задача запускается для проверки шагов рабочего процесса, которые должны выполняться.
Он следует тому же формату, что и в поле «после» рабочего процесса где вы можете указать интервал как число за которым следует единица времени (`ms`, `s` - по умолчанию, `m`, `h`, `d`) или используя формат длительности ISO-8601.

По умолчанию, первое выполнение фоновой задачи происходит после того, как прошло один полный интервал с момента запуска сервера.
Вы можете контролировать это, установив время начала, которое действует как якорь для приведения исполнения к предсказуемому графику:

* `spi-events-listener--workflow-event-listener--step-runner-task-start-time`: Определяет время дня, используемое для выравнивания выполнения фоновых задач в формате `HH:mm` (например, `02:00`, `14:30`), используя локальный часовой пояс сервера.

Когда установлено время начала, интервал задачи выравнивается с сеткой времени выполнения, привязанной к заданному времени. Например, со временем начала «02:00» и интервалом в «12h», задача всегда выполняется в 02:00 и 14:00 независимо от того, когда сервер был запущен. Если сервер запускается в 10:30, первое выполнение произойдет в 14:00.

Вы можете настроить эти параметры исходя из потребностей вашего реалма и ожидаемой частоты выполнения рабочего процесса.

== Настройка таймаута выполнения задач

Чаще всего шаги выполняются за короткое время. However, there might be cases where a step takes longer
to execute due to various reasons, such as network latency depending on an external service delays, or complex processing logic.

По умолчанию тайм-аут выполнения рабочего процесса установлен на *5 секунд*. Количество шагов, обрабатываемых в одном запуске
зависит от количества ближайших шагов, определенных в рабочем процессе, так как они выполняются последовательно в том же режиме. Как только
процесс сталкивается с запланированным шагом, он запланирует шаг и завершает выполнение.

Если выполнение рабочего процесса занимает больше времени, чем заданный тайм-аут, движок не сможет выполнить текущий шаг, и он попытается
запустить этот шаг в следующем запуске рабочего процесса. This is done to prevent long-running executions from blocking the workflow task thread pool
and impacting the execution of other workflows.

Вы можете настроить тайм-аут для задачи исполнителя рабочего процесса, установив следующий параметр конфигурации сервера:

* `spi-workflow--default--executor-task-timeout`: Определяет тайм-аут для выполнения рабочего процесса. Он следует тому же формату
используемый в шаге `after` рабочего процесса где вы можете указать интервал как число за которым следует единица времени (`ms`, `s` - по умолчанию, `m`, `h`, `d`)
или используя длительность ISO-8601.

== Соображения эффективности

Рабочие потоки могут вводить дополнительные накладные расходы. Это в основном верно, когда рабочие процессы часто срабатывают
(например, когда пользователи проходят аутентификацию. Несмотря на то, что рабочие потоки планируются и выполняются асинхронно, они все еще потребляют
системные ресурсы. Поэтому важно отслеживать производительность вашего реалма и соответственно корректировать определения рабочих процессов
для обеспечения оптимальной производительности.

Рассмотреть следующие передовые методы определения рабочих процессов:

* Держите рабочие процессы простыми и сфокусированными на конкретных задачах и избегайте длительной работы транзакций при выполнении шагов в рабочем процессе.
Это особенно верно для шагов, которые выполняются сразу после создания выполнения рабочего процесса.
* Рассмотрим возможность использования коротких таймаутов для выполнения шага во избежание блокирования выполнения рабочего процесса на слишком длинный и потенциально
высвободить пул потоков задач рабочего процесса и повлиять на выполнение других рабочих потоков.
* Отрегулируйте интервал фоновой задачи на основе ожидаемой частоты выполнения рабочего процесса в вашем реалме. Если ваш реалм имеет высокий объем выполнения рабочих процессов,
подумайте о сокращении интервала, чтобы избежать одновременной обработки нескольких рабочих процессов.
